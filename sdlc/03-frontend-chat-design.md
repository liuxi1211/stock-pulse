# 富交互 Chat 前端设计

> 本文档覆盖 C 端用户应用的富交互 Chat 页面前端设计，包括页面布局、对话容器体系、股票卡片组件、常用问题引导、SSE 流式对话、WebSocket 实时推送、前端架构与输入框交互。文档编号 03，对应规划书第五章并做深度扩展。

---

## 一、设计目标与原则

### 1.1 设计原则

规划书明确了五条关键设计原则，前端将其中与交互直接相关的四条落实为具体约束。

第一条是**富交互优先**。对话不只是文字气泡，而是股票卡片、K 线图、PE 分位图、资金流向图、结构化报告的富媒体流。前端的核心职责是把这些异构内容编排进同一条对话流，让用户在"问一句"之后"看到一串"有数据支撑的回复。

第二条是**对话内完成**。所有交互尽量在对话流内完成，避免跳转新页面打断沉浸感。股票卡片可以在对话内展开折叠，任务确认可以在对话内点击按钮提交，只有深度报告等重内容才跳转独立页面。

第三条是**数据与 AI 分离**。数值计算全部走后端确定性代码，AI 只做解读和表达。前端不承担任何估值计算或指标推导，所有数字都来自后端返回的 JSON，前端只负责渲染和排版。这条原则直接决定了容器的数据结构设计——每个容器的数据字段都是后端算好后传入的成品。

第四条是**用户引导**。提供常用问题模板和动态推荐，降低用户使用门槛。新手不需要知道"PE 分位"这个词，只要点击引导问题就能触发完整分析链路。

### 1.2 性能目标

富交互页面最大的体验杀手是等待。前端为全链路设定量化的性能基线，开发过程中以这些数字为准绳。

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 首屏加载时间（FCP） | < 1.5s | 静态资源走 Spring Boot 静态托管，ECharts 按需加载 |
| SSE 首字延迟 | < 800ms | 用户发送消息到看到第一个字符的时间，含网络往返和模型首 token |
| 图表渲染时间 | < 300ms | 从数据到达前端到 ECharts 完成绘制，单个图表 |
| 对话滚动帧率 | 60fps | 流式输出打字机效果期间不卡顿 |
| 侧边栏自选股刷新 | < 200ms | WebSocket 推送价格更新到 DOM 更新完成 |

前三个指标依赖后端配合（模型首 token 时间、接口响应时间），前端可控的是图表按需加载、DOM 更新批处理、虚拟滚动。后两个指标完全由前端架构决定，需要从渲染策略上保证。

### 1.3 用户体验目标

在性能基线之上，前端追求三个体验层级。

**高信噪比**是第一层。用户在 0.5 秒内抓到核心信息，弱化分割线，靠字号、字重、留白做视觉分层。股票卡片的当前价用大字号加粗，涨跌幅用颜色区分，次要指标用小字号灰色。容器之间不靠粗边框分隔，而是靠间距和背景色的微差。

**行动导向**是第二层。容器本身是交互触发器，不只是信息展示板。股票卡片点击可展开为标准卡片，标准卡片上的"深度分析"按钮可跳转详情页，"加入自选"按钮可直接触发后端操作并就地反馈结果。每个容器至少携带一个明确的行动入口。

**流式体验**是第三层。文字打字机输出消除等待焦虑，图表用骨架屏占位让用户知道"内容正在来"。流式体验的核心不是快，而是"让用户始终知道系统在做什么"——工具调用时显示工具名称和状态，图表数据加载时显示骨架，出错时显示明确的重试入口。

## 二、页面整体布局

### 2.1 桌面端布局

页面采用三栏式布局，从左到右依次是顶部导航栏、左侧边栏、对话主区域。顶部导航栏横跨整个页面宽度，下方分为左侧边栏和对话主区域两个纵向区域。

```
┌──────────────────────────────────────────────────────────────────────┐
│  顶部导航栏：Logo │ 搜索框 │ 自选股快捷入口 │ 报告中心 │ 消息通知 │ 用户  │
├────────────┬─────────────────────────────────────────────────────────┤
│            │                                                         │
│  左侧边栏   │              对话区域（主区域）                            │
│            │                                                         │
│  ┌────────┐│  ┌─────────────────────────────────────────────────┐    │
│  │新对话   ││  │  [常用问题引导区 - 首次进入展示]                    │    │
│  │────────││  │  快速查询 / 个股分析 / 板块行情 / 大盘分析          │    │
│  │历史会话  ││  │  选股筛选 / 自动任务 / 持仓管理                   │    │
│  │列表     ││  └─────────────────────────────────────────────────┘    │
│  │         ││                                                         │
│  │会话1    ││  ┌─── 用户消息 ───┐                                    │
│  │会话2    ││  │ 分析一下茅台     │                                    │

│  │         ││  ┌─── AI 回复 ──────────────────────────────────────┐  │
│  │────────││  │ 股票行情卡片 / 数据图表 / 结构化文本 / 操作按钮     │  │
│  │自选股   ││  └─────────────────────────────────────────────────┘  │
│  │快捷面板 ││                                                         │

│  │+2.3%   ││  │  输入框  [附件] [语音] 输入消息...  [发送]        │    │
│  │────────││  └─────────────────────────────────────────────────┘    │

```

左侧边栏宽度固定 260px，可折叠到 48px（仅图标模式）。对话主区域占据剩余空间，内部上下分为对话消息区和输入框区。对话消息区使用 `flex: 1` 撑满高度并支持纵向滚动，输入框固定在底部。

### 2.2 响应式设计

桌面端（>= 1200px）显示完整三栏。平板端（768px-1199px）将左侧边栏改为可滑出抽屉，默认隐藏，点击汉堡菜单按钮展开。移动端（< 768px）进一步简化，顶部导航栏的搜索框收起为搜索图标，自选股快捷入口合并进侧边栏抽屉。

| 断点 | 侧边栏 | 顶部导航 | 对话区 | 输入框 |
|------|--------|----------|--------|--------|
| >= 1200px | 固定展开，可折叠 | 完整显示 | 全宽 | 固定底部，支持多行 |
| 768-1199px | 抽屉式，默认隐藏 | 搜索框收窄 | 全宽 | 固定底部 |
| < 768px | 全屏抽屉 | 仅 Logo + 铃铛 + 用户头像 | 全宽 | 适配软键盘 |

移动端有一个特殊处理：当用户聚焦输入框时，软键盘弹出会压缩可视区域。对话区需要监听 `visualViewport` 的 resize 事件，动态调整滚动位置，确保输入框不被键盘遮挡。输入框在移动端高度限制为 2 行，超出后内部滚动。

### 2.3 各区域状态管理

页面有四个需要独立管理状态的区域。

**顶部导航栏状态**包含搜索框的聚焦/失焦、消息通知铃铛的红点数量和未读列表的展开/折叠、用户菜单的下拉。搜索框失焦时显示占位提示文字，聚焦时展开搜索建议下拉。铃铛红点数来自 WebSocket 推送的未读通知计数，点击展开通知列表（详见第七章）。

**左侧边栏状态**包含展开/折叠切换、当前激活的会话 ID、会话列表的加载状态、自选股快捷面板的实时价格。侧边栏折叠时仅保留图标列，鼠标悬停时展开为浮层。会话列表按 `updated_at` 倒序排列，当前激活会话高亮。自选股面板的价格通过 WebSocket 实时推送更新，涨跌用红绿颜色闪烁提示。

**对话区状态**是最复杂的部分。它维护当前会话的消息列表数组、流式输出中的临时消息、滚动锁定状态（用户手动上滚查看历史时暂停自动滚动到底部）、以及各容器的加载/展开状态。消息列表是单一数据源，所有容器的渲染都由它驱动。

**输入框状态**包含输入内容、发送中禁用、附件上传中、语音录制中。发送中状态下输入框不锁死（用户可以继续输入下一条），但发送按钮变为 loading 态，防止重复提交。

## 三、对话容器体系

### 3.1 容器总览

对话流中每条 AI 回复不是简单的文字气泡，而是**富媒体容器**的有序组合。一条 AI 回复可以包含多个容器，按后端返回的顺序依次渲染。例如用户问"分析一下茅台的基本面"，AI 回复可能包含一段引导文字 + 一张股票行情卡片 + 一张 PE 分位图 + 一段结构化分析文本 + 操作按钮组。

六种容器类型及其触发场景如下：

| 容器类型 | 用途 | 触发场景 | 示例 |
|----------|------|----------|------|
| 股票行情卡片 | 展示实时行情 + 关键指标 | 用户查询某只股票 | 茅台当前价/涨跌幅/PE/PB + K 线缩略图 |
| 数据图表卡片 | 可视化数据展示 | AI 分析需要图表辅助 | PE 历史折线图、资金流向柱状图 |
| 结构化文本容器 | Markdown 渲染分析结论 | 深度分析、研报摘要 | 分层排版的分析报告 |
| 交互表单容器 | 引导用户补充信息 | 需要用户确认或选择 | 选择分析维度的快捷按钮 |
| 报告预览容器 | 完整报告的对话内预览 | 生成深度研究报告 | 摘要 + 查看完整报告等操作 |
| 任务确认容器 | 确认定时任务/盯盘规则 | 用户创建任务 | cron 表达式 + 确认创建按钮 |

### 3.2 容器通用数据结构

所有容器共享一个外层信封结构，通过 `type` 字段区分具体类型。这个设计让前端的流式组装逻辑统一化——先解析信封确定容器类型，再按类型分派到对应的渲染器。

```json
{
  "messageId": "msg_20260806_001",
  "conversationId": "conv_001",
  "role": "assistant",
  "createdAt": "2026-08-06T14:30:00Z",
  "containers": [
    {
      "id": "ctn_001",
      "type": "stock_card",
      "data": { },
      "actions": [
        { "id": "expand", "label": "展开详情", "type": "expand" },
        { "id": "analyze", "label": "深度分析", "type": "navigate", "target": "/stock/600519" }
      ]
    }
  ]
}
```

`containers` 是一个有序数组，前端按顺序渲染。每个容器有独立的 `id` 用于追踪展开/折叠状态，`actions` 定义容器内挂载的操作按钮。流式输出时，容器的 `data` 字段可能是分片到达的，前端需要做增量组装（详见第六章）。

### 3.3 股票行情卡片

展示单只股票的实时行情和核心估值指标，是对话中出现频率最高的容器类型。

```json
{
  "type": "stock_card",
  "data": {
    "tsCode": "600519.SH",
    "name": "贵州茅台",
    "price": 1705.00,
    "change": 38.50,
    "pctChg": 2.31,
    "volume": 1950000,
    "amount": 32500000000,
    "pe": 35.2,
    "pb": 11.8,
    "dividendYield": 1.2,
    "pePercentile": 78,
    "miniKline": [1680, 1690, 1685, 1700, 1705],
    "aiSummary": "当前PE处于近5年78%分位，估值偏高，但资金面转正..."
  }
}
```

渲染逻辑：卡片头部显示股票名称和代码，右侧显示涨跌幅（红涨绿跌，跟随 A 股惯例）。主体区域分两行，第一行是当前价和成交额，第二行是 PE、PB、股息率三个核心指标，每个指标下方标注分位或定性标签（偏高/偏低/适中）。底部是一条迷你 K 线缩略图（sparkline），用纯 CSS 或轻量 canvas 绘制，不启动 ECharts 实例以节省性能。`aiSummary` 作为卡片底部的一句话解读，用灰色小字呈现。

交互行为：点击卡片任意区域展开为标准卡片（Level 2，详见第四章）。操作按钮"深度分析"跳转到股票详情页（Level 3），"加入自选"调用后端接口并就地显示"已加入"反馈，"创建盯盘"将股票代码带入任务确认容器。

### 3.4 数据图表卡片

承载各类数据可视化，包括 K 线折线图、PE 分位图、资金流向柱状图、技术指标图、行业对比雷达图等。

```json
{
  "type": "chart_card",
  "data": {
    "title": "PE 历史分位",
    "subtitle": "近5年",
    "chartType": "line",
    "categories": ["2021-08", "2022-02", "2022-08", "2023-02", "2023-08", "2024-02", "2024-08", "2025-02", "2025-08", "2026-08"],
    "series": [
      {
        "name": "PE-TTM",
        "data": [55.1, 48.3, 42.1, 38.5, 36.2, 34.8, 33.5, 32.1, 33.8, 35.2],
        "color": "#5470c6"
      },
      {
        "name": "中位数",
        "data": [35.0, 35.0, 35.0, 35.0, 35.0, 35.0, 35.0, 35.0, 35.0, 35.0],
        "type": "markLine"
      }
    ],
    "markArea": {
      "low": { "from": 28, "to": 35, "color": "#91cc75", "label": "低估区" },
      "high": { "from": 40, "to": 60, "color": "#ee6666", "label": "高估区" }
    },
    "dataSource": "Tushare daily_basic",
    "dataDate": "2026-08-06"
    }
}
```

渲染逻辑：根据 `chartType` 启动对应的 ECharts 配置（详见第四章图表配置要点）。`categories` 是 X 轴数据，`series` 是数据序列。`markArea` 用于标注估值区间（低估/合理/高估），以背景色块呈现。卡片底部小字标注 `dataSource` 和 `dataDate`，让用户知道数据的来源和时效。

交互行为：图表支持 hover 显示数据点 tooltip，支持图例点击切换序列显隐。移动端图表缩放为静态截图模式（禁用 tooltip 以避免触摸冲突），点击图表放大为全屏可交互模式。

### 3.5 结构化文本容器

渲染 AI 输出的 Markdown 格式分析结论，支持标题分层、加粗强调、数据高亮、表格和有序列表。

```json
{
  "type": "structured_text",
  "data": {
    "content": "## 估值分析\n\n当前 **PE 35.2** 处于近5年 **78%分位**，属于偏高水平。\n\n对比同行业：\n\n| 指标 | 茅台 | 五粮液 | 泸州老窖 |\n|------|------|--------|----------|\n| PE | 35.2 | 28.1 | 22.5 |\n| PB | 11.8 | 6.2 | 5.1 |\n\n> 以上数据不构成投资建议。",
    "highlights": ["PE 35.2", "78%分位"]
  }
}
```

渲染逻辑：使用 `marked.js` 将 Markdown 转换为 HTML，再用 `highlight.js` 处理代码块。`highlights` 数组中的关键词在渲染后做额外的高亮标注（黄色背景）。底部固定追加合规声明"不构成投资建议"。流式输出时，每收到一个 text chunk 就增量追加到 `content` 并重新渲染（详见第六章打字机效果）。

交互行为：纯文本容器本身不携带操作按钮，但如果出现在报告预览容器之前，作为报告的引言部分。长文本支持折叠——超过 200 字时默认折叠为摘要，点击"展开全文"显示完整内容。

### 3.6 交互表单容器

当 AI 需要用户补充信息或做选择时，以快捷按钮组的形式呈现，避免用户重新打字。

```json
{
  "type": "interactive_form",
  "data": {
    "prompt": "请选择分析维度",
    "multiSelect": false,
    "options": [
      { "id": "technical", "label": "技术面", "value": "technical", "icon": "chart-line" },
      { "id": "fundamental", "label": "基本面", "value": "fundamental", "icon": "file-text" },
      { "id": "valuation", "label": "估值", "value": "valuation", "icon": "scale" }
    ]
  }
}
```

渲染逻辑：表单容器渲染为一组水平排列的按钮，按钮带图标和文字。`multiSelect` 为 true 时按钮可多选并显示选中态，为 false 时单选即提交。选中后按钮高亮，底部出现"确认"按钮（多选场景）或直接触发提交（单选场景）。

交互行为：用户选择后，前端将选中的 `value` 作为用户消息发送，同时在表单容器上标记已选项，禁用未选项。这样对话历史中保留了"AI 问了什么、用户选了什么"的完整记录。

### 3.7 报告预览容器

当 AI 生成深度研究报告时，在对话流中展示报告摘要和操作入口，完整报告存入报告中心。

```json
{
  "type": "report_preview",
  "data": {
    "reportId": "rpt_20260806_001",
    "title": "贵州茅台深度分析报告",
    "reportType": "个股深度研究",
    "generatedAt": "2026-08-06T14:30:00Z",
    "dataAsOf": "2026-08-06",
    "summary": "茅台当前估值偏高（PE 78%分位），但基本面稳健，ROE 持续维持在 30% 以上...",
    "toc": [
      "一句话观点",
      "基本面速览",
      "技术面研判",
      "估值分析",
      "竞争格局",
      "财务分析",
      "资金面分析",
      "风险提示"
    ],
    "keyMetrics": {
      "pe": 35.2,
      "pb": 11.8,
      "roe": 31.2,
      "pePercentile": 78
    }
  }
}
```

渲染逻辑：卡片头部显示报告标题、类型标签和生成时间。主体区域显示 `summary` 摘要文字和 `toc` 目录（折叠式列表，点击展开）。底部是 `keyMetrics` 的关键指标速览（横向排列的小卡片），以及操作按钮组。

交互行为：操作按钮包括"查看完整报告"（跳转报告中心详情页）、"收藏"（调用后端收藏接口，按钮变为已收藏态）、"创建盯盘任务"（将股票代码带入任务确认容器）、"导出 PDF"（Phase 4 功能）。

### 3.8 任务确认容器

用户通过自然语言创建定时任务或盯盘规则时，AI 先解析出结构化参数，以确认表单形式让用户确认后再提交。

```json
{
  "type": "task_confirm",
  "data": {
    "taskType": "monitor",
    "ruleType": "price",
    "fields": [
      { "key": "taskName", "label": "任务名称", "value": "茅台价格监控", "editable": true },
      { "key": "tsCode", "label": "监控标的", "value": "600519.SH 贵州茅台", "editable": false },
      { "key": "condition", "label": "触发条件", "value": "跌破 1700.00", "editable": true },
      { "key": "channels", "label": "推送渠道", "value": ["站内消息", "邮件"], "editable": true, "options": ["站内消息", "邮件", "微信"] }
    ],
    "cronExpr": "0 * * * * ?",
    "cronDescription": "交易日盘中每分钟检查"
  }
}
```

渲染逻辑：表单式布局，每个 `field` 渲染为一行，`editable` 为 true 的字段可编辑。推送渠道字段渲染为多选 checkbox。底部显示 `cronDescription` 的人类可读描述和操作按钮。

交互行为：用户可修改可编辑字段后点击"确认创建"，前端将修改后的 `fields` 提交到后端创建任务。点击"修改"进入全字段编辑模式，点击"取消"则放弃创建并在对话中显示"已取消"标记。确认后后端注册 Quartz 任务，返回成功消息。

### 3.9 容器组合规则

一条 AI 回复可以包含多个容器，组合规则由后端的意图路由和 Graph 编排决定，前端只负责按序渲染。常见的组合模式有以下几种。

**轻量查询**返回"结构化文本 + 股票行情卡片"：先一句话回答，再附上数据卡片。**单方法分析**返回"股票行情卡片 + 数据图表卡片 + 结构化文本"：先给数据，再给图表，最后给结论。**多步骤研究**返回"结构化文本（进度说明）+ 报告预览容器"：先说明分析过程，再给报告入口。**操作指令**返回"任务确认容器"：直接弹出确认表单。**选股筛选**返回"结构化文本 + 多个股票行情卡片（列表）"：先说明筛选条件，再列出结果。

前端在渲染多个容器时，容器之间用 12px 的间距分隔，不画分割线。同类型容器（如多个股票行情卡片）在选股结果场景下以网格布局排列（桌面端 2 列，移动端 1 列）。

## 四、股票卡片组件设计

股票卡片是对话中最核心的富媒体组件，分三个层级：对话流内嵌的轻量卡片、点击展开的标准卡片、跳转的独立详情页。三个层级逐层展开信息密度，用户按需深入。

### 4.1 Level 1 轻量卡片

对话流中默认展示的形态，信息密度最低，目标是让用户一眼看到价格和趋势。

```
┌─────────────────────────────────────────┐
│ 贵州茅台 600519.SH              [+2.3%]│
│ 1705.00    成交额 32.5亿    PE 35.2     │
│ [迷你K线图 ▁▃▅▇▆▄▅▇]                  │
└─────────────────────────────────────────┘
```

**展示字段清单与优先级**：

| 字段 | 优先级 | 来源 | 格式化规则 |
|------|--------|------|------------|
| 股票名称 | P0 | stock_basic | 原文 |
| 股票代码 | P0 | stock_basic | 带 .SH/.SZ 后缀 |
| 当前价 | P0 | daily_quote | 保留 2 位小数 |
| 涨跌幅 | P0 | daily_quote | 百分比，红涨绿跌 |
| 成交额 | P1 | daily_quote | 超亿显示"亿"，超万显示"万" |
| PE-TTM | P1 | daily_basic | 保留 1 位小数 |
| 迷你 K 线 | P2 | daily_quote | 近 10 日收盘价 sparkline |

渲染逻辑：卡片高度约 88px，宽度撑满对话气泡。左上角股票名称加粗 16px，右侧涨跌幅用 14px 带背景色块。第二行三列等分展示当前价、成交额、PE。底部 sparkline 高度 24px，用 SVG path 绘制折线，涨为红色描边，跌为绿色。

交互行为：整张卡片可点击，点击后在原位展开为标准卡片（Level 2），使用高度动画过渡。卡片右上角 hover 时显示一个"固定"图钉按钮，点击可将卡片固定到侧边栏自选股面板。

### 4.2 Level 2 标准卡片

### 4.3 标准卡片图表配置要点

三张图表共用 ECharts 实例，但各自有差异化配置。

**K 线折线图**使用 `line` 类型，X 轴为日期，Y 轴为价格。关键配置：`smooth: true` 让折线平滑，`symbol: 'none'` 隐藏数据点标记减少视觉噪音，`areaStyle` 设置从折线到 X 轴的渐变填充（涨为红色渐变、跌为绿色渐变），`dataZoom` 启用但不显示缩放条（仅支持触摸拖拽）。图表高度 120px，禁用图例和标题以节省空间。

**PE 分位图**使用 `line` 类型叠加 `markArea`。关键配置：X 轴为时间（近 5 年按月），Y 轴为 PE 值。叠加一条水平 `markLine` 表示中位数，用虚线绘制。用 `markArea` 标注三个区间——低估区（绿色半透明）、合理区（灰色半透明）、高估区（红色半透明），让用户直观看到当前 PE 落在哪个区间。当前 PE 值用一个 `markPoint` 标注在折线末端。

**资金流向图**使用 `bar` 类型，正负值分色。关键配置：主力净流入为正时柱体红色，为负时柱体绿色。Y 轴穿过 0 轴。叠加一条 `line` 类型的 5 日均值线，用 `markLine` 绘制。X 轴为日期，仅显示近 20 个交易日。图表高度 100px。

三张图表共用一个 `tooltip` 配置：`trigger: 'axis'`，`axisPointer` 用 `shadow` 类型。移动端统一禁用 tooltip 和 dataZoom 触摸，改为静态展示，点击放大。

### 4.4 Level 3 股票详情页

点击标准卡片"深度分析"按钮跳转的独立页面，信息密度最高，适合系统性研究。详情页不在对话流内渲染，是一个独立的 SPA 路由页面。

页面采用标签页布局，顶部固定股票名称、代码、实时价格和涨跌幅。标签页包括：技术面（完整 K 线图 + MA/MACD/KDJ/BOLL 技术指标，可切换指标叠加）、基本面（财务三表数据 + ROE/净利增速/毛利率等关键指标趋势图）、估值（PE/PB 历史分位 + 同业对比雷达图）、资金面（主力资金流向 + 龙虎榜 + 融资融券 + 北向持股趋势）、AI 分析（综合分析报告，结构化呈现）。

技术面标签页的 K 线图使用 ECharts 的 `candlestick` 类型，支持 MA5/MA10/MA20 均线叠加切换，下方副图显示 MACD 或 KDJ（可切换）。dataZoom 同时支持滑动条和框选缩放。估值标签页的雷达图对比同行业 3-5 只股票的 PE/PB/ROE/股息率/营收增速五个维度。

### 4.5 卡片数据加载策略

卡片的渲染不是等数据全部到齐才显示，而是分阶段渐进呈现。

**骨架屏阶段**：容器数据到达前端之前，先渲染卡片骨架——灰色的占位块，模拟最终布局的形状和尺寸。轻量卡片的骨架是两行灰色条 + 一条 sparkline 占位条。标准卡片的骨架是三列指标块 + 三个图表占位区。骨架屏使用 CSS 的 `linear-gradient` 动画做微光扫过效果，传递"正在加载"的信号。

**数据填充阶段**：容器数据通过 SSE 到达后（详见第六章），将骨架替换为真实内容。文字字段直接渲染，图表字段启动 ECharts 实例。三个图表实例按顺序初始化而非并行，避免同时创建三个 ECharts 实例导致主线程卡顿。每个图表初始化完成后立即 `resize` 到容器尺寸。

**交互就绪阶段**：所有数据填充完毕后，启用卡片的点击和按钮交互，之前点击卡片只显示 loading 态。操作按钮（加入自选、创建盯盘）在点击时显示独立 loading 态，完成后就地反馈结果文字。

### 5.2 动态推荐逻辑

引导问题不只是静态列表，还会根据用户行为做动态调整。推荐逻辑在前端侧实现，依赖两个输入：当前会话上下文和用户历史行为。

**会话内推荐**基于当前对话的股票实体和意图。当用户刚问了"分析一下茅台的基本面"，AI 回复结束后，对话区底部显示"你可能还想问"区域，推荐 3 个相关问题。推荐规则：如果当前涉及特定股票，推荐该股票的其他维度（技术面怎么样、估值贵不贵、资金面分析）；如果当前是选股筛选，推荐细化筛选条件（加入ROE限制、改为高股息）；如果当前创建了任务，推荐查看任务状态或创建关联任务。

```json
{
  "type": "follow_up_suggestions",
  "data": {
    "context": "stock_analysis",
    "entity": { "tsCode": "600519.SH", "name": "贵州茅台" },
    "suggestions": [
      "茅台的技术面怎么样",
      "茅台的估值贵不贵",
      "茅台最近的资金流向"
    ]
  }
}
```

**跨会话推荐**基于用户历史行为画像。前端维护一个轻量的用户行为计数器（localStorage 存储），记录用户最常查询的股票、最常使用的分析类别、最近创建的任务。新建对话时，引导区顶部的"最近常用"区域优先展示这些高频问题。例如用户过去一周频繁查询白酒股，引导区顶部显示"今天白酒板块怎么样"。

### 5.3 @ 提及股票的自动联想

输入框支持 `@` 符号触发股票提及，自动联想补全股票名称或代码。这个功能让用户在提问时快速引用股票实体，而不需要手打完整代码。

**实现方案**：监听输入框的 `input` 事件，当检测到 `@` 字符时进入"提及模式"，捕获 `@` 之后的输入文本作为搜索关键词。以 150ms 的防抖间隔向后端发送搜索请求（`GET /api/stock/search?q=茅台`），后端从 stock_basic 表中模糊匹配名称和代码，返回前 10 条结果。前端在下拉浮层中展示结果列表，每条显示股票名称、代码和所属行业。

用户通过键盘上下键或鼠标点击选择一条结果后，前端将 `@` 和搜索文本替换为一个不可删除的股票标签（chip），形如 `@[贵州茅台 600519]`。标签在输入框中作为一个整体存在，光标无法进入标签内部。实际提交时，标签被转换为 `{{stock:600519.SH}}` 的结构化标记发送给后端，后端解析后注入对话上下文。

下拉浮层在以下情况关闭：用户选择了结果、用户按 Esc、用户输入空格或删除了 `@`、浮层失去焦点。浮层定位在输入框上方（移动端）或下方（桌面端），宽度不超过 320px，最大高度 280px 超出滚动。

## 六、SSE 流式对话实现

### 6.1 SSE 消息协议设计

对话流式输出采用 SSE（Server-Sent Events）协议，后端通过 `text/event-stream` 逐条推送事件。前端使用浏览器原生 `EventSource` API 接收。一次 AI 回复由多个 SSE 事件组成，每个事件携带一个 JSON 信封。

SSE 事件分为五类，通过 `event` 字段区分：

```
event: text_chunk
data: {"messageId":"msg_001","containerId":"ctn_001","text":"当前PE"}

event: text_chunk
data: {"messageId":"msg_001","containerId":"ctn_001","text":"处于近5年"}

event: container_start
data: {"messageId":"msg_001","containerId":"ctn_002","type":"stock_card","meta":{"tsCode":"600519.SH"}}

event: container_data
data: {"messageId":"msg_001","containerId":"ctn_002","data":{"price":1705.00,"pctChg":2.31}}

event: container_end
data: {"messageId":"msg_001","containerId":"ctn_002"}

event: tool_call
data: {"messageId":"msg_001","toolName":"queryDailyQuote","status":"success","duration":320}

event: error
data: {"messageId":"msg_001","code":"MODEL_TIMEOUT","message":"模型响应超时，请重试"}

event: done
data: {"messageId":"msg_001","message":"complete"}
```

**text_chunk** 携带流式文本片段，前端将其追加到对应容器的 `content` 字段。同一容器的多个 text_chunk 按到达顺序拼接。**container_start** 标记一个新容器开始，携带容器类型和元数据，前端创建骨架占位。**container_data** 携带容器的数据字段，可能分多次到达（大对象分片），前端增量合并。**container_end** 标记容器数据完整，前端将骨架替换为最终渲染。**tool_call** 携带工具调用的状态信息，前端在对话流中显示"正在查询茅台行情..."的进度提示。**error** 携带错误码和消息，前端显示错误状态和重试按钮。**done** 标记整条 AI 回复结束，前端解锁输入框。

### 6.2 前端消息组装逻辑

前端维护一个 `MessageAssembler` 模块，负责将流式事件组装成完整的消息对象。核心数据结构是一个 `Map<messageId, Message>`，每个 Message 包含一个 `Map<containerId, Container>`。

组装流程分三步。收到 `container_start` 时，创建一个新的 Container 对象，根据 `type` 渲染对应类型的骨架屏插入 DOM。收到 `text_chunk` 或 `container_data` 时，将数据追加到对应 Container 对象，并触发增量渲染——文本容器追加文字并执行打字机效果，图表容器累积数据但不渲染（等 container_end）。收到 `container_end` 时，标记 Container 为完整状态，执行最终渲染（启动 ECharts 实例、启用交互按钮）。

```javascript
class MessageAssembler {
  constructor() {
    this.messages = new Map();        // messageId -> Message
    this.containers = new Map();       // containerId -> Container
  }

  handleEvent(event) {
    const data = JSON.parse(event.data);
    switch (event.event) {
      case 'text_chunk':
        this.appendText(data.containerId, data.text);
        break;
      case 'container_start':
        this.startContainer(data);
        break;
      case 'container_data':
        this.mergeContainerData(data);
        break;
      case 'container_end':
        this.finalizeContainer(data.containerId);
        break;
      case 'tool_call':
        this.showToolProgress(data);
        break;
      case 'error':
        this.handleError(data);
        break;
      case 'done':
        this.completeMessage(data.messageId);
        break;
    }
  }
}
```

### 6.3 打字机效果

文本容器的流式输出需要打字机效果，让文字逐字浮现而非整块跳出。但逐字渲染会频繁触发 DOM 更新和 marked.js 重新解析，性能开销大。折中方案是**按 chunk 追加 + 节流渲染**。

前端维护一个文本缓冲区，每收到 `text_chunk` 就追加到缓冲区。渲染采用 50ms 节流：每 50ms 取缓冲区当前内容重新渲染一次。对于 Markdown 文本，渲染策略是先做纯文本追加（在最后一个 Markdown 块内追加文字），当检测到换行符或 Markdown 语法符号时触发一次完整 Markdown 重新解析。这样在打字过程中，未完成的 Markdown 行以纯文本呈现，完成的行渲染为格式化 HTML。

滚动行为：打字机输出期间，如果用户当前在对话底部（滚动条距离底部 < 50px），则自动滚动跟随新内容。如果用户手动上滚查看历史，则暂停自动滚动，在底部显示一个"有新消息"的悬浮按钮，点击后滚回底部。

### 6.4 错误处理和重连机制

SSE 连接的生命周期管理是前端可靠性的关键。`EventSource` 原生支持断线重连，但默认行为不够细致，前端需要覆盖。

**连接建立**：用户发送消息时创建 `EventSource` 连接，URL 携带 `conversationId` 和 `messageId`。连接建立后前端标记消息为"流式输出中"状态。

**正常结束**：收到 `done` 事件后，前端主动调用 `eventSource.close()` 关闭连接，清理资源。这是最常见的结束方式。

**异常断开**：`EventSource` 的 `onerror` 回调触发时，分两种情况处理。如果是网络抖动导致断开（已接收过数据但连接中断），前端显示"连接中断"提示并提供"重试"按钮，不自动重连（避免重复消息）。如果是连接建立阶段就失败（首字都没收到），前端自动重试 1 次，间隔 2 秒，仍失败则显示错误提示。

**超时处理**：前端设置一个 60 秒的空闲超时计时器，如果 60 秒内没有收到任何事件，主动关闭连接并提示"响应超时"。收到任意事件时重置计时器。这个兜底机制防止后端静默挂起导致用户无限等待。

**消息幂等**：每次重试时携带原 `messageId`，后端根据 `messageId` 判断是否已有部分输出，从断点续传而非重头开始。如果后端不支持断点续传，前端清理未完成的消息后重新发送完整请求。

## 七、WebSocket 实时推送设计

### 7.1 连接管理

WebSocket 负责所有非对话场景的实时推送，包括盯盘通知、任务完成、系统通知。与 SSE 的区别在于：SSE 是请求-流式响应模式（用户发消息后建立、回复完关闭），WebSocket 是长连接模式（用户登录后建立、全程保持）。

**连接建立**：用户登录成功后，前端创建 WebSocket 连接 `ws://host/ws/notification?userId=xxx`。连接建立后发送一条 `hello` 握手消息，后端确认后开始推送消息。前端在 `sessionStorage` 中标记连接已建立，页面刷新后重新连接。

**断线重连**：采用指数退避策略。首次断开后立即重连，第二次间隔 1 秒，第三次 2 秒，第四次 4 秒，最大间隔 30 秒。重连期间顶部导航栏显示"连接中"状态提示。重连成功后清除提示，并请求一次增量通知（`GET /api/notifications/since?timestamp=xxx`）补齐断线期间错过的消息。

**心跳机制**：前端每 30 秒发送一个 `ping` 帧，后端回复 `pong`。如果 10 秒内未收到 `pong`，前端认为连接已死，主动关闭并触发重连。心跳的另一个作用是保持连接不被 Nginx 等中间代理的超时断开（默认 60 秒空闲断开）。

### 7.2 消息协议设计

### 7.3 前端通知展示逻辑

通知的展示分三层：铃铛红点、通知列表、详情跳转。

**通知列表**：点击铃铛展开的下拉面板，按时间倒序展示通知。每条通知包含类型图标（盯盘/任务/系统三色区分）、标题、摘要、时间。未读通知高亮背景。面板顶部有筛选标签（全部/未读/盯盘/任务/系统），底部有"查看全部"链接跳转到完整通知中心页面。面板内支持单条已读、删除和批量操作。

**详情跳转**：每条通知点击后跳转到对应内容。盯盘通知跳转到股票详情页并展开触发时的分析报告；任务完成通知跳转到报告中心对应报告详情页；系统通知根据 `actionUrl` 跳转或就地关闭。跳转后通知自动标记为已读。

通知列表的数据持久化在后端 `push_notification` 表中，前端通过 WebSocket 接收实时推送，通过 REST API 拉取历史列表。断线重连后用 `since` 时间戳补齐增量，保证不丢消息。

## 八、前端技术栈与架构

### 8.1 技术栈选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 基础框架 | 原生 JS + ES Modules（初期）/ Vue 3（拆分后） | 初期轻量快速，后期可平滑迁移 |
| 图表库 | ECharts 5 | 丰富的金融图表类型，与 stock-pulse 技术栈一致 |

### 8.3 组件化策略

原生 JS 没有组件框架，但可以通过**模块工厂模式**实现可复用的组件。每个容器组件导出一个工厂函数，接收容器数据和挂载点，返回一个组件实例对象，包含 `render()`、`update()`、`destroy()` 三个方法。

```javascript
// containers/stock-card.js
export function createStockCard(containerData, mountEl) {
  let expanded = false;

  function render() {
    mountEl.innerHTML = template(containerData);
    bindEvents();
  }

  function expand() {
    expanded = true;
    // 渲染 Level 2 标准卡片
  }

  function destroy() {
    // 清理 ECharts 实例和事件监听
  }

  function bindEvents() {
    mountEl.addEventListener('click', expand);
  }

  return { render, expand, destroy };
}
```

**容器注册表**（`container-registry.js`）维护类型到工厂函数的映射。消息组装器收到 `container_start` 事件时，从注册表查找对应的工厂函数创建实例，存入容器实例表。收到后续事件时调用实例的 `update()` 方法。消息清理时调用 `destroy()` 释放 ECharts 实例和事件监听，防止内存泄漏。

```javascript
// containers/container-registry.js
import { createStockCard } from './stock-card.js';
import { createChartCard } from './chart-card.js';
// ...其他容器导入

const registry = {
  stock_card: createStockCard,
  chart_card: createChartCard,
  structured_text: createStructuredText,
  interactive_form: createInteractiveForm,
  report_preview: createReportPreview,
  task_confirm: createTaskConfirm,
};

export function createContainer(type, data, mountEl) {
  const factory = registry[type];
  if (!factory) {
    console.warn(`未知容器类型: ${type}`);
    return null;
  }
  return factory(data, mountEl);
}
```

### 8.4 状态管理方案

原生 JS 时代没有 Pinia/Vuex，但可以用**事件总线 + 状态切片**的模式实现轻量状态管理。`state.js` 导出一个全局状态对象，各模块通过事件总线订阅状态变更。

```javascript
// core/state.js
import { EventBus } from './event-bus.js';

const state = {
  conversation: {
    currentId: null,
    messages: [],
    streaming: false,
  },
  watchlist: {
    stocks: [],
    loading: false,
  },
  notification: {
    unreadCount: 0,
    list: [],
  },
  sidebar: {
    collapsed: false,
  },
};

export const State = {
  get(key) {
    return state[key];
  },
  set(key, value) {
    state[key] = value;
    EventBus.emit(`state:${key}:change`, value);
  },
  update(key, updater) {
    const next = updater(state[key]);
    state[key] = next;
    EventBus.emit(`state:${key}:change`, next);
  },
};
```

**对话状态**管理当前会话 ID、消息列表、流式输出状态。消息列表是单一数据源，对话区渲染完全由它驱动。流式输出期间，临时消息挂在消息列表末尾，组装完成后转为正式消息。

**自选股状态**管理自选股列表和实时价格。自选股列表通过 REST API 初始化加载，实时价格通过 WebSocket 推送更新。侧边栏的自选股面板订阅这个状态，价格变动时局部更新 DOM。

**通知状态**管理未读数量和通知列表。未读数量由 WebSocket 推送实时更新，通知列表通过 REST API 拉取。铃铛组件订阅未读数量，通知面板订阅通知列表。

### 8.5 从原生 JS 迁移到 Vue 3 的路径规划

迁移不是一步到位的重写，而是分阶段渐进替换。规划在 Phase 4 前后端分离时启动迁移，分三个阶段完成。

**阶段一：引入 Vue 3 + Vite 构建**。将前端资源从 Spring Boot static 目录迁出为独立项目，引入 Vite 作为构建工具。此时页面仍以原生 JS 为主，Vue 3 仅用于新开发的功能模块。原生 JS 和 Vue 3 通过事件总线桥接，保证两套体系可以共存。这一阶段的目标是建立 Vue 3 工程骨架，不改变现有功能。

**阶段二：逐容器迁移**。将六种容器组件逐个从原生 JS 工厂模式迁移为 Vue 3 单文件组件（SFC）。迁移顺序按使用频率：先迁移股票行情卡片和数据图表卡片（最高频），再迁移结构化文本和交互表单，最后迁移报告预览和任务确认。每迁移一个容器，在容器注册表中将原生工厂替换为 Vue 组件的挂载逻辑。ECharts 配置逻辑直接复用，封装为 Vue 3 的 composable（`useECharts`）。

**阶段三：整体迁移完成**。所有组件迁移完毕后，移除原生 JS 模块和事件总线，全面采用 Vue 3 的响应式状态管理和组件通信。状态管理从手写 State + EventBus 迁移到 Pinia。路由从多 HTML 页面迁移到 Vue Router 的 SPA 模式。

迁移过程中的关键约束：容器数据结构（JSON schema）保持不变，后端 SSE 和 WebSocket 协议保持不变。这样后端在迁移期间完全不需要改动，前端可以独立部署和回滚。

## 九、输入框交互设计

### 9.1 基础交互

输入框固定在对话区底部，左侧是附件和语音按钮，中间是文本输入区域，右侧是发送按钮。文本区域默认单行高度，输入内容超出时自动扩展为多行，最大高度 120px（约 5 行），超出后内部滚动。

**多行输入**：输入框使用 `textarea` 而非 `input`，通过监听 `input` 事件动态调整高度。每次输入时，先重置 `scrollHeight` 为 auto，再读取 `scrollHeight` 设置为实际高度，但不超过 120px 上限。这样输入框跟随内容自适应增长，不会出现内容被截断的情况。

**Enter 发送 / Shift+Enter 换行**：监听 `keydown` 事件，Enter 键（不按 Shift）触发发送，Shift+Enter 插入换行符。这个行为对标主流 Chat 产品的惯例，用户不需要学习新交互。在移动端（触摸设备）不启用此快捷键，因为移动端键盘的 Enter 通常用于换行，发送通过右侧按钮触发。

**发送中禁用**：发送消息后，发送按钮变为 loading 态（旋转图标），但输入框不锁死——用户可以继续输入下一条消息。当流式回复正在进行时，如果用户再次点击发送，新消息会排队等待当前回复结束后发送。这样设计是因为深度分析报告可能需要 30 秒以上，期间不应该阻塞用户输入。

### 9.2 附件上传

点击附件按钮弹出文件选择器，支持图片上传（K 线截图分析，Phase 4 功能）。上传过程中附件按钮显示进度条，上传完成后在输入框上方显示文件缩略图标签。文件标签可点击删除。提交消息时，附件 ID 作为消息的 `attachments` 字段一并发送。

### 9.3 语音输入

语音按钮在移动端显示，点击后启动浏览器 `webkitSpeechRecognition` API（Chrome 支持）进行语音转文字。录音过程中按钮变为红色脉动动画，转写结果实时填入输入框。用户可以手动编辑转写结果后发送。桌面端隐藏语音按钮，因为桌面端用户更习惯键盘输入。

### 9.4 @ 提及交互流程

@ 提及的完整交互流程如下，从前置条件到提交流程闭环。

用户在输入框中输入 `@`，前端检测到 `@` 后进入提及模式，在 `@` 位置下方弹出搜索浮层。用户继续输入"茅台"，前端以 150ms 防抖向后端发送搜索请求，浮层展示匹配结果。用户通过键盘上下键浏览结果，按 Enter 或点击选中"贵州茅台 600519.SH"。

选中后，前端将 `@茅台` 文本替换为一个股票标签元素。标签在 `textarea` 中无法直接渲染为可视化组件，因此输入框改为 `contenteditable` 的 div 容器，标签作为 `span` 内嵌其中。标签显示为蓝色背景的胶囊形状"贵州茅台 600519"，带有删除按钮（hover 显示）。

实际提交时，前端遍历输入框中的所有股票标签，将它们转换为 `{{stock:600519.SH}}` 结构化标记，与纯文本拼接后发送给后端。后端解析这些标记，将股票实体注入对话上下文，AI 在回复时可以直接引用这些实体而无需二次识别。

## 十、前端与后端的协作约定

### 10.1 接口风格

C 端前端与后端之间有三类通信通道，各有适用场景。

**REST API** 用于非流式的增删改查：会话管理（创建/列表/删除）、自选股管理（增删改查）、报告中心（列表/详情/收藏）、通知列表拉取、股票搜索。统一返回 `ApiResponse` 包装格式，前端封装统一的错误处理逻辑。

**SSE** 用于对话流式输出：用户发送消息后建立 EventSource 连接，接收流式事件直到 `done` 事件后关闭。SSE 是短连接（单次对话的生命周期），不是长连接。

**WebSocket** 用于实时推送：用户登录后建立，全程保持，接收盯盘通知、任务完成、系统通知。WebSocket 是长连接，需要心跳保活和断线重连。

### 10.2 数据时效标注

所有容器数据都携带 `dataSource` 和 `dataDate` 字段，前端在容器底部小字展示。这个设计源自规划书"数据与 AI 分离"原则的延伸——不仅数值计算走确定性代码，用户也需要知道每个数字的来源和时效，以建立对数据的信任。

行情数据标注"Tushare daily_quote，截止 2026-08-06 收盘"。估值数据标注"Tushare daily_basic，截止 2026-08-06"。财务数据标注"Tushare 财务报表，截止 2026Q2"。AI 解读部分明确标注为"AI 解读"，与确定性数据视觉区分。
