# 产品概览与可行性分析

> 本文档基于《AI 优先的股票分析平台 - 项目规划书》第一至三章，对项目定义、用户画像、竞争格局、可行性验证和设计原则进行深度扩展和优化，作为后续架构设计与开发实施的依据。

---

## 一、项目定义与定位

### 1.1 项目定义

本平台是一个面向 C 端个人投资者的**互联网 AI 投资助手**，以自然语言对话为核心交互方式，采用 SaaS 模式云端部署。用户通过富交互 Chat 页面提问股票相关问题，平台调用数据查询、因子计算、研究分析、定时任务等能力，以**股票卡片、实时图表、结构化报告**等富媒体形式返回结果，而非纯文本回复。

平台的核心价值主张是：把散户从"信息过载但有效分析不足"的困境中解放出来。用户问一句"茅台现在贵不贵"，得到的不是一段文字，而是一张**股票卡片**叠加一张 PE 历史折线图，再配上 AI 的通俗解读。这种从自然语言到"数据 + 图表 + 结论"的富媒体跨越，是建立用户信任的关键。

### 1.2 产品边界

明确边界是避免范围蔓延的前提。下表界定平台的做与不做：

| 维度 | 做什么 | 不做什么 |
|------|--------|----------|
| **分析性质** | 数据整理、可视化呈现、方法论解读 | 不提供买卖建议、不预测涨跌 |
| **用户范围** | 面向个人 A 股投资者的 C 端产品 | 不服务机构客户、不做 B 端投顾 |
| **交易能力** | 模拟持仓管理（手动录入） | 不对接券商交易接口、不执行真实交易 |
| **数据范围** | A 股市场为主，Phase 4 扩展港美股 | 不做期货、期权、外汇等衍生品 |
| **部署形态** | 云端 SaaS，用户开箱即用 | 不提供本地私有化部署 |
| **AI 边界** | 数值计算走确定性代码，AI 只做解读和表达 | 不让 AI 直接输出价格、涨跌幅等数值 |

### 1.3 与 stock-pulse 的关系

stock-pulse 是一个**规则化量化**本地部署系统，面向个人开发者的策略回测和信号生成。本平台是**对话化研究**的 C 端互联网产品，面向更广泛的散户投资者群体。两者的交互范式、用户群体、部署方式完全不同。

本平台从零构建全新代码库，不复用 stock-pulse 的任何代码。借鉴的价值在于两点：一是 stock-pulse 已验证的 **Tushare 六层数据架构**和五条数据采集铁律，为 ERP 系统的数据治理提供设计参考；二是 stock-pulse 在 AI skill 研究方法体系上的积累，为本平台 18 种研究方法的 Graph 节点映射提供方法论基础。新平台与 stock-pulse 各自独立演进，互不依赖。

## 二、目标用户画像

### 2.1 用户群体概述

平台的目标用户是个人 A 股投资者，核心特征是：有一定投资经验但缺乏专业研究能力，信息来源碎片化且难以整合。原报告列出了三类用户特征，本节将其扩展为三个完整的典型用户画像（Persona），作为产品设计和需求优先级判断的基准。

### 2.2 Persona 一：陈志远 - 忙碌的上班族

| 属性 | 内容 |
|------|------|
| **年龄** | 35 岁 |
| **职业** | 互联网公司产品经理 |
| **投资经验** | 6 年，懂基础概念但没时间深研 |
| **资金量级** | 50-100 万 |
| **核心痛点** | 工作繁忙没时间盯盘，经常错过关键时点；自选股散落在多个 App 里，缺乏统一管理 |
| **使用场景** | 通勤地铁上快速查看持仓涨跌；盘中没空看盘，希望系统在异动时主动推送；收盘后看一份简明的复盘 |
| **期望价值** | 设置好规则后系统自动盯盘，只在他关心的时点推送提醒，把碎片时间利用起来 |

陈志远代表平台最具规模潜力的用户群体：**时间稀缺型投资者**。这类用户不需要系统替他做决策，但极度需要系统替他"盯着"。平台的智能盯盘引擎、定时任务推送、自选股统一管理，是服务这类用户的核心抓手。

### 2.3 Persona 二：林晓雯 - 看不懂研报的散户

| 属性 | 内容 |
|------|------|
| **年龄** | 43 岁 |
| **职业** | 个体经营文具店 |
| **投资经验** | 3 年，主要靠朋友推荐和财经新闻 |
| **资金量级** | 10-30 万 |
| **核心痛点** | 券商研报术语太专业看不懂；财经 App 推送的信息过载，真假难辨；买卖决策主要靠"感觉" |
| **使用场景** | 看到某只股票的新闻后，想问一句得到易懂的分析；想了解自己持仓的股票"到底好不好"；需要图表来辅助理解但自己不会看 K 线 |
| **期望价值** | 像跟懂行的朋友聊天一样问问题，得到数据加图表加大白话解读，降低理解门槛 |

林晓雯代表平台的**信任稀缺型用户**。这类用户对纯文字 AI 回复天然怀疑，但看到具体数据和图表后信任度会显著提升。平台的富交互 Chat 体验、常用问题引导、股票卡片可视化，是降低这类用户使用门槛的关键设计。她们不需要最深的分析，但需要最直观的呈现。

### 2.4 Persona 三：赵磊 - 数据驱动的年轻投资者

| 属性 | 内容 |
|------|------|
| **年龄** | 28 岁 |
| **职业** | 后端开发工程师 |
| **投资经验** | 2 年，喜欢用数据和工具辅助决策 |
| **资金量级** | 20-50 万 |
| **核心痛点** | 多个工具来回切换，数据口径不一致；分析结论无法溯源，不知道"这个 PE 分位是怎么算的"；做完一次深度分析后，过段时间想对比却找不到 |
| **使用场景** | 深度分析个股的估值分位和资金流向；定期生成持仓诊断报告；对比不同时间点的分析结论变化 |
| **期望价值** | 数据可溯源、分析有逻辑链、报告可管理和横向对比，形成自己的研究资产库 |

赵磊代表平台的**深度型用户**。这类用户占比不一定最大，但使用深度和留存率最高，是口碑传播的主力。平台的专业报告中心、报告对比功能、数据快照可追溯，是服务这类用户的核心差异化能力。

### 2.5 用户旅程图

以下从"发现平台"到"日常使用"的完整路径，描述三类典型用户的共性旅程：

```
阶段一：发现平台
  渠道：财经社区帖子 / 朋友推荐 / 搜索"股票分析AI"
  用户状态：好奇但怀疑，"又一个套壳ChatGPT？"
  关键触点：落地页展示富交互对话Demo（非纯文本截图）

阶段二：注册登录
  方式：手机号 / 微信扫码
  用户状态：期待快速体验，不愿填太多信息
  关键触点：注册后直接进入Chat页面，无冗余引导

阶段三：首次体验
  触发：常用问题引导区展示分类问题
  典型行为：点击"分析一下茅台的基本面"
  关键时刻：收到股票卡片+图表+AI解读的富媒体回复
  转折点：如果首次回复是纯文本，用户大概率流失

阶段四：深度使用
  触发：信任建立后，开始查询自选股
  典型行为：添加自选股、发起深度分析、查看报告
  关键触点：报告预览容器中的"收藏到报告中心"按钮

阶段五：个性化配置
  触发：用户发现手动查太累
  典型行为：对话创建盯盘规则、设置定时晨报
  关键触点：任务确认容器的"确认创建"交互

阶段六：日常使用
  触发：盯盘触发推送 / 定时任务执行
  典型行为：查看推送 -> 点击跳转详情 -> 对比历史报告
  关键触点：通知中心铃铛红点 + WebSocket实时推送

阶段七：持续留存
  触发：报告中心积累一定量报告后
  典型行为：报告对比、持仓复盘、跨会话引用历史报告
  关键触点："上次分析的茅台现在怎么样了"的跟踪分析能力
```

整个旅程的**首次体验**阶段是最关键的留存分水岭。如果用户第一次提问后收到的是纯文本回复，大概率会判定为"又一个套壳产品"然后流失。只有富媒体回复才能在 30 秒内建立差异化认知，这是平台交互设计的首要原则。

## 三、核心差异化分析

### 3.1 竞品全景对比

基于原报告的竞品矩阵，扩展为更完整的六维度对比。对比对象覆盖海外对话型产品（FinChat）、国内 Agent 集合型产品（财搭子）、券商原生 AI（AI 涨乐）、自动化报告工具（daily_stock_analysis）和自然语言选股工具（同花顺问财）。

| 维度 | 本平台 | FinChat | 财搭子 | AI 涨乐 | daily_stock_analysis | 同花顺问财 |
|------|--------|---------|--------|---------|----------------------|------------|
| **数据深度** | 25+ Tushare 接口 + 六层治理，数据可溯源 | 依赖第三方 API，口径不透明 | 无本地数据治理，Agent 直接调外部 | 绑定华泰行情 | 依赖单一数据源 | 依赖同花顺自有数据 |
| **分析方法** | 18 种方法映射为 Graph 节点，可组合编排 | 通用问答，无方法论体系 | 32 个 Agent 扁平堆叠，缺乏编排深度 | 券商研报摘要 | 固定模板日报 | 仅筛选，无深度分析 |
| **交互体验** | 富交互 Chat：股票卡片 + 实时图表 + 数据可视化 + 常用问题引导 | 纯文本对话 + 图表 | 对话 + 模拟回放 | 纯对话 | 无对话，固定报告 | 自然语言筛选框 |
| **个性化** | 自动盯盘 + 异动推送 + 自选股管理 + 持仓管理 | 无自定义任务 | 预设 Agent，无自定义 | 低，绑定账户 | 无 | 无 |
| **报告管理** | 专业报告中心（分类/搜索/收藏/对比/导出） | 无 | 散在对话中 | 账户内 | 无独立管理 | 无 |
| **部署形态** | C 端 SaaS，用户无需部署 | SaaS | SaaS | 券商 App 内 | 开源本地部署 | Web 工具 |

### 3.2 差异化点深度论证

#### 差异化点一：数据深度与可溯源

**竞品现状**：FinChat 依赖第三方 API 拼接数据，数据口径不透明，用户无法追溯某个数值的来源。财搭子的 32 个 Agent 各自调用外部数据源，缺乏统一的数据治理层，数据一致性无法保证。

**本平台方案**：参考 stock-pulse 已验证的 Tushare 六层架构（Config -> Client + RateLimiter -> DO + Mapper -> Service -> DataInitService -> DataGovernanceController），由 B 端 ERP 系统统一采集 25+ 个 Tushare 接口数据，经过质量检测后写入 MySQL。每份分析报告标注生成时的**数据快照**，用户可查看"AI 给出这个结论时用了什么数据、数据截止什么时间"。

**优势论证**：数据可溯源是建立用户信任的基础。散户最大的痛点不是"找不到数据"，而是"不知道数据可不可信"。当用户能点击报告中的任意数值查看到来源和时间戳，信任感会从"相信 AI"升级为"相信数据"。六层架构已在 stock-pulse 中验证过可行性，不是从零试错。

#### 差异化点二：研究方法的可编排性

**竞品现状**：财搭子将 32 个垂直 Agent 扁平堆叠，Agent 之间缺乏编排关系，无法实现"先做技术面分析、再结合基本面交叉验证"的多步骤研究流程。FinChat 是通用问答，没有体系化的方法论支撑。

**本平台方案**：将 18 种研究方法映射为 Spring AI Graph 的节点，通过 Workflow 编排实现多节点串联、条件分支和并行执行。例如"全面分析茅台"会编排 tear-sheet -> 技术面 -> 估值分析 -> 资金面 -> 风险提示等多个节点，每个节点产出结构化片段，最终拼装为完整报告。

**优势论证**：深度研究与简单问答的本质区别在于"多步骤推理链"。扁平堆叠的 Agent 只能回答单一维度的问题，而 Graph 编排能模拟专业研究员的分析路径。这种编排能力的上限决定了平台分析深度的天花板，是技术壁垒而非产品壁垒，竞品短期难以复制。

#### 差异化点三：富交互对话体验

**竞品现状**：绝大多数竞品的对话是纯文本问答，最多附一张静态图表。用户需要在文字中寻找关键数字，认知负荷高。同花顺问财虽然支持自然语言选股，但返回的是筛选列表，没有图表和解读。

**本平台方案**：对话流中的每条 AI 回复是**富媒体容器**，包含股票行情卡片（实时价格 + 关键指标 + 迷你 K 线）、数据图表卡片（PE 分位图、资金流向图）、结构化文本容器和交互表单容器。文字打字机流式输出 + 图表骨架屏占位，消除等待焦虑。

**优势论证**：富交互不是锦上添花，而是降低散户理解门槛的刚需。林晓雯这类用户看不懂纯文字的 PE 解读，但看一张 PE 历史折线图加一行"当前处于近 5 年 78% 分位"的标注，立刻就能理解。竞品的纯文本交互在用户首次体验时就会流失这类用户。

#### 差异化点四：用户自建定时任务与智能盯盘

**竞品现状**：FinChat 无自定义任务能力。财搭子支持预设 Agent 但不支持用户自建规则。AI 涨乐的推送绑定券商账户体系。所有竞品的定时推送都是平台预设的，用户无法自定义触发条件和推送内容。

**本平台方案**：用户通过对话创建监控规则（"盯住茅台，跌破 1700 就通知我"）和定时任务（"每天早上 8 点给我发茅台晨报"）。LLM 解析自然语言为结构化规则，Quartz 调度执行，触发时调用 AI 生成简评并推送。8 种盯盘规则类型覆盖价格、涨跌幅、技术指标、资金流向、财务事件等场景。

**优势论证**：陈志远这类上班族的核心诉求是"替我盯着"。自建任务能力把平台从"被动问答工具"升级为"主动投研助手"，这是留存率的关键驱动力。竞品的预设推送无法满足个性化需求，用户只能被动接收平台认为重要的信息。

#### 差异化点五：专业报告中心

**竞品现状**：所有竞品的分析报告都散落在对话历史中。用户上周做了一次茅台深度分析，这周想回看时只能翻聊天记录，且无法对比两次分析结论的变化。财搭子的报告虽然在对话中有回放，但无法跨会话检索和管理。

**本平台方案**：分析报告生成后独立存入**报告中心**，支持按股票、行业、类型三个维度分类，提供搜索、收藏、对比、导出功能。报告内每个数据点标注来源和时间戳。用户可对比两份不同时间的同类报告，查看关键指标变化和 AI 观点变化。

**优势论证**：报告资产化是赵磊这类深度用户的核心诉求，也是平台区别于"用完即走"工具的关键。当报告积累到一定量后，报告中心本身成为用户的研究资产库，迁移成本极高，构成用户留存壁垒。

#### 差异化点六：C 端 SaaS 部署形态

**竞品现状**：AI 涨乐强绑定华泰证券账户生态，非华泰客户无法使用。daily_stock_analysis 需要本地部署，技术门槛高。券商 AI 普遍以"增强客户黏性"为目标，而非独立产品。

**本平台方案**：纯 C 端 SaaS 产品，用户手机号或微信注册即用，不绑定任何券商。ERP 系统负责数据采集和治理，C 端应用只读查询，数据权限隔离清晰。

**优势论证**：不绑定券商意味着用户基数不受券商客户池限制，也不受券商业务利益约束（券商 AI 不会建议用户转户）。独立 SaaS 产品的商业模型更灵活，未来可探索会员订阅等变现路径。

## 四、可行性分析

### 4.1 需求真实性验证

散户的信息获取路径通常是：财经 App 推送 -> 股吧雪球讨论 -> 券商研报（看不懂）-> 凭感觉买卖。核心痛点是**信息过载但有效分析不足，且缺乏数据可视化支撑信任**。这不是一个伪需求，而是每天数千万 A 股散户的真实困境。

三个约束必须正视：第一，**AI 分析的边界**，数值计算交给确定性代码，AI 只做解读和表达，避免幻觉；第二，**合规红线**，不提供买卖建议，所有分析标注"不构成投资建议"；第三，**成本控制**，模型调用按量计费，数据积分成本需控制。这三个约束不是可行性障碍，而是设计约束，在架构层面已有对应方案。

### 4.2 技术可行性

原报告给出了五维度的技术评估。下表保留原评估结论，并为每个维度补充具体的技术验证方案：

| 维度 | 原评估 | 验证方案 |
|------|--------|----------|
| **Tushare 数据** | 可行 | 参考 stock-pulse 已验证的六层架构。验证方式：在 ERP 项目中实现 stock_basic + daily_quote 两个接口的完整六层链路，触发增量更新确认 data_pull_log 记录成功，查询 MySQL 确认数据写入。两个接口跑通即可证明 25+ 接口的架构可行性。 |
| **AI 对话框架** | 可行 | Spring AI Alibaba 提供 ChatClient / Graph / RAG / Function Calling 全栈。验证方式：在 C 端项目中接入通义千问 DashScope API，跑通最小 ChatClient 对话，再封装 1 个 Function Calling 工具（queryDailyQuote）验证工具调用链路。 |
| **富交互前端** | 可行 | SSE 流式 + ECharts 图表 + 组件化卡片。验证方式：实现一个股票卡片组件 + 一张 PE 分位折线图，通过 SSE 接口接收流式文字 + 图表数据，验证打字机效果和图表渲染。ECharts 的金融图表类型已在 stock-pulse 中验证。 |
| **C 端 SaaS 部署** | 可行 | Spring Boot 单体可支撑初期，后续按需拆分。验证方式：单机部署 C 端 + ERP + 计算服务三组件，用 JMeter 模拟 50 并发用户 SSE 对话，观察响应延迟和内存占用。JDK 21 虚拟线程可支撑高并发 SSE 连接。 |
| **用户个性化** | 可行 | Quartz 调度 + WebSocket 推送 + 事件驱动架构。验证方式：创建一个价格监控规则（茅台跌破某价位触发），Quartz 调度每分钟检查，触发后通过 WebSocket 推送消息到前端，验证端到端链路。 |

### 4.3 成本可行性

#### 4.3.1 模型调用成本估算

平台采用分级模型策略，轻量查询用低成本模型，深度分析用均衡模型。以下基于阿里云百炼 2026 年中国内地定价估算（价格为每百万 Token）：

| 模型 | 用途 | 输入单价 | 输出单价 | 适用场景 |

| qwen-flash | 超轻量查询 | 0.15 元 | 1.5 元 | 意图路由、简单问答、参数解析 |
| qwen-plus | 均衡分析 | 0.8 元 | 2 元 | 单方法分析、报告节点解读、盯盘简评 |
| qwen3.6-plus | 深度推理 | 2 元 | 12 元 | 多步骤研究报告、复杂逻辑推理 |

以单个活跃用户日均 10 次对话为例，其中 7 次轻量查询、3 次深度分析（每次深度分析涉及 5 个 Graph 节点调用），月度成本估算如下：

| 场景 | 日均调用次数 | 单次输入 Token | 单次输出 Token | 月输入量 | 月输出量 | 月成本 |
|------|------------|--------------|--------------|---------|---------|--------|
| 轻量查询（qwen-flash） | 7 | 3,000 | 800 | 0.63M | 0.17M | 约 0.35 元 |
| 深度分析（qwen-plus，5 节点/次） | 15 | 4,000 | 3,000 | 1.80M | 1.35M | 约 4.14 元 |

按不同用户规模推算月度模型成本：

| 用户规模 | 月模型成本 | 年模型成本 |
|----------|----------|----------|
| 100 人（内测） | 约 450 元 | 约 5,400 元 |

#### 4.3.2 数据积分成本

Tushare Pro 采用积分制，积分决定接口调用频率和权限等级，而非按次消耗。平台需要 2000 积分以解锁 25+ 接口的调用权限。

### 4.4 合规可行性

#### 4.4.1 证券投资咨询合规边界

平台的核心合规原则是**定位为信息整理和研究辅助工具，不提供证券投资咨询**。根据《证券法》和《证券投资顾问业务暂行规定》，证券投资咨询业务的核心特征是"向客户提供投资建议并获取经济利益"。平台通过以下设计规避这一边界：

| 合规要点 | 平台设计 | 说明 |
|----------|----------|------|
| **不提供买卖建议** | AI 分析只做数据呈现和方法论解读，不输出"建议买入""建议卖出"等指令性语言 | 从 Prompt 层面约束模型输出范围 |
| **不预测涨跌** | 不做价格预测，不做收益率承诺，不做择时建议 | 所有分析基于历史和当前数据，不涉及未来预测 |
| **风险提示** | 所有分析报告和深度回复标注"本内容不构成投资建议" | 通过合规过滤 Advisor 在输出层强制注入 |
| **数据来源合规** | Tushare Pro 是合规的商业数据服务，非爬虫抓取 | 数据获取方式合法，可追溯 |
| **不代客交易** | 持仓管理为模拟持仓（手动录入），不对接券商交易接口 | 不涉及代客理财 |

#### 4.4.2 合规落地方案

合规不是写在文档里的一句话，而是需要在技术架构中落地的约束。平台通过三层机制保障合规：第一，**Prompt 层约束**，在系统提示词中明确禁止输出买卖建议类语言，限制 AI 的输出范围；第二，**Advisor 层过滤**，在 Spring AI 的输出 Advisor 中接入合规过滤器，扫描 AI 回复中的敏感词（"买入""卖出""满仓""加杠杆"等），命中则拦截或改写；第三，**审计层追溯**，ai_analysis_audit 表记录每次 AI 调用的完整输入输出，便于事后审计和问题定位。

需要注意的是，平台不持有用户资金、不执行真实交易、不提供个性化投顾服务，因此不触及证券投资咨询牌照的要求。但如果未来商业模型变化（如引入付费投顾服务），需要重新评估牌照合规性。

## 五、设计原则

### 5.1 数据与 AI 分离

**原则**：数值计算全部走确定性代码，AI 只做解读和表达，避免幻觉。

**落地指导**：所有价格、涨跌幅、PE 分位、财务指标等数值由后端通过 Tushare 数据查询或 Python 计算服务得出，AI 模型不参与数值计算。具体做法是：Function Calling 工具返回结构化数据（JSON），前端组件负责渲染数值和图表，AI 只接收数据摘要后生成解读文字。报告生成时，每个数据点在 data_snapshot 字段中标注来源和时间戳，用户可追溯。在 Code Review 中设立检查项：如果 AI 的输出中包含未经工具调用验证的具体数值，判定为违规。

### 5.2 富交互优先

**原则**：对话不只是文字，而是股票卡片、图表、报告的富媒体流。

**落地指导**：意图路由层根据用户意图决定输出形态，轻量查询返回股票卡片，单方法分析返回图表卡片，多步骤研究返回报告预览容器。前端建立组件化卡片体系，每种富媒体容器对应一个独立组件，通过 SSE 流式协议分批推送文字和图表数据。设计验收标准：任何一条 AI 回复如果只有纯文本且用户问了股票相关问题，视为不达标。富交互不是可选项，而是默认输出形态。

### 5.3 渐进式架构

**原则**：初期前后端一体，做大后拆分微服务。

**落地指导**：Phase 0-2 阶段前端资源放在 Spring Boot 的 static 目录下，后端提供 REST API + SSE 接口，前后端同项目同部署，追求开发速度。Phase 3+ 当用户量增长或前端复杂度提升时，拆分为独立 Vue 3 前端项目和纯 API 后端。关键是在初期代码中保持前后端逻辑的清晰边界：前端只通过 HTTP/SSE 接口与后端通信，不嵌入后端逻辑；后端接口设计遵循 RESTful 规范，为未来分离预留空间。避免在初期就引入前后端分离的工程复杂度。

### 5.4 用户引导

**原则**：提供常用问题模板，降低用户使用门槛。

**落地指导**：首次进入或新建对话时展示常用问题引导区，按快速查询、个股分析、板块行情、大盘分析、选股筛选、自动任务、持仓管理七个分类展示引导问题。每次对话结束后底部推荐 3 个相关问题，引导用户深入探索。输入框支持 `@` 提及股票代码自动联想。引导问题的设计不是随意的，而是基于用户旅程中每个阶段的典型需求，帮助用户从"不知道问什么"过渡到"知道平台能做什么"。

### 5.5 报告资产化

**原则**：分析报告是对话产物，更是可管理、可回溯的用户资产。

**落地指导**：报告生成后独立存入 analysis_report 表，与对话消息解耦。报告中心提供按股票、行业、类型三个维度的分类筛选，支持全文搜索、收藏标记、同类报告横向对比和导出。每份报告记录 data_snapshot（生成时的数据快照 JSON），用户可查看 AI 结论背后的数据依据。对话与报告的关系是"对话中生成、报告中心管理"，用户问"上次分析的茅台现在怎么样了"时，系统从报告中心检索历史报告并与当前数据对比，形成跟踪分析。这一原则的核心是把一次性的对话产出转化为可持续积累的研究资产，提升用户长期留存。
