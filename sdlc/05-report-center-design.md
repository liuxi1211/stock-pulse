## 一、报告资产化理念

### 1.1 核心理念

分析报告不是一次性的对话产物，而是**用户的可管理资产**。这是报告中心设计的出发点，也是区别于竞品的核心差异化点。FinChat、财搭子等竞品的分析报告散落在对话历史中，用户想找回三周前做过的茅台分析，只能翻聊天记录，而聊天记录往往已经超出上下文窗口、被摘要或截断。本平台将每一次深度分析、每一份定时任务报告都作为独立资产持久化存储，赋予它独立的 ID、分类标签、检索索引和生命周期。

资产化带来三个直接收益。第一是**可检索**，用户可以按股票、行业、类型、时间、标签任意组合检索历史报告，不再依赖对话记忆。第二是**可对比**，同一只股票不同时点的报告可以横向对比，观察估值和观点的变化轨迹。第三是**可追溯**，每份报告标注生成时的数据快照和来源接口，用户可以回查"AI 给出这个结论时用了什么数据"，建立对 AI 分析的信任。

### 1.2 报告生命周期管理

报告作为资产，需要完整的生命周期管理，覆盖从生成到清理的全过程。

```
生成 ──────────> 存储 ──────────> 检索 ──────────> 归档 ──────────> 过期清理
 │                │                │                │                │
 │ 对话触发       │ 持久化到        │ 按多维条件      │ 超过活跃期     │ 超过保留期
 │ 定时触发       │ analysis_report│ 查询和搜索      │ 移至归档区     │ 物理删除
 │ 手动重生成     │ + 向量索引      │                │ 仅保留摘要     │ 保留摘要
```

**生成阶段**是生命周期的起点。报告生成有三种触发方式：对话中用户请求深度分析、定时任务自动产出、用户在报告中心手动重新生成。生成完成后报告立即进入存储阶段，同时写入关系表和向量索引，确保既可结构化查询也可语义检索。

**存储阶段**是报告的活跃期。新生成的报告处于"活跃"状态，出现在报告中心列表顶部，可被检索、收藏、对比、导出。活跃期的时长没有硬性限制，但系统会根据报告的访问频率动态调整其在列表中的排序权重--长期未被访问的报告排序权重逐渐降低，让近期生成和高频访问的报告优先展示。

**检索阶段**贯穿整个生命周期。用户可以通过报告中心的筛选栏做结构化查询，也可以通过对话引用历史报告做语义检索。检索结果始终带有时效标注，提醒用户报告的数据截止日期，避免基于过时数据做决策。

**归档阶段**处理长期闲置的报告。超过 180 天未被访问且未被收藏的报告，系统自动将其标记为"归档"状态。归档报告在列表中默认隐藏，用户勾选"包含归档"后才会显示。归档报告的完整 HTML 内容从热存储迁移到冷存储，列表和详情页只保留摘要和元数据。归档不改变报告的可检索性，用户仍可通过搜索找到并展开归档报告。

**过期清理**是生命周期的终点。超过 365 天的归档报告且未被收藏的，系统执行物理删除，仅保留摘要记录用于历史引用的溯源链接。定时任务报告（晨报、收盘分析等）的保留期更短，默认 90 天后自动清理，因为这些报告的时效性强、历史价值低。用户可以对任意报告设置"永久保留"标记，豁免自动清理。所有过期清理操作记录在审计日志中，管理员可在 ERP 后台查看清理记录。

### 1.3 报告与对话的双向引用机制

报告和对话不是割裂的两个系统，而是通过**双向引用**紧密关联。用户在对话中生成报告，也可以在对话中引用历史报告；报告本身记录了生成它的对话上下文，用户可以从报告回溯到原始对话。

```
┌───────────┐  生成报告时写入 conversation_id    ┌───────────┐
│           │ ─────────────────────────────────> │           │
│   对话     │                                    │   报告     │
│           │ <───────────────────────────────── │           │
└───────────┘  对话引用历史报告时携带 report_id   └───────────┘
       │                                           │
       │  从报告详情页跳转到原始对话                │
       │  （report.conversation_id -> conversation）│
       └───────────────────────────────────────────┘
```

**正向引用**（对话到报告）在报告生成时建立。`analysis_report` 表的 `conversation_id` 字段记录报告归属的对话，用户在报告详情页点击"查看原始对话"即可跳回生成该报告时的对话上下文。这让用户能回看自己当时问了什么、AI 的分析思路是什么，理解报告结论的推导过程。

**反向引用**（报告到对话）在用户对话中提及历史报告时建立。当用户问"上次分析的茅台现在怎么样了"，AI 从报告中心检索历史报告，在回复中嵌入报告预览容器并携带 `reportId`。这条对话消息记录了引用的 `report_id`，形成反向引用链。反向引用让报告不再是静态文档，而是可以被持续追踪和更新的活资产。

双向引用的底层支撑是 `chat_message` 表的 `tool_result_json` 字段。当 AI 调用 `generateReport` 工具生成报告时，工具返回结果中包含 `reportId`，存入 `tool_result_json`。当 AI 调用历史报告检索工具时，返回结果同样包含 `reportId`。这样从对话侧可以查出"这次对话引用了哪些报告"，从报告侧可以通过 `conversation_id` 查出"这份报告在哪些对话中被引用过"。

## 二、报告分类体系

### 2.1 三维分类设计

报告分类体系沿三个正交维度展开：**按类型**、**按股票**、**按行业**。三个维度相互独立，任意一份报告同时属于三个维度中的一个或多个类别。

| 分类维度 | 索引依据 | 典型用途 | 示例 |
|----------|----------|----------|------|
| 按类型 | report_type 字段 | 按分析类型浏览报告 | 个股深度研究、板块分析 |
| 按股票 | ts_code 字段 | 查看某只股票的所有历史报告 | 茅台的全部报告 |
| 按行业 | industry 字段 | 查看某行业的所有历史报告 | 白酒板块的全部报告 |

按类型分类是最核心的维度，直接决定报告的章节模板和数据来源。按股票和按行业分类是辅助维度，用于横向关联同一标的或同一板块的多份报告。选股筛选报告和持仓诊断报告可能关联多只股票，此时 `ts_code` 字段存储主标的或留空，具体股票列表记录在报告内容中。

### 2.2 多维度交叉筛选

单一维度的分类不够用，用户往往需要组合多个条件精确定位报告。例如"茅台 + 深度研究 + 最近一个月"、"白酒行业 + 定时任务报告 + 已收藏"。报告中心的筛选栏支持多维度交叉筛选，所有条件之间是 AND 关系。

```
┌──────────────────────────────────────────────────────────────────┐
│  筛选栏                                                           │
│                                                                  │
│  按类型: [全部] [个股深度] [板块分析] [选股筛选] [持仓诊断]        │
│         [市场综述] [定时任务]                                      │
│                                                                  │
│  按股票: [输入股票代码/名称...] ── 选定: 600519.SH 贵州茅台 [x]   │
│  按行业: [选择行业 v] ── 选定: 食品饮料-白酒 [x]                  │
│  按时间: [全部] [近一周] [近一月] [近三月] [自定义区间]            │
│  仅收藏: [ ]                                                      │
│  关键词: [输入关键词搜索报告标题和摘要...]                        │
│                                                                  │
│  [搜索] [重置]                                        共 23 份报告 │
└──────────────────────────────────────────────────────────────────┘
```

交叉筛选的查询设计如下。前端将所有筛选条件封装为一个 `ReportQueryDTO`，通过 POST 请求提交到后端。后端将条件组装为 MyBatis-Plus 的 `QueryWrapper`，各条件以 AND 拼接。

```json
{
  "reportType": "STOCK_DEEP",
  "tsCode": "600519.SH",
  "industry": "食品饮料-白酒",
  "dateRange": {
    "start": "2026-07-06",
    "end": "2026-08-06"
  },
  "favoritedOnly": true,
  "keyword": "估值",
  "page": 1,
  "size": 12,
  "sortBy": "created_at",
  "sortOrder": "desc"
}
```

关键词搜索同时匹配报告标题和摘要两个字段，使用 MySQL 的 `LIKE` 模糊匹配。后续如接入全文索引（MySQL FULLTEXT 或 Elasticsearch），可将关键词搜索升级为全文检索，支持分词和相关性排序。在当前阶段，`LIKE` 匹配已能满足个人投资者的报告量级需求。

### 2.3 标签系统设计

三维分类是系统预设的结构化维度，覆盖不了用户个性化的组织需求。例如用户可能想把"重点关注"、"已买入"、"待观察"的报告分组管理，或者给报告打上"财报季"、"政策利好"等事件标签。标签系统让用户在系统分类之外建立自己的报告组织体系。

标签分为**系统标签**和**用户自定义标签**两类。系统标签由平台自动生成，基于报告的元数据推断，例如定时任务报告自动打上"晨报"或"周报"标签，财报解读报告自动打上"财报季"标签。用户自定义标签由用户手动添加，完全由用户控制命名和用途。

标签的数据结构采用多对多关系。一份报告可以拥有多个标签，一个标签可以关联多份报告。`report_tag` 表存储标签定义，`report_tag_relation` 表存储报告与标签的关联关系（详见第八章数据模型）。

标签的操作入口分布在三个位置。报告卡片上有"添加标签"按钮，点击弹出标签选择浮层，显示用户已有的标签列表和"新建标签"输入框。报告详情页顶部展示当前报告的所有标签，每个标签可点击移除。筛选栏的"标签"筛选区显示用户所有标签，点击标签筛选出该标签下的全部报告。

### 2.4 报告类型完整定义

六种报告类型各有不同的字段结构、生成条件和内容模板。以下是每种类型的完整定义。

**个股深度研究（STOCK_DEEP）** 是信息密度最高的报告类型，覆盖单只股票的全维度分析。生成条件：用户在对话中请求"全面分析茅台"、"做个茅台的深度研究"，或选择 DCF 估值、可比估值、首次覆盖、财报解读等研究方法时触发。关联字段：`ts_code` 必填，`industry` 自动填充。章节模板包含一句话观点、基本面速览（Tear Sheet）、技术面研判、估值分析（PE/PB 分位 + 同业对比）、竞争格局、财务分析（三表 + 关键指标趋势）、资金面分析、风险提示共八个章节。数据来源涵盖 `daily_quote`、`daily_basic`、`income`、`balancesheet`、`cashflow`、`fina_indicator`、`moneyflow`、`top_list`、`hk_hold` 等多张 Tushare 业务表。

**板块/行业分析（SECTOR）** 聚焦申万行业或自定义板块的整体研判。生成条件：用户问"今天白酒板块怎么样"、"半导体板块有哪些龙头股"，或定时任务的板块周报触发。关联字段：`industry` 必填，`ts_code` 留空（板块成分股列表记录在报告内容中）。章节模板包含板块行情概览、成分股涨跌分布、资金流向分析、龙头股对比、板块估值分位、行业政策与事件、趋势研判共七个章节。数据来源包括 `sw_industry`、`daily_quote`（板块成分）、`moneyflow`、`daily_basic`（板块估值统计）。

**选股筛选报告（SCREENING）** 记录用户的选股条件和筛选结果。生成条件：用户在对话中输入筛选条件（"PE 小于 20 且 ROE 大于 15%"），或使用对话式选股功能。关联字段：`ts_code` 留空，`industry` 留空（筛选条件可能跨行业）。章节模板包含筛选条件描述、结果列表（含代码/名称/关键指标/简评）、结果统计（行业分布/市值分布/估值分布）、筛选逻辑说明共四个章节。数据来源以 `daily_basic` 为主，配合 `stock_basic` 做基础过滤。

**持仓诊断报告（PORTFOLIO）** 针对用户的模拟持仓做综合诊断。生成条件：用户问"帮我看看持仓怎么样"、"做个持仓体检"，或定时任务的持仓复盘触发。关联字段：`ts_code` 留空，`industry` 留空（持仓可能跨多个行业）。章节模板包含持仓概览（总市值/盈亏/收益率）、持仓分布（行业暴露/市值分布/风格分布）、个股诊断（每只持仓的估值和技术面简评）、风险评估（集中度/波动率/最大回撤）、优化建议共五个章节。数据来源包括 `user_portfolio` 表和持仓个股的 `daily_quote`、`daily_basic` 数据。

**市场综述（MARKET）** 覆盖大盘和宏观层面的分析。生成条件：用户问"今天大盘怎么样"、"北向资金今天流入多少"、"最近有什么宏观事件影响股市"。关联字段：`ts_code` 留空，`industry` 留空。章节模板包含大盘行情概览（上证/深证/创业板）、板块轮动分析、资金面分析（北向/融资融券/主力净流入）、宏观事件影响、市场情绪指标共五个章节。数据来源包括主要指数的 `daily_quote`、`moneyflow`、`margin_detail`、`hk_hold`。

**定时任务报告（SCHEDULED）** 是定时任务自动产出的标准化报告，是报告中心中数量最多的一类。生成条件：用户创建的定时任务（晨报/收盘分析/板块周报/持仓复盘/事件跟踪）在 cron 触发时自动生成。关联字段根据任务类型不同而变化：晨报和收盘分析关联 `ts_code`（单只股票）或留空（自选股整体），板块周报关联 `industry`，持仓复盘无关联字段。章节模板因任务类型而异，晨报包含盘前数据概览和 AI 简评两个章节，收盘分析包含收盘行情和异动解读两个章节，板块周报包含板块周行情和龙头股表现两个章节。这类报告的章节简洁、篇幅较短，重点是时效性而非深度。

## 三、报告中心架构

### 3.1 页面整体架构

报告中心是一个独立的 SPA 页面，从顶部导航栏的"报告中心"入口进入。页面采用**筛选栏 + 报告卡片列表 + 详情视图**的三段式架构。

```
│  报告中心                                              [返回对话]      │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌──────────────────────────────────────────────────────────────┐    │
│  │  筛选栏                                                       │    │
│  │  [按类型] [按股票] [按行业] [按时间] [仅收藏] [关键词搜索]     │    │
│  │  [标签筛选]                                                   │    │
│  └──────────────────────────────────────────────────────────────┘    │
│                                                                      │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐        │
│  │  报告卡片       │  │  报告卡片       │  │  报告卡片       │        │
│  │                │  │                │  │                │        │
│  │ 茅台深度分析    │  │ 白酒板块周报    │  │ 低估值选股      │        │
```

### 3.2 报告列表分页/排序/筛选 API

报告列表通过 REST API 获取，支持分页、排序和多条件筛选。

```
POST /api/reports/search
Content-Type: application/json

Request Body: ReportQueryDTO
{
  "reportType": "STOCK_DEEP",      // 可空，不传则查全部类型
  "tsCode": "600519.SH",           // 可空
  "industry": "食品饮料-白酒",      // 可空
  "dateRange": {                    // 可空
    "start": "2026-07-06",
    "end": "2026-08-06"
  },
```

报告内容以 HTML 格式存储在 `analysis_report.content` 字段中，详情页需要安全渲染这些 HTML。由于报告内容由后端模板引擎生成（非用户直接输入），XSS 风险相对可控，但仍需做安全处理。渲染方案采用 **DOMPurify 清洗 + 沙箱 iframe** 双重防护。后端生成的 HTML 先经过 DOMPurify 清洗，移除 `<script>` 标签、`on*` 事件属性、`javascript:` 协议等危险内容，然后注入到 `sandbox` 属性的 iframe 中渲染。沙箱 iframe 阻止报告内的脚本访问父页面的 DOM，保证对话页面的安全。

目录导航基于报告 HTML 中的章节标题锚点。后端在生成报告时，每个章节标题添加 `id` 属性（如 `<h2 id="section-1">一句话观点</h2>`）。前端解析报告 HTML 提取所有章节标题，构建左侧目录列表。点击目录项时，右侧内容区滚动到对应的锚点位置，使用 `scrollIntoView({ behavior: 'smooth' })` 实现平滑滚动。滚动过程中，根据当前可视区域内的章节高亮对应的目录项（scroll spy）。

报告详情页底部固定显示合规声明"以上分析不构成投资建议"。这个声明在报告 HTML 的末尾由后端模板注入，前端不负责追加，确保即使报告被导出为 PDF，声明也始终包含。

## 四、报告生成引擎

### 4.1 触发方式

报告生成有三种触发方式，分别对应不同的使用场景和时效要求。

**对话触发**是最主要的方式。用户在对话中请求深度分析（"全面分析茅台"）时，AI 对话中枢的意图路由识别为"多步骤研究"意图，编排 Graph 工作流执行多节点分析。工作流完成后调用 `generateReport` 工具，将各节点的分析结果拼装为 HTML 报告。对话触发是同步阻塞式的（从用户视角看），但底层是异步的（详见 4.5 节并发控制），用户在对话中看到的是报告预览容器的流式呈现。

**定时任务触发**由 Quartz 调度器按用户设定的 cron 表达式自动执行。晨报在每天 8:00 触发，收盘分析在交易日收盘后触发，板块周报在每周日触发。任务执行时，后端的定时任务引擎调用报告生成接口，生成的报告自动存入报告中心并推送给用户。定时任务报告的生成完全在后台进行，用户通过通知中心得知报告已就绪。

**手动重新生成**是用户在报告详情页主动触发的操作。当用户觉得某份历史报告的数据已经过时，点击"重新生成"按钮，系统以原报告的参数和模板为基础，拉取最新数据重新生成一份新报告。新报告与原报告通过 `report_compare` 表的版本链关联（详见第六章），用户可以对比新旧两份报告的差异。手动重新生成也走异步流程，生成过程中详情页显示进度条。

### 4.3 报告生成流程

报告生成遵循"数据与 AI 分离"原则，流程分为五个阶段：数据采集、确定性计算、AI 解读、HTML 拼装、持久化存储。

```
┌─────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  数据采集    │ --> │ 确定性计算     | --> │  AI 解读     │ --> │  HTML 拼装    │ --> │  持久化存储   │
│              │     │               │     │              │     │              │     │              │
│ 从 MySQL     │     │ 技术指标       │     │ 分章节调用   │     │ 模板引擎     │     │ analysis     │
│ 读取 Tushare │     │ 估值分位       │     │ ChatClient   │     │ 拼装章节     │     │ _report 表   │
│ 业务数据     │     │ 财务比率       │     │ 生成解读     │     │ 注入数据     │     │ + 向量索引   │
│              │     │ 统计汇总       │     │ 文本         │     │ 溯源标注     │     │ + 通知推送   │
└─────────────┘     └──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
```

**数据采集阶段**从 MySQL 读取报告所需的 Tushare 业务数据。采集逻辑根据报告类型和章节模板的 `dataSources` 配置，确定需要查询的数据表和字段。数据采集遵循 point-in-time 原则，只取报告生成日期之前的数据，避免引入未来数据。采集结果存入内存中的 `DataContext` 对象，供后续阶段引用。

**确定性计算阶段**将原始数据加工为分析所需的指标和统计量。技术指标（MA/MACD/KDJ/BOLL）由 Python 计算服务通过 HTTP 接口计算，估值分位（PE/PB 在近 5 年的百分位）由后端用 Pandas 统计，财务比率（毛利率/净利增速/ROE 趋势）由后端从 `fina_indicator` 表直接读取或简单计算。所有数值计算走确定性代码，AI 不参与任何数值计算。

**AI 解读阶段**分章节调用 ChatClient 生成解读文本。每个需要 AI 解读的章节单独构造 prompt，将确定性计算结果作为上下文传入，AI 只负责生成文字解读和观点。分章节调用的好处是可以并行执行（多个章节同时调用模型），缩短总生成时间。AI 解读阶段还会生成报告标题和摘要，用于报告卡片的展示。

**HTML 拼装阶段**使用模板引擎将各章节内容拼装为完整的 HTML 报告。后端维护一套 Thymeleaf 报告模板，每个章节模板对应一种 renderer。模板引擎将数据值注入到 HTML 结构中，图表以 ECharts option JSON 的形式嵌入（前端渲染时初始化 ECharts 实例）。每个数据点在 HTML 中附带溯源标注（详见 4.4 节）。

**持久化存储阶段**将报告写入 `analysis_report` 表，同时将报告摘要写入 Redis Stack 的历史报告向量索引（RAG 知识库的一部分），供后续对话引用检索。存储完成后，如果是定时任务触发的报告，通过通知中心推送消息给用户；如果是对话触发的报告，返回报告预览容器数据给前端。

### 4.4 数据溯源机制

报告中的每个数据点都标注来源接口和采集时间戳，这是"数据与 AI 分离"原则在报告层面的延伸。溯源机制让用户能回查 AI 给出结论时依据的数据，建立对分析结果的信任。

溯源标注在 HTML 拼装阶段注入。每个数据值外层包裹一个 `<span>` 标签，携带 `data-source`、`data-table`、`data-date` 三个自定义属性。

```html
<span class="data-point"
      data-source="Tushare"
      data-table="daily_basic"
      data-date="2026-08-05">
  PE 35.2
</span>
```

前端在渲染报告时，为带有 `data-source` 属性的数据点添加下划虚线样式，鼠标悬停时显示溯源浮层，展示数据来源、数据表名和数据截止日期。报告详情页的"数据溯源"折叠面板汇总展示全报告的数据来源清单，按数据表分组列出所有引用的数据表及其截止日期。

整个报告级别还有一个 `data_snapshot` 字段（JSON 格式），记录生成时使用的完整数据快照。数据快照不是原始数据的全量副本，而是各数据表的查询参数和结果摘要。用户点击"查看数据快照"可以展开快照详情，查看 AI 分析时实际看到的数据内容。这个机制在用户对报告结论存疑时特别有用--可以回溯到具体的数据输入，验证 AI 的解读是否合理。

### 4.5 并发控制与进度通知

深度研究报告涉及多张数据表读取、多次模型调用和 HTML 拼装，整个流程可能耗时 30 秒到 2 分钟。如果同步阻塞等待，用户体验极差。报告生成采用**异步处理 + 进度通知**的设计。

```
用户请求生成报告
       │
       ▼
┌──────────────┐
│  接收请求     │ -> 立即返回 reportId 和初始状态 "QUEUED"
│  分配 taskId  │
└──────┬───────┘
       │
       ▼
┌──────────────┐     ┌──────────────────────────────────────────┐
│  任务队列     │ --> │  报告生成 Worker（异步线程池执行）           │
│  (Redis)     │     │                                          │
└──────────────┘     │  阶段 1: 数据采集      -> 进度 20%         │
                     │  阶段 2: 确定性计算     -> 进度 40%         │
                     │  阶段 3: AI 解读        -> 进度 70%         │
                     │  阶段 4: HTML 拼装      -> 进度 90%         │
                     │  阶段 5: 持久化存储     -> 进度 100%        │
                     │                                          │
                     │  每阶段完成时通过 WebSocket 推送进度更新    │
                     └──────────────────────────────────────────┘
```

对话触发的报告生成，前端通过 SSE 连接接收进度。后端在 SSE 流中推送 `report_progress` 事件，携带当前阶段和进度百分比，前端在报告预览容器中展示进度条和当前阶段描述。报告生成完成后，SSE 推送 `report_complete` 事件，携带报告预览容器的完整数据。

定时任务触发的报告生成没有 SSE 连接（任务是后台执行的），进度通过 WebSocket 推送。用户如果在线，会在通知中心看到"茅台晨报正在生成..."的进度消息；如果离线，报告生成完成后推送任务完成通知。

并发控制方面，单个用户的报告生成任务串行执行（避免同一用户并发生成多份报告导致资源浪费），不同用户的任务并行执行。后端使用 Redis 分布式锁保证同一用户的报告生成任务串行化，锁的 key 为 `report:generate:user:{userId}`，锁的过期时间设为 5 分钟（防止任务异常导致锁不释放）。线程池大小配置为 10，足以支撑初期用户量。

每个阶段设置超时阈值：数据采集 10 秒、确定性计算 15 秒、AI 解读 60 秒（多章节并行时取最长的一个）、HTML 拼装 5 秒、持久化存储 5 秒。任一阶段超时则整个报告生成任务标记为失败，通过 SSE 或 WebSocket 推送错误信息，用户可点击"重试"重新生成。

## 五、报告与对话的关系

### 5.1 四种关系

报告在对话中生成，但生成后独立存在于报告中心。两者之间存在四种关系，覆盖了从生成到引用的完整链路。

**对话中生成报告**。用户在对话中请求深度分析后，AI 编排 Graph 工作流完成多节点分析，最终调用 `generateReport` 工具生成报告。报告存入报告中心的同时，对话流中展示报告预览容器，包含报告摘要、目录和操作按钮。用户不需要离开对话就能看到报告的核心内容，完整报告随时可以在报告中心查看。

**报告中心查看**。报告生成后，用户可以随时在报告中心查看、搜索、收藏、对比、导出历史报告。报告中心与对话是两个独立的入口，用户可以在不打开任何对话的情况下浏览和管理所有报告。

**对话引用历史报告**。用户在对话中提到历史报告时（"上次分析的茅台现在怎么样了"），AI 从报告中心检索匹配的历史报告，对比当前数据生成跟踪分析。这让历史报告不只是静态存档，而是可以被持续追踪和更新的活资产。

**报告内可追溯**。每份报告标注生成时的数据快照和来源信息，用户可以从报告回查"AI 给出这个结论时用了什么数据"。同时报告记录了生成它的 `conversation_id`，用户可以从报告跳回原始对话，回看当时的分析上下文。

### 5.2 对话中报告预览容器的数据流

对话中生成报告时，报告预览容器的数据流如下，从 AI 触发生成到前端展示预览。

```
AI 调用 generateReport 工具
       │
       ▼
┌──────────────────────┐
│  报告生成引擎          │
│  (异步执行，见第四章)  │
│  -> 生成 HTML 报告    │
│  -> 写入 analysis_    │
│     report 表         │
│  -> 写入向量索引       │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  构造预览容器数据       │
│  reportId: 1024       │
│  title: 茅台深度分析   │
│  summary: 摘要文本     │
│  toc: [章节目录]       │
│  keyMetrics: 关键指标 │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  SSE 推送 report_     │
│  complete 事件        │
│  携带预览容器数据      │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  前端渲染报告预览容器   │
│  (report_preview     │
│   容器组件)           │
│  摘要 + 目录 + 按钮    │
└──────────────────────┘
```

预览容器返回的数据结构在 SSE 的 `container_data` 事件中携带，与报告中心的 `ReportCardVO` 共享核心字段。关键区别在于预览容器额外携带 `toc`（章节目录）和 `keyMetrics`（关键指标速览），让用户在对话中就能看到报告的核心信息，而不必跳转到报告中心。

预览容器的 `reportId` 是连接对话和报告中心的桥梁。用户点击"查看完整报告"时，前端携带 `reportId` 跳转到报告中心详情页，直接加载该报告的完整 HTML 内容。这个跳转是对话场景下唯一推荐的页面跳转，因为深度报告的信息密度太高，在对话流内完整渲染会破坏对话的节奏感。

### 5.3 对话引用历史报告的检索逻辑

当用户在对话中提及历史报告时，AI 需要从报告中心检索匹配的报告。检索逻辑分为两步：实体识别和报告匹配。

**实体识别**由 AI 对话中枢的意图路由层完成。当用户说"上次分析的茅台现在怎么样了"，意图路由识别出两个关键信息：股票实体"茅台"（解析为 `600519.SH`）和"上次"（时间限定，取最近一份）。意图路由将这两个信息传递给历史报告检索工具 `searchHistoryReports`。

**报告匹配**通过后端接口查询 `analysis_report` 表。查询条件包括用户 ID、股票代码、报告类型（优先个股深度研究）、排序（按生成时间倒序）、数量限制（取最近 1-3 份）。查询结果返回报告的摘要和关键指标，AI 拿到这些信息后与当前数据对比，生成跟踪分析。

```
用户: "上次分析的茅台现在怎么样了"
  │
  ▼
意图路由:
  - 实体: 贵州茅台 600519.SH
  - 时间意图: 最近一份历史报告
  - 意图类型: 历史报告引用
  │
  ▼
调用 searchHistoryReports 工具:
  GET /api/reports/search
  {
    "tsCode": "600519.SH",
    "reportType": "STOCK_DEEP",
    "sortBy": "created_at",
    "sortOrder": "desc",
    "size": 1
  }
  │
  ▼
返回历史报告:
  - reportId: 1024
  - title: 茅台深度分析报告
  - generatedAt: 2026-07-05
  - summary: 当时 PE 78%分位，估值偏高...
  - keyMetrics: { pe: 35.2, roe: 31.2 }
  │
  ▼
AI 拉取当前数据对比:
  - 当时 PE 35.2 (78%分位) -> 现在 PE 32.1 (65%分位)
  - 估值分位下降 13 个百分点
  │
  ▼
AI 回复:
  "上次（7月5日）分析茅台时，PE 为 35.2，处于近5年 78% 分位，
   估值偏高。目前 PE 已降至 32.1，分位下降到 65%，估值有所回归。
   [报告预览容器: 茅台深度分析报告 2026-07-05]"
```

当用户的查询不包含明确的股票实体时（"上周的白酒板块报告呢"），检索逻辑使用行业维度匹配。当用户只说"上次的分析报告"而不指定任何实体时，检索逻辑取用户最近生成的一份报告。这些模糊查询依赖 AI 的上下文理解能力，将自然语言转化为结构化查询条件。

检索结果在对话中以报告预览容器的形式展示，携带历史报告的 `reportId`。用户可以点击预览容器查看历史报告原文，也可以继续追问"和上次比有什么变化"，触发报告对比功能。

## 六、报告对比功能

### 6.1 对比功能设计

报告对比支持两份同类报告的横向对比，让用户观察同一标的在不同时点的变化轨迹。典型场景是用户选中两份不同时间的茅台深度分析报告，对比关键指标的变化和 AI 观点的演变。

```
┌──────────────────────────────────────────────────────────────────────┐
│  报告对比                                                              │
├───────────────────────────┬──────────────────────────────────────────┤
│  报告 A (2026-07-05)      │  报告 B (2026-08-05)                      │
│  茅台深度分析报告          │  茅台深度分析报告                          │
├───────────────────────────┼──────────────────────────────────────────┤
│  关键指标对比              │                                          │
│  ┌────────────┬──────────┬──────────┬──────────┐                   │
│  │ 指标        │ 报告 A   │ 报告 B   │ 变化     │                   │
│  ├────────────┼──────────┼──────────┼──────────┤                   │
│  │ PE         │ 35.2     │ 32.1     │ -3.1     │                   │
│  │ PE 分位     │ 78%      │ 65%      │ -13pp    │                   │
│  │ PB         │ 11.8     │ 10.9     │ -0.9     │                   │
│  │ ROE        │ 31.2%    │ 31.0%    │ -0.2pp   │                   │
│  └────────────┴──────────┴──────────┴──────────┘                   │
│                                                                      │
│  AI 观点变化                                                          │
│  报告 A: "估值偏高，但基本面稳健，ROE 持续维持在 30% 以上..."         │
│  报告 B: "估值有所回归，PE 分位从 78% 降至 65%，基本面维持稳定..."    │
│  变化摘要: 估值从偏高回归至合理偏高水平，基本面无明显变化              │
│                                                                      │
│  [指标变化趋势图]                                                     │
│  [导出对比结果]                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

对比入口在报告卡片的"对比"按钮和报告详情页的"对比"按钮。用户点击"对比"后，当前报告加入对比篮（最多两份）。对比篮在页面右下角显示为悬浮卡片，展示已选报告的标题和"开始对比"按钮。用户选择第二份报告后点击"开始对比"，进入对比详情视图。

### 6.2 对比算法设计

对比的核心是**关键指标差异计算**和**AI 观点变化对比**，两者分别处理定量和定性维度。

关键指标差异计算从两份报告的 `data_snapshot` 字段中提取指标值，逐项计算差值和变化率。对比的指标集取决于报告类型：个股深度研究对比 PE、PB、ROE、营收增速、净利润增速、股息率、PE 分位、PB 分位等；板块分析对比板块涨跌幅、资金净流入、板块平均 PE 等；持仓诊断对比总市值、总收益率、行业分布变化等。差值用正负号和颜色标识（红色表示上升、绿色表示下降，遵循 A 股惯例），变化率用百分比表示。

AI 观点变化对比从两份报告的 `summary` 字段和各章节的 AI 解读文本中提取。对比算法不是简单的文本 diff，而是调用 ChatClient 做语义级别的观点对比。后端构造一个对比 prompt，将两份报告的摘要和关键章节文本传入，AI 生成一段"观点变化摘要"，指出两份报告在结论上的主要差异（如估值判断从"偏高"变为"合理偏高"、技术面从"看多"变为"中性"）。这个变化摘要在对比视图的"AI 观点变化"区域展示。

可视化差异展示包括两部分。关键指标的变化以表格形式呈现，每个指标一行，列出报告 A 值、报告 B 值和变化量。对于有时间序列的指标（如 PE 分位），额外绘制一条变化趋势折线图，横轴为两份报告的生成日期，纵轴为指标值，用 ECharts 渲染。

### 6.3 对比的限制条件

对比功能有三个硬性限制，保证对比结果的有效性。

**只有同类报告才能对比**。不同类型的报告章节结构不同、指标体系不同，对比没有意义。用户选择第一份报告后，对比篮会记录其 `report_type`，第二份报告必须同为该类型才能加入对比篮。如果用户尝试加入不同类型的报告，前端提示"只能对比同类型的报告"。

**最多两份对比**。对比是两两关系，三份或更多报告的横向对比在信息呈现上过于复杂，个人投资者用不上。对比篮限制为两份，已满两份时用户需要先移除一份才能添加新的。

**对比的两份报告应关联同一标的**。系统不强制限制（因为选股筛选报告可能跨标的），但对同标的的报告对比才有实际意义。如果两份报告的 `ts_code` 或 `industry` 不一致，前端在对比视图顶部提示"两份报告关联标的不同，对比结果仅供参考"。

每次对比操作记录在 `report_compare` 表中，存储两份报告的 ID、对比时间、对比结果摘要。这些记录构成报告的版本链，用户可以在报告详情页查看"该报告的历史对比记录"，追溯同一标的的分析演变轨迹。

## 七、报告导出与分享

### 7.1 PDF 导出技术方案

报告以 HTML 格式存储，导出为 PDF 需要将 HTML 转换为可下载的 PDF 文件。转换方案采用后端无头浏览器渲染，保证 PDF 的排版与在线浏览一致。

后端使用 Playwright（或 Puppeteer）驱动 Chromium 无头浏览器，加载报告 HTML 内容，等待 ECharts 图表渲染完成后触发 PDF 打印。整体流程如下：后端接收到导出请求后，将报告 HTML 包装在一个完整的 HTML 文档中（包含 ECharts 库引用和图表初始化脚本），写入临时文件。启动无头浏览器加载该文件，注入一段等待脚本确保所有 ECharts 实例完成 `setOption` 和动画。等待完成后调用浏览器的 PDF 打印接口，生成 PDF 字节流，通过 HTTP 响应返回给前端下载。

PDF 导出有几个细节需要注意。ECharts 图表在 PDF 中以 Canvas 形式存在，无头浏览器需要启用 Canvas 渲染。报告中的数据溯源标注在 PDF 中保留为下划虚线，但鼠标悬停浮层不可用，因此溯源信息以脚注形式追加在每页底部。报告底部的合规声明"不构成投资建议"在 PDF 的最后一页固定显示。PDF 文件名格式为 `{报告标题}_{生成日期}.pdf`。

导出操作是同步阻塞的（从用户点击到文件下载），但后端处理时间通常在 5-10 秒内（无头浏览器启动 + 图表渲染 + PDF 生成）。前端在导出按钮上显示 loading 状态，导出完成后触发浏览器下载。对于内容特别长的报告（超过 50 页），导出可能超时，后端将超时阈值设为 30 秒，超时后返回错误提示用户稍后重试。

### 7.2 报告分享机制

报告分享有两种方式：**分享链接**和**长图截图分享**，分别适合不同场景。

分享链接方式生成一个带 token 的公开 URL，非登录用户也可以通过该链接查看报告内容。后端在用户点击"分享"时生成一个分享 token（UUID），写入 `report_share` 记录（包含 report_id、token、过期时间、访问密码），返回分享 URL 如 `https://domain/share/{token}`。访问者打开链接后，后端校验 token 有效性和过期时间，通过则返回报告 HTML 内容。分享链接默认有效期为 7 天，用户可在分享时自定义有效期（1 天 / 7 天 / 30 天 / 永久）。可选设置访问密码，访问者需要输入密码才能查看。

长图截图分享方式将报告内容渲染为一张纵向长图，用户可保存到本地或分享到社交平台。后端使用无头浏览器对报告 HTML 做整页截图，生成 PNG 格式的长图。长图分享不需要 token，图片本身包含全部内容，但不含交互能力（图表为静态截图、目录不可点击）。长图底部自动追加平台水印和合规声明。

两种方式的选择由用户决定。分享链接适合发给特定的人查看，对方可以交互式浏览报告、放大图表。长图分享适合快速传播到微信群或社交平台，接收者不需要打开链接就能看到内容。

### 7.3 报告权限设计

报告权限分为**私有报告**和**公开报告**两类，默认所有报告为私有。

私有报告只有报告所有者可以查看、编辑和删除。`analysis_report` 表的 `user_id` 字段标识报告所有者，后端在所有报告查询接口中自动注入 `user_id` 过滤条件，确保用户只能看到自己的报告。报告中心的列表、详情、对比、导出等操作都经过权限校验，通过分享链接生成的公开访问走独立的只读接口，不经过用户权限校验。

公开报告是平台运营 curated 的精选报告，所有用户可见。这部分报告由平台运营人员从高质量的用户报告中筛选（征得用户同意后）标记为公开，或由平台自行生成。公开报告在报告中心有独立的"精选报告"入口，不影响用户私有报告的列表。公开报告的 `user_id` 设为系统账号，`is_public` 字段标记为公开。

权限校验在 Controller 层和 Service 层双重保障。Controller 层通过 session 获取当前用户 ID，注入到查询参数中。Service 层在查询 `analysis_report` 时强制追加 `user_id` 条件（除非查询的是公开报告）。删除和修改操作的权限校验更严格：除了校验 `user_id` 匹配外，还校验报告是否被定时任务引用（被引用的报告不能直接删除，需要先解除关联）。

## 八、数据模型设计

### 8.1 analysis_report 表

`analysis_report` 是报告中心的核心表，存储报告的完整内容和元数据。在原报告设计的基础上补充归档状态、公开标记和数据快照版本字段。

```sql
CREATE TABLE analysis_report (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    conversation_id BIGINT,                        -- 生成报告的对话 ID（正向引用）
    report_type     VARCHAR(32) NOT NULL,          -- STOCK_DEEP/SECTOR/SCREENING/PORTFOLIO/MARKET/SCHEDULED
    ts_code         VARCHAR(16),                   -- 关联股票（如适用）
    industry        VARCHAR(64),                   -- 关联行业（如适用）
    title           VARCHAR(255) NOT NULL,
    summary         TEXT NOT NULL,                 -- 报告摘要（卡片展示用）
    content         LONGTEXT NOT NULL,             -- 完整报告内容（HTML）
    data_snapshot   LONGTEXT,                      -- 生成时的数据快照 JSON
    snapshot_version INT DEFAULT 1,                -- 数据快照版本号
    key_metrics     TEXT,                          -- 关键指标 JSON（对比和预览用）
    is_favorited    TINYINT DEFAULT 0,             -- 是否收藏
    is_public       TINYINT DEFAULT 0,             -- 是否公开报告
    status          VARCHAR(16) DEFAULT 'ACTIVE',  -- ACTIVE/ARCHIVED
    source          VARCHAR(16) DEFAULT 'CHAT',    -- CHAT/SCHEDULED/MANUAL
    task_id         BIGINT,                        -- 定时任务 ID（定时任务报告关联）
    created_at      VARCHAR(32) NOT NULL,
    archived_at     VARCHAR(32),                    -- 归档时间
    INDEX idx_report_user (user_id),
    INDEX idx_report_type (report_type),
    INDEX idx_report_code (ts_code),
    INDEX idx_report_industry (industry),
    INDEX idx_report_fav (user_id, is_favorited),
    INDEX idx_report_status (user_id, status),
    INDEX idx_report_created (user_id, created_at),
    INDEX idx_report_task (task_id)
);
```

`key_metrics` 字段存储报告的关键指标 JSON，供报告卡片和对比功能快速取用，避免每次都解析完整 HTML 内容。`source` 字段标识报告的触发来源，`task_id` 关联定时任务表，用于定时任务报告的溯源。

### 8.2 report_tag 表

标签系统使用两张表：`report_tag` 存储标签定义，`report_tag_relation` 存储报告与标签的多对多关系。

```sql
-- 标签定义
CREATE TABLE report_tag (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id     BIGINT NOT NULL,               -- 标签所有者（用户自定义标签归属用户）
    tag_name    VARCHAR(64) NOT NULL,          -- 标签名称
    tag_color   VARCHAR(16) DEFAULT '#5470c6', -- 标签颜色
    system_tag  TINYINT DEFAULT 0,             -- 是否系统标签（系统自动生成）
    created_at  VARCHAR(32) NOT NULL,
    UNIQUE KEY uk_user_tag (user_id, tag_name),  -- 同一用户下标签名唯一
    INDEX idx_tag_user (user_id)
);

-- 报告与标签关联
CREATE TABLE report_tag_relation (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    report_id   BIGINT NOT NULL,
    tag_id      BIGINT NOT NULL,
    created_at  VARCHAR(32) NOT NULL,
    UNIQUE KEY uk_report_tag (report_id, tag_id),  -- 防止重复打标签
    INDEX idx_rtr_report (report_id),
    INDEX idx_rtr_tag (tag_id)
);
```

用户自定义标签归属用户，不同用户可以有同名标签。系统标签的 `user_id` 设为 0，所有用户共享。标签的增删改由用户在报告中心操作，删除标签时同步清理 `report_tag_relation` 中的关联记录。

### 8.3 report_compare 表

`report_compare` 记录用户的对比历史，构成报告的版本链，用于追踪同一标的的分析演变。

```sql
CREATE TABLE report_compare (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    report_id_a     BIGINT NOT NULL,             -- 较早的报告
    report_id_b     BIGINT NOT NULL,             -- 较晚的报告
    report_type     VARCHAR(32) NOT NULL,        -- 对比报告类型（冗余，便于查询）
    ts_code         VARCHAR(16),                 -- 对比标的（如有）
    industry        VARCHAR(64),                 -- 对比行业（如有）
    diff_summary    TEXT,                        -- AI 生成的观点变化摘要
    diff_metrics    TEXT,                        -- 关键指标差异 JSON
    created_at      VARCHAR(32) NOT NULL,
    INDEX idx_compare_user (user_id),
    INDEX idx_compare_report_a (report_id_a),
    INDEX idx_compare_report_b (report_id_b),
    INDEX idx_compare_code (ts_code)
);
```

`diff_metrics` 存储指标差异的计算结果 JSON，避免每次查看对比时重新计算。`diff_summary` 存储 AI 生成的观点变化摘要。通过 `report_id_a` 和 `report_id_b` 的索引，可以从任意一份报告出发查询其参与过的对比历史。

### 8.4 report_share 表

`report_share` 记录分享链接信息，支持报告的对外分享。

```sql
CREATE TABLE report_share (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    report_id       BIGINT NOT NULL,
    user_id         BIGINT NOT NULL,             -- 分享发起者
    share_token     VARCHAR(64) NOT NULL,        -- 分享 token（UUID）
    password        VARCHAR(64),                 -- 访问密码（可空）
    expire_at       VARCHAR(32),                 -- 过期时间（null 表示永久）
    view_count      INT DEFAULT 0,               -- 访问次数
    created_at      VARCHAR(32) NOT NULL,
    UNIQUE KEY uk_share_token (share_token),
    INDEX idx_share_report (report_id),
    INDEX idx_share_user (user_id)
);
```

### 8.5 索引设计说明

报告中心的查询场景集中在多维筛选和排序，索引设计围绕这些场景展开。

`idx_report_user` 是最基础的索引，支撑"查看某用户的所有报告"这一最高频查询。`idx_report_fav` 是复合索引，支撑"查看某用户已收藏的报告"这一筛选条件。`idx_report_created` 是复合索引，支撑按时间排序分页查询，因为 `created_at DESC` 是默认排序方式，复合索引覆盖"用户 + 时间排序"的查询路径。

`idx_report_type` 和 `idx_report_code`、`idx_report_industry` 分别支撑按类型、按股票、按行业的筛选。当多个筛选条件同时使用时（如"茅台 + 深度研究 + 近一月"），MySQL 优化器会选择区分度最高的索引，其余条件走回表过滤。在当前报告量级（单用户几百到几千份报告）下，这个查询性能是足够的。

`idx_report_status` 复合索引支撑"活跃报告列表"查询，过滤掉归档报告。`idx_report_task` 支撑定时任务查询其产出的报告列表。

对比表的 `idx_compare_code` 索引支撑"查看某只股票的对比历史"查询，用于在报告详情页展示该标的的历史对比记录链。标签关联表的 `uk_report_tag` 唯一索引防止同一份报告重复打同一标签，同时作为报告标签查询的覆盖索引。
