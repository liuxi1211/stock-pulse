## 一、风险矩阵

### 1.1 风险评估方法

平台面临 7 项核心风险，涵盖 AI 可靠性、成本控制、数据采集、系统性能和数据安全等维度。每项风险按**发生概率**和**影响程度**两个维度评估，概率分为高/中/低三档，影响程度同理。风险等级由概率与影响的乘积决定，分为高/中/低三档，等级越高越需要优先投入资源预防和应对。

概率和影响的判定依据如下：概率"高"指在平台正常运营中大概率会发生的事件，"中"指特定条件下可能发生，"低"指较少触发但后果需防备。影响"高"指直接导致用户错误决策或系统不可用，"中"指影响用户体验或增加成本，"低"指影响有限且可快速恢复。

### 1.2 风险矩阵

| 编号 | 风险 | 影响 | 发生概率 | 影响程度 | 风险等级 | 预防措施 | 应急预案 |
|------|------|------|----------|----------|----------|----------|----------|
| R1 | AI 幻觉（编造数据） | 用户基于错误数据决策 | 中 | 高 | **高** | 数值计算走确定性代码；报告节点数据校验；每点溯源标注；Prompt 层约束禁止输出未经验证的数值 | 合规过滤 Advisor 拦截敏感输出；审计日志回溯定位；用户反馈入口标注疑似错误 |
| R2 | 模型调用成本失控 | 费用超预期 | 中 | 中 | **中** | 轻量查询用 qwen-turbo，深度分析用 qwen-plus；每日调用上限；缓存查询结果 | 降级到更低成本模型；临时降低调用频率上限；触发成本告警并人工介入 |
| R3 | Tushare 接口限流 | 数据更新失败 | 中 | 中 | **中** | RateLimiter 阻塞限流；遵循 5 条铁律；data_pull_log 记录失败详情 | 自动重试机制；错峰采集避开高峰；降级使用缓存数据并标注数据延迟 |
| R4 | Graph 工作流超时 | 深度报告卡住 | 中 | 中 | **中** | 节点级超时设置；长任务异步执行+推送通知 | Human-in-the-loop 跳过可选节点；返回部分结果并标注未完成项；通知用户稍后查看 |
| R5 | 对话上下文丢失 | 多轮对话断裂 | 低 | 中 | **低** | ChatMemory 持久化 MySQL；超窗口旧消息摘要存入 long-term memory | 会话恢复机制从 MySQL 重建上下文；提示用户重新描述关键信息 |
| R6 | C 端并发压力 | 响应变慢 | 低 | 中 | **低** | JDK 21 虚拟线程承载高并发 SSE；Redis 缓存热点数据；Caffeine 本地缓存 | 限流降级保护核心功能；扩容 C 端实例；后期拆分微服务分散压力 |
| R7 | 数据权限冲突 | ERP 写入与 C 端读取冲突 | 低 | 高 | **中** | 读写分离：ERP 独占写入，C 端只读查询；MySQL InnoDB 事务隔离；ERP 批量写入控制粒度 | 紧急切换 C 端只读模式；排查冲突源；数据一致性校验与修复 |

### 1.3 风险应对优先级

7 项风险中，R1（AI 幻觉）是唯一的高等级风险，也是平台的**信任红线**。AI 编造数据会导致用户基于错误信息做出投资决策，这种伤害不可逆。因此 R1 的预防措施必须在 Phase 1 上线前全部落地，包括确定性代码兜底、报告节点数据校验和数据溯源标注，任一项未完成不允许面向用户开放。

R2-R4、R7 为中等级风险，需在对应 Phase 内落实预防措施。R3（Tushare 限流）在 Phase 0 数据底座阶段就需部署 RateLimiter；R4（Graph 超时）在 Phase 2 报告引擎开发时同步实现节点级超时；R7（数据权限冲突）在 Phase 0 双项目架构搭建时通过读写分离设计规避。

R5-R6 为低等级风险，预防措施已嵌入架构设计（ChatMemory 持久化、虚拟线程），日常无需额外投入，但需在监控体系中持续观察指标趋势，一旦概率上升及时升级应对等级。

原报告列出 8 条关键决策。每条决策都是在多个备选方案中做出的选择，理解选择理由有助于后续演进时判断是否需要重新决策。

## 三、测试策略

### 3.1 测试分层设计

平台采用测试金字塔模型，从底层到顶层分为单元测试、集成测试和端到端测试三层。每层关注不同的质量维度，下层测试数量多、执行快，上层测试数量少、覆盖广。

| 层级 | 覆盖范围 | 占比目标 | 执行频率 | 工具 |
|------|----------|----------|----------|------|
| 单元测试 | Service 层逻辑、计算公式、工具函数 | 70% | 每次提交 | JUnit 5 + Mockito（Java）/ pytest（Python） |
| 集成测试 | API 接口、数据库交互、跨模块调用 | 20% | 每日构建 | Spring Boot Test / Testcontainers |
| 端到端测试 | 对话流程、盯盘触发、报告生成全链路 | 10% | 每个 Phase 验收 | 手动 + 自动化脚本 |

**单元测试**聚焦于业务逻辑的正确性验证。Java 侧重点覆盖 Service 层的数据查询逻辑、意图路由判断、Function Calling 工具的参数解析和返回组装。Python 侧重点覆盖技术指标计算（MA/MACD/KDJ）、因子计算和统计公式的数值正确性，这部分涉及金融计算，对精度要求高，需用已知输入输出对验证。单元测试不依赖外部服务，全部使用 Mock 隔离数据库和网络。

**集成测试**验证模块间的协作正确性。重点覆盖三类场景：API 接口的请求响应契约（参数校验、返回格式、错误码）、数据库交互（MyBatis-Plus 的 CRUD、事务回滚、分页查询）、跨模块调用（C 端调用计算服务的 HTTP 链路、ERP 写入后 C 端读取的数据一致性）。集成测试使用 Testcontainers 启动临时 MySQL 和 Redis 实例，保证测试环境与生产一致且互不污染。

**端到端测试**验证完整业务链路的可用性。重点覆盖对话流程（用户输入 -> 意图路由 -> 工具调用 -> 富媒体回复 -> 多轮上下文）、盯盘触发（规则创建 -> Quartz 调度 -> 条件命中 -> AI 分析 -> WebSocket 推送）和报告生成（深度分析请求 -> Graph 编排 -> 节点串联 -> 报告存库 -> 报告中心展示）。端到端测试在 Phase 验收时执行，部分场景可编写自动化脚本重复运行。

### 3.2 AI 对话测试策略

AI 对话的输出具有非确定性，传统断言式测试难以直接适用。平台采用**Golden Case 回归**和**Prompt 版本管理**两套机制保障 AI 输出质量。

**Golden Case 回归**的核心思路是建立一批标准问答用例，每个用例包含固定输入和期望的输出特征（而非精确文本）。例如用例"茅台今天的 PE 是多少"，期望输出特征为：包含股票卡片组件、包含 PE 数值、包含分位描述、不含买卖建议。每次 Prompt 调整或模型升级后，运行全部 Golden Case，检查输出是否仍满足期望特征。用例集随功能迭代持续扩充，每个 Phase 至少新增 10 个核心用例。

Golden Case 的判定不是全通过或全失败，而是按维度评分。每个用例拆分为多个检查点（如"是否包含卡片""数值是否正确""是否有合规风险提示"），单个检查点失败时精确定位问题，而非笼统判定用例失败。对于数值正确性检查点（如 PE 值是否与数据库一致），采用精确断言；对于文本表达检查点，采用关键词匹配或正则匹配。

**Prompt 版本管理**要求所有 AI 提示词纳入版本控制，每次变更记录变更原因、变更内容和预期效果。Prompt 变更后必须运行 Golden Case 回归，对比变更前后的输出质量。如果回归结果下降，变更不予合并。Prompt 版本与代码版本绑定，便于回溯某个时期的 AI 输出对应的 Prompt 版本。

### 3.3 数据质量测试

Tushare 数据是平台分析的基础，数据质量直接影响分析结论可信度。数据质量测试在 ERP 系统的数据治理层实现，分完整性校验和一致性校验两类。

**完整性校验**验证每张表的数据是否齐全。核心检查项包括：股票基础表是否覆盖全 A 股（沪深两市主板、创业板、科创板、北交所）、日线行情表是否每个交易日都有数据、财务报表是否按季更新。校验方式是统计每张表的记录数，与 Tushare 接口返回的总数比对，差异超过阈值时告警。

**一致性校验**验证关联表之间的数据逻辑。核心检查项包括：日线行情的股票代码是否都在基础表中存在、财务指标的报告期与财报披露日期是否匹配、复权因子是否与行情数据对齐。校验方式是跨表 JOIN 查询，找出孤立记录或矛盾记录。

数据质量测试在 ERP 的 DataCheckable 接口中实现，每张表对应一个校验器，在每次采集完成后自动执行。校验结果写入 data_pull_log，异常时在 ERP 管理页面标红提示。以下是关键表的质量校验维度。

| 数据表 | 完整性校验 | 一致性校验 | 异常处理 |
|--------|-----------|-----------|----------|
| stock_basic | 记录数 > 5000（全 A 股） | 交易所代码合法、上市状态字段非空 | 缺失记录触发全量重建 |
| daily_quote | 每个交易日记录数与上市股票数匹配 | ts_code 在 stock_basic 中存在 | 缺失交易日触发增量补拉 |
| daily_basic | PE/PB 字段非空率 > 95% | ts_code + trade_date 与 daily_quote 对齐 | 空值超过阈值标记数据异常 |
| income / balancesheet / cashflow | 报告期按季覆盖 | 三表报告期一致、ts_code 存在 | 缺失季度触发补拉 |

### 4.6 验证报告产出要求

每个 Phase 验证完成后需产出**验证报告**，记录每项验证步骤的执行结果。验证报告包含以下内容：验证步骤编号与名称、执行人、执行时间、执行方式（手动/自动化）、实际结果、通过/失败判定、失败原因与修复记录。验证报告存入项目文档目录，作为 Phase 验收的存档依据。

验证报告的核心价值在于**可追溯**。当线上出现问题时，可回溯对应 Phase 的验证报告，确认该功能在验收时是否通过、当时的测试环境与线上差异在哪里。如果某项验证在验收时就是手动执行的，需在报告中记录手动操作的详细步骤和截图，便于后续复现。

## 五、监控与告警

### 5.1 系统监控指标

平台运行时需持续监控四类核心指标，覆盖服务性能、AI 调用、数据采集和资源消耗。指标采集通过 Spring Boot Actuator 暴露的 metrics 端点实现，配合 Prometheus 采集和 Grafana 展示。

| 指标类别 | 监控指标 | 采集方式 | 正常范围 | 说明 |
|----------|----------|----------|----------|------|
| API 性能 | 接口响应时间（P95） | Actuator + Prometheus | < 2 秒（普通接口）/ < 30 秒（SSE 对话） | 超过阈值说明性能下降 |
| API 性能 | 接口错误率（5xx） | Actuator + Prometheus | < 1% | 超过阈值说明服务异常 |
| AI 调用 | 模型调用成功率 | 自定义 metrics | > 95% | 低于阈值检查模型服务状态 |
| AI 调用 | 模型调用延迟（P95） | 自定义 metrics | < 10 秒 | 超过阈值影响对话体验 |
| AI 调用 | 每日模型调用次数 / 成本 | 自定义 metrics + DashScope 用量 API | 低于每日上限 | 超过上限触发成本告警 |
| 数据采集 | Tushare 采集成功率 | data_pull_log 统计 | > 98% | 低于阈值检查限流和网络 |
| 数据采集 | 数据新鲜度（最新交易日数据是否到位） | 定时检查 daily_quote 最新记录 | 当日 16:30 前到位 | 延迟超过 1 小时告警 |
| 资源消耗 | JVM 堆内存使用率 | Actuator | < 80% | 超过阈值检查内存泄漏 |
| 资源消耗 | CPU 使用率 | 系统监控 | < 70% | 持续偏高需扩容 |
| 资源消耗 | MySQL 慢查询数 | 慢查询日志 | < 10 条/小时 | 超过阈值检查索引和查询优化 |

### 5.2 告警阈值与通知方式

监控指标超过阈值时触发告警，告警按严重程度分级，不同级别采用不同的通知方式和响应时效。

| 告警级别 | 触发条件 | 通知方式 | 响应时效 | 示例 |
|----------|----------|----------|----------|------|
| P0 紧急 | 服务不可用 / 数据全部采集失败 / 模型调用全部失败 | 短信 + 电话 + 即时通讯 | 15 分钟内响应 | C 端应用宕机、MySQL 不可连接 |
| P1 严重 | 错误率 > 5% / 采集成功率 < 80% / 成本超日上限 | 即时通讯 + 邮件 | 1 小时内响应 | 接口错误率飙升、Tushare 持续限流 |
| P2 警告 | 响应时间超阈值 / 采集成功率 < 95% / 内存 > 80% | 即时通讯 | 当天内处理 | 响应变慢、个别接口采集失败 |
| P3 提示 | 慢查询增多 / 磁盘使用率 > 70% | 邮件 | 次日处理 | 磁盘空间预警 |

告警通知通过统一告警通道发送，初期可接入企业微信或钉钉机器人推送消息。P0 级别告警需额外配置短信和电话通知，确保责任人能及时收到。告警消息需包含：告警级别、触发指标、当前值、阈值、发生时间、建议处理方式，便于接收人快速判断和响应。

### 5.3 日志收集与分析

平台采用分层的日志收集方案，业务日志和系统日志分别管理，统一汇聚到可查询的日志平台。

**日志分类与内容**：业务日志记录用户操作和 AI 调用链路，包括用户对话输入输出、Function Calling 工具调用记录、Graph 节点执行日志、盯盘规则触发记录。系统日志记录技术层面的运行状态，包括 HTTP 请求响应、数据库慢查询、异常堆栈、定时任务执行日志。AI 审计日志单独存储在 ai_analysis_audit 表，记录每次模型调用的完整输入输出、Token 消耗和延迟，用于成本分析和问题回溯。

**日志收集与存储**：Java 应用通过 Logback 输出结构化 JSON 日志，写入本地日志文件并按天滚动。Python 计算服务通过 logging 模块输出同级日志。初期采用本地文件 + 日志检索工具（如 loki 或 ELK 的轻量版）的方案，避免引入完整的 ELK 栈增加运维成本。日志保留 30 天，ai_analysis_audit 表的数据保留 90 天用于审计回溯。

**日志分析场景**：日常分析关注错误日志趋势和慢请求分布。当用户反馈"AI 回复不对"时，通过 conversation_id 在审计日志中检索完整的对话链路，定位是意图路由错误、工具返回错误还是模型生成问题。当成本异常时，通过审计日志统计各类型调用的 Token 消耗分布，找出高消耗的调用模式。

## 六、质量保障流程

### 6.1 Code Review 流程

所有代码合并到主分支前必须经过至少一人审查。Code Review 不是走形式，而是质量保障的第一道关卡，重点关注量化计算正确性、数据安全和架构约束遵守。

**审查流程**分为四步：提交者发起 PR 并关联 Issue，说明改动内容和自测结果；审查者按检查清单逐项审查，给出反馈分级（阻断 / 重要 / 建议 / 提问）；提交者根据反馈修改，阻断级问题必须修复后才能合并；合并后由提交者触发部署。审查者与提交者不应是同一人，核心模块（因子计算、数据采集、AI 对话）的 PR 需指定领域负责人审查。

**审查重点**按模块差异化设置。量化计算模块重点检查：计算公式是否与业务定义一致、是否有未来函数、边界值处理是否正确（空数据、停牌、涨跌停）。数据采集模块重点检查：是否遵循 5 条铁律（分批 500 行、禁止跨 API 大事务、RateLimiter 限流、data_pull_log 记录、DataCheckable 校验）。AI 对话模块重点检查：AI 输出是否包含未经验证的数值（幻觉风险）、是否输出了买卖建议类语言（合规风险）、是否正确使用 Function Calling 工具而非让模型直接生成数据。

### 6.2 发布流程

平台采用四阶段发布流程，每个阶段有明确的准入和准出条件，确保问题在影响用户前被发现。

| 阶段 | 环境 | 准入条件 | 准出条件 | 负责人 |
|------|------|----------|----------|--------|
| 开发 | 本地开发环境 | PR 合并到 develop 分支 | 开发自测通过，单元测试全绿 | 开发者 |
| 测试 | 测试环境（独立部署） | 开发阶段准出 | 集成测试通过，回归用例全绿 | 测试人员 |
| 预发布 | 预发布环境（生产配置） | 测试阶段准出 | 端到端验证通过，性能指标达标 | 开发 + 测试 |
| 生产 | 生产环境 | 预发布阶段准出 + 审批 | 线上监控指标正常，灰度用户无异常 | 运维 + 开发 |

发布流程的关键原则是**小步快走、灰度先行**。每次发布只包含一个 Phase 的增量功能，不做跨 Phase 的大版本发布。上线后先灰度 10% 用户观察 24 小时，监控错误率和用户反馈，无异常后再全量发布。预发布环境使用与生产相同的配置（数据库、Redis、模型 API），避免环境差异导致的问题遗漏。

### 6.3 回滚方案

当线上出现严重问题时，需要能快速回滚到上一个稳定版本。回滚方案按问题类型分级处理。

**代码回滚**针对发布引入的功能缺陷。平台维护每个生产版本的构建产物和数据库迁移脚本，代码回滚时通过重新部署上一个版本的构建产物完成。数据库变更需特别注意：如果新版本包含数据库 Schema 变更（新增表、新增字段），回滚代码版本前需确认 Schema 变更是否向前兼容。新增字段通常向前兼容，回滚安全；修改字段类型或删除字段则需先处理数据。建议所有数据库变更采用**只增不改**策略，新增字段加默认值，避免回滚时数据不一致。

**配置回滚**针对配置错误导致的问题（如模型 API Key 失效、限流阈值设置错误）。配置项通过配置中心或环境变量管理，变更后可快速切回上一版本。配置回滚不需要重新部署，生效速度快于代码回滚。

**数据回滚**针对数据错误导致的问题（如采集了错误数据导致分析结论异常）。Tushare 业务数据由 ERP 独占写入，数据回滚通过 ERP 管理页面触发指定表的全量重建完成，用 Tushare 接口的正确数据覆盖错误数据。C 端用户业务数据（对话、自选股、报告等）不设自动回滚，因为用户数据不可逆，错误数据需人工排查后定向修复。

回滚操作需在**告警触发后 30 分钟内**完成决策和执行。为缩短回滚时间，建议在每次发布前预演回滚流程，确认上一个版本的构建产物可用、回滚步骤清晰。回滚后需产出事故报告，记录问题原因、影响范围、回滚操作和后续修复计划。
