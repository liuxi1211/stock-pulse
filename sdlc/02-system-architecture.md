## 一、架构总览

### 1.1 分层架构

平台采用**双项目 + 计算服务**的三体结构。三个进程各自独立部署、独立演进，通过 MySQL 共享数据、通过 HTTP/JSON 完成进程间通信。整体分为四层：前端展现层、后端服务层、计算服务层、数据存储层。

### 1.2 架构设计目标

| 目标 | 含义 | 落地手段 |
|------|------|----------|
| **高可用** | 单点故障不影响整体，数据采集失败可重试 | 双项目进程隔离；Tushare 采集失败记录日志并重试；Redis 缓存兜底 |
| **可扩展** | 用户量增长时能横向扩容 | C 端无状态化设计，支持多实例部署；JDK 21 虚拟线程承载高并发 |
| **数据安全** | 用户数据与采集数据互不污染 | 读写权限隔离：ERP 独占 Tushare 表写入，C 端只读；用户业务表由 C 端独占读写 |
| **成本可控** | 模型与数据费用不失控 | 轻量查询用 qwen-turbo、深度分析用 qwen-plus；查询结果缓存；每日调用上限 |

### 1.3 架构约束

平台存在三条硬性约束。第一，**C 端公网暴露**：C 端应用面向个人投资者，必须通过公网访问，前端资源与 API 都暴露在互联网上，安全防护压力大。第二，**ERP 内网部署**：B 端 ERP 系统部署在内网，不直接暴露公网，仅通过内网与 MySQL、Tushare API 通信。第三，**数据库读写隔离**：MySQL 作为两个项目的共享存储，但写入权限严格分离，ERP 独占 Tushare 业务表的采集写入，C 端对这些表只能只读查询，避免读写竞争。

## 二、双项目职责划分

### 2.1 职责矩阵

两个项目从定位到部署形态完全独立，各自服务不同的人群。

| 维度 | C 端用户应用 | B 端 ERP 系统 |
|------|-------------|---------------|
| **定位** | 面向个人投资者的 AI 对话产品 | 面向运维/管理员的数据管理后台 |
| **端口** | :8080 | :8081 |
| **前端** | 富交互 Chat 页面 + SPA 式动态页面 | Thymeleaf SSR 管理页面 |
| **数据库权限** | 只读查询 + 用户业务表读写 | 全量读写（数据采集/治理） |
| **AI 能力** | Spring AI Alibaba 全栈 | 无 |
| **用户认证** | C 端用户注册/登录（手机号/微信） | 管理员账号 |
| **部署** | 独立部署，面向公网 | 内网部署，不暴露公网 |
| **数据流** | 从 MySQL 读取 Tushare 数据 -> AI 分析 -> 返回用户 | 从 Tushare API 拉取 -> 写入 MySQL -> 质量检测 |

### 2.2 模块归属边界

C 端应用独占以下模块：AI 对话中枢（ChatClient、Graph、ChatMemory、RAG、Function Calling）、研究方法引擎（18 种方法映射为 Graph 节点）、数据查询服务（Tushare 数据只读查询 + 个性化统计）、用户中心（自选股、持仓、任务调度、报告管理、推送通知）。计算服务虽然归入 C 端项目范畴，但它是一个独立进程，仅接收 C 端后端的 HTTP 调用，不与用户直接交互。

B 端 ERP 独占以下模块：Tushare 六层数据架构（Config、Client+RateLimiter、DO+Mapper、Service、DataInitService、DataGovernanceController）、数据采集调度（Quartz 定时任务）、质量检测、拉取日志管理、健康监控。ERP 不持有任何 AI 能力，也不处理用户业务数据。

### 2.3 跨项目协作协议

两个项目的协作纽带是 **MySQL 数据库**。ERP 系统负责把 Tushare 接口的数据采集、清洗后写入 MySQL 的 Tushare 业务表，C 端应用从这些表中只读查询。两者之间没有直接的 API 调用，完全通过共享数据库间接协作。

这种间接协作带来一个关键问题：**ERP 写入后 C 端何时可见**。由于 MySQL 的写入对其他连接即时可见（InnoDB 默认隔离级别下，事务提交后即可读），C 端查询到的数据新鲜度取决于 ERP 采集任务的执行频率。例如行情数据每日 16:00 采集一次，那么 C 端在 16:00 之前查到的是前一交易日的数据。这种延迟在日线级业务中是可接受的，无需引入实时同步机制。

ERP 采集任务均为**批量写入**，单次事务粒度控制在每页或每批（铁律：500 行/批、禁止跨 API 大事务），不会长时间锁表，因此不会阻塞 C 端的只读查询。C 端读取时配合 Redis 缓存热点数据，进一步降低数据库压力。

## 三、C 端应用内部架构

### 3.1 接入层

接入层对外暴露三种通信通道，分别服务于不同的交互场景。

| 通道 | 协议 | 用途 | 典型场景 |
|------|------|------|----------|
| **HTTP REST** | HTTP/JSON | 同步请求/响应 | 股票基本信息查询、自选股增删、报告列表、用户登录 |
| **SSE** | Server-Sent Events | AI 对话流式输出 | 用户提问后，AI 回复以打字机效果逐字推送，富媒体容器流式拼装 |
| **WebSocket** | 双向长连接 | 实时推送 | 盯盘触发通知、定时任务完成推送、消息中心铃铛红点 |

HTTP REST 承担绝大多数常规请求，属于"问一句答一句"的同步交互。SSE 专门服务于 AI 对话流，当用户发送消息后，后端建立一条 SSE 连接，将 ChatClient 的逐 token 输出实时推给前端，配合富媒体容器（股票卡片、图表）的骨架屏占位，消除等待焦虑。WebSocket 用于服务端主动推送场景，维持一条双向长连接，当盯盘引擎检测到触发条件或定时任务执行完成时，通过 WebSocket 把富媒体消息推送到用户浏览器。

JDK 21 的**虚拟线程**是接入层的并发底座。SSE 和 WebSocket 都是长连接，传统平台线程模型下每个连接占用一个 OS 线程，并发量上去后线程数爆炸。虚拟线程让每个连接挂在一个轻量级线程上，阻塞时自动让出载体线程，单机即可承载数万并发连接。

### 3.2 AI 中枢层

AI 中枢层是 C 端后端的核心，基于 **Spring AI Alibaba** 构建，包含五个组件，各自承担明确职责。

**ChatClient** 是与通义千问模型交互的统一入口，封装了模型调用、token 计费、流式输出。所有需要 AI 生成文本的场景都经过 ChatClient，便于统一做限流、缓存和成本统计。轻量查询场景调用 qwen-turbo 控制成本，深度分析场景调用 qwen-plus 保证质量。

**Graph 多智能体编排**负责多步骤研究的节点串联。18 种研究方法各自映射为一个 Graph 节点，当用户请求"全面分析茅台"时，Graph 引擎编排基本面速览、技术面研判、估值分析、资金面分析等多个节点，节点间可串联、可并行、可条件分支，产出结构化 HTML 报告。

**ChatMemory** 维护对话上下文，按 conversationId 隔离。窗口保留最近 20 条消息，超出窗口的旧消息由 AI 摘要后存入长期记忆。用户偏好（关注板块、估值偏好）跨会话持久化，让 AI 记住用户的投资风格。

**RAG 检索增强**基于 Redis Stack 的 RediSearch 向量索引，维护三个知识库：投资方法论库、历史报告库、公司基本面库。当 AI 需要引用方法论或回溯历史报告时，先做向量检索再注入上下文，降低幻觉。

**Function Calling 工具调用**是 AI 与数据世界连接的桥梁。15 个核心工具（查行情、查财务、查资金流向、计算指标、创建任务等）注册为可调用函数，AI 根据用户意图自动选择工具、组装参数、解析返回值，生成股票卡片等富媒体容器。

```
用户消息
  │
  ▼
┌──────────────────────────────────────────────┐
│              意图路由（Function Calling）       │
│  判断：轻量查询 / 单方法分析 / 多步骤研究 /     │
│        操作指令 / 选股筛选 / 闲聊兜底          │
└──┬───────┬──────────┬───────────┬───────────┘
   │       │          │           │
   ▼       ▼          ▼           ▼
ChatClient  Graph     Function     ChatClient

```

### 3.3 业务服务层

业务服务层在 AI 中枢之下，提供两类支撑能力。第一类是**研究方法引擎**，将 18 种研究方法（tear-sheet、technical-analysis、event-anomaly、DCF 估值、可比估值等）封装为独立模块，既可被 Graph 单独调用，也可组合编排。每个方法模块的职责是组装数据、调用计算服务、生成富媒体组件，AI 只负责最终的文字解读。第二类是**用户中心**，管理自选股、持仓、任务调度（Quartz）、报告管理、推送通知，这些是用户个性化的载体，数据全部落在用户业务表中。

数据查询服务是业务服务层中连接数据的枢纽。它封装了对 Tushare 业务表的只读查询，提供股票行情、估值指标、财务三表、资金流向、龙虎榜等查询能力，并叠加个性化统计（自选股涨跌汇总、持仓盈亏、行业分布）。这些查询既服务于 Function Calling 工具，也服务于研究方法引擎和定时任务。

### 3.4 数据访问层

数据访问层基于 **MyBatis-Plus**，对两类数据采取不同策略。Tushare 业务表（stock_basic、daily_quote、daily_basic 等 25+ 张）由 ERP 写入，C 端只做只读查询，对应 Mapper 只暴露 select 方法，不提供 insert/update/delete。用户业务表（chat_conversation、user_watchlist、analysis_report 等）由 C 端独占读写，Mapper 提供完整 CRUD。

Caffeine 本地缓存与 Redis 分布式缓存配合使用。热点行情数据（如当日大盘指数、热门股票实时价）先查 Caffeine，未命中再查 Redis，最后回源 MySQL。查询结果按 ts_code + trade_date 做复合 key 缓存，行情数据 TTL 设为当日有效，估值数据 TTL 设为 1 小时，避免重复查询数据库。

## 四、B 端 ERP 内部架构

### 4.1 Tushare 六层数据架构

B 端 ERP 的核心是参考 stock-pulse 验证过的 **Tushare 六层数据架构**，自下而上分层，每层职责单一，数据从 Tushare API 流向 MySQL 的过程中逐层加工。

```
┌─────────────────────────────────────────────────────────┐
│  第6层  DataGovernanceController                          │
│  数据治理：健康总览、单表管理、拉取日志、质量检测          │
└────────────────────────┬────────────────────────────────┘
                         │ 调用
┌────────────────────────▼────────────────────────────────┐
│  第5层  DataInitService                                  │
│  增量/全量入口：switch case 路由到各 Service + 写拉取日志  │
└────────────────────────┬────────────────────────────────┘
                         │ 调用
┌────────────────────────▼────────────────────────────────┐
│  第4层  Service 层                                       │
│  分页拉取 + 批量保存（5条铁律）+ DataCheckable 质量校验   │
└────────────────────────┬────────────────────────────────┘
                         │ 调用
┌────────────────────────▼────────────────────────────────┐
│  第3层  DO + Mapper                                      │
│  数据对象 + MyBatis-Plus 持久化（schema.sql 定义表结构）  │
└────────────────────────┬────────────────────────────────┘
                         │ 调用
┌────────────────────────▼────────────────────────────────┐
│  第2层  TushareClient + RateLimiter                      │
│  统一请求入口 + 阻塞式限流 + 分页回调 + FastJSON2 解析    │
└────────────────────────┬────────────────────────────────┘
                         │ 读取配置
┌────────────────────────▼────────────────────────────────┐
│  第1层  Config + TushareApiEnum                          │
│  接口元数据（api_name + fields 字符串）+ 限流参数配置     │
└─────────────────────────────────────────────────────────┘
```

**第1层 Config** 管理 Tushare 接口元数据，核心是 TushareApiEnum 枚举，每个枚举项记录 api_name 和 fields 字符串，fields 必须与 Tushare 官方文档逐字一致，错一个字符会导致返回值全为 null。限流参数（每分钟调用上限）也在配置层定义。

**第2层 Client + RateLimiter** 是所有 Tushare 请求的统一入口。TushareClient 封装了请求组装、POST 调用、fields[]+items[][] 解析、DTO 映射；RateLimiter 做阻塞式限流，防止触发 Tushare 的 429 限流响应。所有接口都必须支持 offset/limit 分页，不允许绕过 RateLimiter 直接拼 HTTP。

**第3层 DO + Mapper** 负责持久化，表结构定义在 schema.sql，DO 对象与表一一对应，Mapper 基于 MyBatis-Plus 提供批量写入能力。这层只做存取，不含业务逻辑。

**第4层 Service** 是采集逻辑的核心，必须同时满足 5 条铁律：单次返回不超过 5000 且必须 offset+limit 循环分页、offset 超过 10 万时按时间或标的降维拆分、不绕过 RateLimiter、事务粒度最小化禁止跨 API 大事务、批量写入每批 500 行禁止循环逐条插入。Service 层还实现 DataCheckable 接口做质量校验。

**第5层 DataInitService** 是增量/全量更新的统一入口，通过 switch case 路由到各业务 Service，并记录拉取日志（data_pull_log），记录每次拉取的接口、时间、状态、数据量。

**第6层 DataGovernanceController** 暴露 REST 接口给 ERP 管理页面，提供数据总览、单表管理（触发增量更新/全量重建）、拉取日志查询、质量检测结果展示。

### 4.2 数据采集调度架构

数据采集由 **Quartz 定时任务**驱动，按接口出数频率注册不同调度策略。

| 数据类别 | 调度频率 | 涉及表 | 说明 |
|----------|----------|--------|------|
| 日线行情 | 每日 16:00 | daily_quote / daily_basic / moneyflow | 盘后采集当日全量 |
| 财务数据 | 每周日 17:00 | income / balancesheet / cashflow / fina_indicator | 财报季按季更新 |
| 事件数据 | 每日 16:00 | top_list / margin_detail / hk_hold | 龙虎榜、融资融券、北向 |
| 基础数据 | 每日 02:00 | stock_basic / trade_cal | 股票列表、交易日历 |

调度引擎在执行采集时，逐表调用 DataInitService 的增量更新逻辑，失败时记录日志并标记异常状态。采集任务之间无强依赖，单表失败不影响其他表。TushareDataScheduler 按接口出数频率统一注册调度步骤，避免每个接口单独配置定时任务。

### 4.3 质量检测与日志管理

每张 Tushare 业务表的 Service 实现了 **DataCheckable** 接口，提供 3-5 个核心检测指标，覆盖数据量级、最新数据日期、缺失交易日、重复数据、字段异常值等常见问题。检测结果写入治理表，由 DataGovernanceController 在管理页面以状态灯（绿色正常/黄色延迟/红色异常）展示。

拉取日志（data_pull_log）记录每次采集的完整轨迹：接口名称、拉取时间、起始参数、返回数据量、耗时、状态（成功/失败）、失败原因。运维人员通过日志排查数据断更问题，定位到具体接口后可一键触发增量更新重试。

## 五、计算服务架构

### 5.1 服务定位与通信协议

计算服务是一个独立的 **Python FastAPI** 进程，部署在 C 端后端同网络域，端口 :8085。它与 C 端后端通过 HTTP/JSON 通信，C 端后端把行情数据或参数通过 HTTP 传入，计算服务返回 JSON 结果，不直接接触数据库。

这种设计遵循 stock-pulse 验证的**数据单源性原则**：数据库的读写由 Java 侧独占，Python 计算服务只做纯计算。数据需要时由 C 端后端从 MySQL 取出后通过 HTTP 传入，计算结果原路返回 JSON，由 C 端后端决定如何存储和展示。

```
C 端后端 (Java :8080)
    │
    │  1. 从 MySQL 取行情数据
    │  2. HTTP POST 传入计算服务
    │     {kline_data: [...], indicator: "MACD", params: {...}}
    │
    ▼
计算服务 (Python :8085)
    │
    │  3. Pandas/talib 计算指标
    │  4. 返回 JSON 结果
    │     {indicator: "MACD", values: [...]}
    │
    ▼
C 端后端 (Java :8080)
    │
    │  5. 组装富媒体容器 / 存入报告
```

### 5.2 技术指标与因子计算接口

计算服务对外提供两类接口。第一类是**技术指标计算**，接收 K 线数据序列和指标名称（MA、MACD、KDJ、BOLL、RSI、ATR 等），返回计算后的指标数值序列，供前端 ECharts 渲染图表。第二类是**因子计算与统计分析**，接收股票池和因子定义，返回因子值排名、收益率统计、DCF 估值等结果，供研究方法引擎和选股筛选使用。

接口设计遵循 FastAPI 最佳实践：路由层只做参数校验和响应封装，核心逻辑放在 service 层，数据模型用 Pydantic Schema 定义。FastAPI 自动生成 OpenAPI 文档（:8085/docs），方便 C 端后端联调对齐字段。

### 5.3 engine 不读写数据库的硬约束

计算服务有一条不可违反的硬约束：**engine 禁止出现任何数据库驱动、ORM 或直连 .db 的代码**。这条约束源自 stock-pulse 的数据治理经验，目的是保证数据单源性。

如果计算服务直连数据库，会引入两个风险。一是数据库连接数翻倍，Python 侧与 Java 侧各自维护连接池，高并发时连接池容易耗尽。二是数据一致性失控，两个进程同时读写同一张表，锁竞争和脏读难以排查。通过 HTTP 传入数据的模式，数据库的读写入口收敛到 Java 侧一处，计算服务变为无状态的纯函数，可随意水平扩容而不触及数据库。

计算服务自身不持久化任何业务数据，所有计算结果要么由调用方（C 端后端）决定是否存库，要么作为临时结果返回给前端。这种无状态特性让计算服务可以多实例部署，通过负载均衡分摊计算压力。

## 六、数据架构设计

### 6.1 数据存储总览

平台的数据存储由 **MySQL** 和 **Redis** 两个组件构成，前者承载结构化数据，后者承担缓存、向量索引与队列职责。

```
┌─────────────────────────────────────────┐
│              MySQL 数据库                │
│                                         │
│  ┌─────────────┐   ┌─────────────────┐  │
│  │ Tushare 业务表│   │  C 端用户业务表   │  │
│  │ (25+张，ERP  │   │  chat_conversation│  │
│  │  写入，C端   │   │  chat_message     │  │
│  │  只读)       │   │  user_watchlist   │  │
│  │              │   │  user_portfolio   │  │
│  │  stock_basic │   │  user_task        │  │
│  │  daily_quote │   │  user_task_log    │  │
│  │  daily_basic │   │  analysis_report  │  │
│  │  ...         │   │  push_notification │  │
│  └─────────────┘   │  ai_audit_log     │  │
│                     └─────────────────┘  │
│  ┌─────────────────────────────────────┐ │
│  │         Redis（缓存+向量）            │ │
│  │  会话缓存 │ 向量索引(RediSearch)     │ │
│  │  实时行情缓存 │ 任务队列              │ │
│  └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

MySQL 内部按写入权限分为两组表。**Tushare 业务表**有 25+ 张，涵盖股票基础信息、日线行情、估值指标、财务三表、资金流向、龙虎榜、融资融券、北向持股等，全部由 ERP 系统采集写入，C 端只读查询。**C 端用户业务表**包括对话会话、消息记录、自选股、持仓、监控规则、定时任务、分析报告、推送通知、AI 审计日志等，由 C 端应用独占读写，ERP 不触及。

### 6.2 MySQL 表分区策略

两类表的数据特征和访问模式不同，分区策略也相应区分。Tushare 业务表以时间序列为主，数据量大且持续增长，按交易日期做分区最合理。例如 daily_quote 表按年分区，每个分区存一个交易年度的行情数据，查询特定时间段时只需扫描对应分区，避免全表扫描。财务表（income、balancesheet 等）数据量较小，按报告期年度分区即可。

C 端用户业务表的数据增长与用户量正相关，按 user_id 做哈希分区较为合适。analysis_report 和 chat_message 是数据量增长最快的两张表，单表数据量随用户活跃度线性增长，通过 user_id 哈希可以把不同用户的数据分散到不同分区，避免单分区成为热点。

索引设计上，Tushare 业务表以 ts_code + trade_date 复合索引为主，覆盖绝大多数行情查询场景；用户业务表以 user_id 为首要索引列，配合业务字段（如 conversation_id、report_type）建二级索引。

### 6.3 Redis 使用规划

Redis Stack 在平台中承担四类职责，各自有独立的使用方式和生命周期管理。

| 用途 | Key 模式 | TTL | 说明 |
|------|----------|-----|------|
| **会话缓存** | `session:{userId}` | 30 分钟 | 用户登录态、会话上下文窗口（20 条消息） |
| **向量索引** | RediSearch 索引 | 长期 | 三个 RAG 知识库：方法论、历史报告、公司基本面 |
| **实时行情缓存** | `quote:{ts_code}:{trade_date}` | 当日 | 热门股票行情、估值指标，降低 MySQL 查询压力 |
| **任务队列** | `task:queue:{userId}` | 持久 | 盯盘触发事件、定时任务结果排队推送 |

会话缓存用于存储 ChatMemory 的窗口消息，避免每次对话都查 MySQL 的 chat_message 表。向量索引是 RAG 的存储底座，RediSearch 提供高效的向量相似度检索，支撑 AI 对话中引用历史报告和方法论。实时行情缓存服务于高频查询场景，当多个用户同时查询茅台行情时，第一次查 MySQL 后缓存到 Redis，后续直接命中缓存。任务队列用于异步场景，盯盘触发或定时任务完成后，消息先入 Redis 队列，再由推送服务消费并通过 WebSocket 推给在线用户。

### 6.4 数据一致性策略

平台的数据一致性需求是**最终一致**而非强一致。ERP 采集写入 MySQL 后，C 端何时可见取决于两个因素：MySQL 事务提交时机和 C 端缓存失效策略。

ERP 的批量写入遵循铁律，每页或每批一个事务，事务提交后数据对其他连接立即可见（InnoDB 默认 READ COMMITTED 即可满足）。这意味着 C 端在 ERP 采集完成后查询，能立即读到最新数据。但 C 端的 Redis 缓存可能持有旧数据，因此需要**缓存失效策略**配合。

针对实时行情缓存，采用"当日有效"的 TTL 策略：缓存 Key 中带 trade_date，当日缓存次日自动过期，配合 ERP 每日 16:00 采集的节奏，保证 C 端在盘后能读到当日最新行情。对于不在缓存中的查询，直接回源 MySQL 拿到最新数据并回填缓存。估值类数据变化频率低，TTL 设为 1 小时，在新鲜度和缓存命中率之间取平衡。

用户业务表的数据由 C 端独占读写，不存在跨进程一致性问题，写入后立即对自己可见，无需额外同步。

## 七、渐进式架构演进

### 7.1 演进总览

平台架构遵循"先一体后分离"的渐进策略，按 Phase 阶段逐步演进，避免过早引入分布式复杂度。

| 阶段 | 架构形态 | 核心变化 | 迁移成本 |
|------|----------|----------|----------|
| **Phase 0-2** | 前后端一体 | C 端前端静态资源与后端同进程 | 无（起始状态） |
| **Phase 3** | 一体 + 个性化 | 新增盯盘、任务、推送模块 | 低（同进程内新增） |
| **Phase 4** | 前后端分离 | C 端前端拆为独立 Vue 3 项目 | 中（前端重构） |
| **Phase 4+** | 微服务（可选） | 按业务域拆分后端服务 | 高（分布式改造） |

### 7.2 Phase 0-2：前后端一体

初期 C 端应用前端（Chat 页面、股票卡片、报告中心等）与后端（Java）在同一个 Spring Boot 项目中。前端资源放在 `src/main/resources/static` 下，通过 Spring Boot 静态资源服务直接提供，后端提供 REST API 和 SSE 流式接口。

这种模式的优势是开发快、部署简单、调试方便。前端改了 JS 直接刷新即可生效，后端改了接口本地联调，无需跨进程联调。Phase 0 完成项目骨架和数据底座，Phase 1 打通富交互对话，Phase 2 建设报告中心，三个阶段都在一体架构下完成。

### 7.3 Phase 3：一体架构下的个性化扩展

Phase 3 在一体架构上新增盯盘引擎、定时任务、消息通知中心三个模块。这些模块都部署在 C 端后端进程内，通过 Quartz 调度和 WebSocket 推送实现。架构本身不发生变化，只是进程内的模块增多，**迁移成本极低**。

需要注意的新增点是：Quartz 调度器的线程池要独立于 HTTP 请求线程池，避免定时任务耗尽请求线程导致 API 无响应。盯盘引擎的取数和 AI 分析是耗时操作，应异步执行，结果通过 Redis 队列缓冲后推送，不阻塞调度线程。

### 7.4 Phase 4：前后端分离

当 C 端用户量增长、前端复杂度提升时，将前端拆分为独立 Vue 3 项目。后端变为纯 API 服务，前端独立部署到 CDN 或独立 Web 服务器，通过 HTTP/SSE/WebSocket 调用后端接口。

**架构变化点**：前端构建产物从 Java 项目中的静态资源变为独立部署的 SPA 应用；后端需要处理 CORS 跨域；静态资源服务从 Spring Boot 迁移到 Nginx。**迁移成本评估**为中等，主要工作在于前端从原生 JS 模块化迁移到 Vue 3 组件化，以及路由、状态管理的重新设计。后端接口基本无需改动，因为 Phase 0-2 已经按 RESTful 设计接口。

### 7.5 Phase 4+：微服务拆分（可选）

微服务拆分不是必选项，只有当单体后端的性能或团队协作出现瓶颈时才触发。拆分的业务域边界为：**对话服务**（AI 中枢、意图路由、Graph 编排）、**数据服务**（Tushare 查询、计算服务调用）、**任务服务**（盯盘引擎、定时调度、推送通知）。

触发拆分的判断标准有三条。第一，**单机性能瓶颈**：C 端后端单实例 CPU 利用率持续超过 70%，通过横向扩容多实例（无状态化已支持）仍无法缓解。第二，**资源争用**：盯盘引擎的批量 AI 调用消耗大量模型配额和 CPU，影响对话接口的响应延迟，P95 响应时间超过 2 秒。第三，**团队规模**：开发团队超过 5 人，单体代码库的合并冲突频繁，迭代效率下降。三条满足其一即可考虑拆分，优先拆出资源消耗最大的任务服务。

拆分后，三个服务共享 MySQL 和 Redis，通过 HTTP 互相调用。拆分带来的成本是分布式事务、链路追踪、服务发现等基础设施的引入，因此必须有明确的收益支撑，不可为拆而拆。

## 八、非功能性设计

### 8.1 性能目标

| 指标 | 目标值 | 适用场景 | 保障手段 |
|------|--------|----------|----------|
| **API 响应时间（P95）** | < 500ms | 常规 HTTP 查询接口 | Redis 缓存热点数据；MyBatis-Plus 索引优化；Caffeine 本地缓存 |
| **SSE 流式首字延迟** | < 1.5s | AI 对话首 token 输出 | ChatClient 流式调用模型；意图路由快速分流，轻量查询走 qwen-turbo |
| **WebSocket 推送延迟** | < 2s | 盯盘触发到用户收到 | 触发事件入 Redis 队列，推送服务实时消费；在线连接复用 |
| **深度报告生成** | < 60s | 多节点 Graph 编排 | 节点级超时控制；可并行节点并行执行；长任务异步化 + 完成推送 |

SSE 流式首字延迟是用户体验的关键指标。用户发送消息后，如果在 1.5 秒内看不到任何输出，会认为系统卡死。通过流式调用模型（模型边生成边返回 token），首字延迟主要由模型推理启动时间决定，qwen-turbo 的首 token 延迟通常在 1 秒以内。深度报告因涉及多节点编排和多次模型调用，采用异步模式：先返回"正在生成报告"的提示，后台编排完成后通过 WebSocket 推送完成通知。

### 8.2 可用性目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| **C 端服务可用性** | 99.5% | 对应每月停机不超过 3.6 小时 |
| **数据采集成功率** | 99% | 单表采集失败记入日志并重试，重试三次仍失败才标记异常 |
| **模型调用可用性** | 99% | 依赖通义千问 DashScope API 的服务稳定性，需有降级文案兜底 |

数据采集成功率通过 ERP 的重试机制保障。Tushare 接口限流（429）是采集失败的主要诱因，RateLimiter 阻塞式限流从源头规避，失败后记录日志由运维触发重试。C 端服务可用性依赖单实例的稳定性，初期通过进程监控和自动重启保障，Phase 4 后可多实例部署提升容错。

### 8.3 安全设计

**C 端用户认证**采用手机号/微信登录，会话凭证存储在 Redis（session:{userId}，TTL 30 分钟），每次请求校验会话有效性。密码存储使用 BCrypt 加盐哈希，不可逆。登录态失效后跳转登录页，WebSocket 连接在会话失效时主动断开。

**API 鉴权**分两层。第一层是会话鉴权，所有 C 端接口校验请求头中的 session token，未登录请求返回 401。第二层是 Function Calling 内部鉴权，AI 调用工具时携带当前 user_id，查询用户业务数据时强制按 user_id 过滤，防止越权访问他人数据。ERP 管理接口仅内网可访问，配合管理员账号独立认证。

**数据隔离**通过读写权限和用户维度双重保障。Tushare 业务表所有用户共享只读，无隔离需求；用户业务表以 user_id 为隔离边界，查询索引以 user_id 为首列，MyBatis-Plus 的 QueryWrapper 强制追加 user_id 条件。C 端公网暴露带来 SQL 注入和 XSS 风险，MyBatis-Plus 的参数化查询天然防 SQL 注入，前端 Markdown 渲染时对用户输入做转义防 XSS。AI 输出内容经合规过滤 Advisor 检查，确保不输出买卖建议类违规内容。
