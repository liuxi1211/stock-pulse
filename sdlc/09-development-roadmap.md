## 一、路线图总览

### 1.1 Phase 划分与目标

平台开发分为五个阶段，从数据底座到架构拆分层层递进。每个 Phase 都有明确的目标和验收标准，前一个 Phase 的产出是后一个 Phase 的前置条件。

| Phase | 名称 | 核心目标 | 关键产出 |
|-------|------|----------|----------|
| Phase 0 | 项目骨架 + 数据底座 | 搭建双项目骨架，ERP 完成数据采集，C 端跑通最小对话 | 25 张表数据落库、最小 ChatClient 联调 |
| Phase 1 | 富交互 Chat + 单方法分析 | 打通富交互对话界面，实现股票卡片与单方法分析 | 股票卡片、4 种 Graph 节点、15 个工具 |
| Phase 2 | 深度研究 + 报告中心 | 实现多步骤研究报告生成，建立专业报告中心 | 18 种 Graph 节点、报告中心、数据可追溯 |
| Phase 3 | 个性化盯盘 + 定时任务 | 实现盯盘引擎、定时任务、消息通知中心 | 8 种盯盘规则、定时任务、WebSocket 推送 |
| Phase 4 | 多源增强 + 体验打磨 + 架构拆分 | 接入多源数据，打磨体验，前后端分离 | ifind 多源、前后端分离、微服务评估 |

### 1.2 Phase 间依赖关系

五个 Phase 之间存在严格的先后依赖，不能跳序执行。下表描述每个 Phase 的前置依赖和解除依赖后才能启动的后续阶段。

| Phase | 前置依赖 | 依赖原因 | 解锁的后续 Phase |
|-------|----------|----------|------------------|
| Phase 0 | 无 | 项目从零起步，数据底座是一切前提 | Phase 1 |
| Phase 1 | Phase 0 | 富交互对话依赖 Phase 0 的数据查询接口和最小 ChatClient | Phase 2、Phase 3 |
| Phase 2 | Phase 1 | 深度研究依赖 Phase 1 的单方法 Graph 节点和 Chat 界面 | Phase 3（任务执行需调报告引擎）、Phase 4 |
| Phase 3 | Phase 1、Phase 2 | 定时任务执行需调用 Phase 2 的报告生成引擎；盯盘推送需复用卡片组件 | Phase 4 |
| Phase 4 | Phase 2、Phase 3 | 多源增强与架构拆分需在功能完整后进行 | 无（终态） |

需要说明的是，Phase 3 对 Phase 2 的依赖是**部分依赖**而非完全阻塞。盯盘引擎的价格监控、通知中心的基础能力可以在 Phase 2 报告引擎完成前先行开发，只有定时任务的报告产出能力需要等待 Phase 2 的报告生成引擎就绪。因此在排期上，Phase 3 的部分任务可以与 Phase 2 并行启动。

### 1.3 预估工期与人力配置

下表给出每个 Phase 的预估工期和人力配置建议。工期基于任务复杂度和串行依赖推算，人力配置按"一人多岗、核心聚焦"原则安排，假设团队规模为 2-3 名全栈倾向的开发者。

| Phase | 预估工期 | 后端（Java） | 前端 | Python/算法 | 说明 |
|-------|----------|-------------|------|-------------|------|
| Phase 0 | 4-6 周 | 1.5（ERP 1 + C 端 0.5） | 0.5 | 0 | ERP 六层架构是工期瓶颈 |
| Phase 1 | 6-8 周 | 1 | 1 | 0.5 | 富交互前端与工具封装并行 |
| Phase 2 | 6-8 周 | 1 | 0.5 | 0.5 | Graph 编排与报告中心并重 |
| Phase 3 | 5-7 周 | 1 | 0.5 | 0 | 调度引擎与通知中心为主 |
| Phase 4 | 4-6 周 | 1 | 1 | 0.5（含 DevOps） | 前后端分离需前后端协同 |
| **合计** | **25-35 周** | | | | 约 6-9 个月 |

上述工期按串行执行估算。如果团队人力充足且 Phase 2、Phase 3 的部分任务并行推进，整体工期可压缩 15%-20%。工期估算已包含联调、自测和修复时间，但未包含正式公测后的线上问题修复周期。

## 二、Phase 0 - 项目骨架 + 数据底座

### 2.1 任务清单

Phase 0 分为 B 端 ERP 和 C 端应用两条并行工作线，目标是在数据层打通"ERP 采集写入 -> MySQL 共享 -> C 端只读查询"的链路，同时让 C 端跑通最小 AI 对话。

**B 端 ERP 任务：**

| 编号 | 任务 | 说明 |
|------|------|------|
| B0-1 | 创建 ERP 项目骨架 | Java + Spring Boot + MyBatis-Plus + Thymeleaf，独立端口 :8081 |
| B0-2 | 实现 Tushare 六层架构基础层 | Config / Client / RateLimiter / TushareApiEnum |
| B0-3 | 实现 DO + Mapper 数据层 | 25 张表对应的实体类与 Mapper |
| B0-4 | 实现 Service 分页/事务/分批层 | 遵循 500 行/批、禁止跨 API 大事务的铁律 |
| B0-5 | 实现 25 个 Tushare 接口采集与治理 | 增量更新 + 全量重建 + DataCheckable 校验 |
| B0-6 | 开发数据管理 ERP 页面 | 数据总览 / 单表管理 / 拉取日志 / 数据源健康 |
| B0-7 | 配置定时采集任务 | 行情每日 16:00 / 财务每周日 17:00 / 事件每日 16:00 |

**C 端应用任务：**

| 编号 | 任务 | 说明 |
|------|------|------|
| C0-1 | 创建 C 端项目骨架 | Java + Spring Boot + Spring AI Alibaba，独立端口 :8080 |
| C0-2 | 接入通义千问 DashScope API | 跑通最小 ChatClient 对话 |
| C0-3 | 搭建前端骨架 | HTML + CSS + JS + ECharts，静态资源托管 |
| C0-4 | 实现 Tushare 数据只读查询接口 | 对接 MySQL，读 ERP 写入的数据 |
| C0-5 | 部署 Redis Stack | 作为向量存储和会话缓存 |

| B0-4 | B0-2、B0-3 | 无 | Service 层需要 Client 和 Mapper |
| B0-5 | B0-4 | B0-6（部分） | 采集依赖 Service；ERP 页面框架可先行 |
| B0-6 | B0-4 | B0-7 | 页面需 Service 提供数据 |
| B0-7 | B0-5 | 无 | 定时任务需采集逻辑就绪 |

### 2.3 关键路径

Phase 0 的**关键路径**为 B0-1 -> B0-2 -> B0-4 -> B0-5 -> C0-4。这条路径决定了 Phase 0 的最短工期：ERP 六层架构逐层搭建、25 个接口采集实现、最后 C 端只读查询验证数据贯通。B0-3（DO+Mapper）虽然也依赖 B0-1，但它与 B0-2 可以并行，因此不在关键路径上。

C0-2（接入 DashScope）和 C0-3（前端骨架）是 C 端的短路径，通常会在 B 端关键路径推进期间提前完成，等待 C0-4 汇合。C0-5（Redis Stack）是完全独立的部署任务，可在任意时间点完成，只要在 Phase 0 验收前就绪即可。

### 2.4 验收标准与量化指标

原报告给出了两条定性验收标准，此处补充量化指标以便客观判定通过与否。

| 验收项 | 原报告标准 | 量化指标 |
|--------|-----------|----------|
| B 端数据采集 | ERP 页面能触发 25 张表的增量更新和全量重建 | 25 张表全部触发成功；data_pull_log 记录完整；单表增量更新响应 < 30 秒 |
| C 端 AI 对话 | 能通过 API 发送消息并收到 AI 回复 | 调用 chat API 返回 200；回复非空且为通义千问生成内容；端到端延迟 < 5 秒 |
| C 端数据查询 | 能查询茅台的日线行情 | 查询 600519.SH 返回最近 30 个交易日 OHLCV 数据；字段无空值 |
| Redis Stack | 向量索引创建成功 | RediSearch 索引可查询；FT.INFO 返回索引信息 |

验收需全部通过才算 Phase 0 完成。任一项不达标，需在当前 Phase 内修复后重新验收，不进入 Phase 1。

### 3.3 验收标准与前端验收流程

原报告给出了四条验收标准，此处补充前端验收的具体操作流程，确保验收过程可重复、可比对。

| 验收项 | 原报告标准 | 前端验收流程 |
|--------|-----------|-------------|
| PE 查询富交互 | 输入"茅台今天的 PE 是多少"，返回股票卡片 + PE 分位图 + AI 解读 | 1. 在输入框输入查询语句；2. 确认 AI 回复流式输出（打字机效果）；3. 确认回复包含股票卡片组件（非纯文本）；4. 确认卡片内含 PE 分位图；5. 确认有 AI 解读文字 |
| 技术面分析 | 输入"茅台技术面怎么样"，返回技术指标图表 + 结构化分析 | 1. 输入查询语句；2. 确认回复包含技术指标图表（MA/MACD/KDJ）；3. 确认图表下方有结构化分析文本；4. 确认非纯文本回复 |
| 多轮上下文 | 连续对话 3 轮以上，上下文连贯 | 1. 第 1 轮问"茅台今天怎么样"；2. 第 2 轮问"它的 PE 呢"（不重复股票名）；3. 第 3 轮问"帮我加自选"；4. 确认每轮 AI 能理解指代关系；5. 确认左侧会话列表显示当前会话 |

前端验收流程的核心判定原则是：任何一条 AI 回复如果只有纯文本且用户问了股票相关问题，视为不达标。富交互不是可选项，而是默认输出形态。

### 4.3 Graph 编排开发顺序

Graph 编排是 Phase 2 技术复杂度最高的部分，建议按"从简到繁"的渐进顺序开发，每一步验证通过后再进入下一步，避免一次性实现复杂分支导致难以调试。

| 步骤 | 编排类型 | 示例场景 | 验证点 | 难度 |
|------|----------|----------|--------|------|
| 第 1 步 | 单节点直连 | tear-sheet 单独执行 | 节点输入输出正确 | 低 |
| 第 2 步 | 双节点串联 | tear-sheet -> 技术面分析 | 节点间数据传递正确 | 低 |
| 第 3 步 | 多节点串联 | tear-sheet -> 技术面 -> 估值 -> 资金面 -> 风险提示 | 5 节点链路完整 | 中 |
| 第 4 步 | 条件分支 | 根据市值大小走不同估值方法 | 分支判断逻辑正确 | 中 |
| 第 5 步 | 并行节点 | 技术面与基本面并行执行后汇总 | 并行结果合并正确 | 高 |
| 第 6 步 | Human-in-the-loop | 估值分析前暂停等待用户确认确认维度 | 暂停/恢复机制正确 | 高 |

前 3 步是 Phase 2 验收的最低要求（"编排 5+ 节点"），第 4-6 步是增强能力。建议在第 3 步验证通过后，先完成报告生成引擎（P2-4）和报告中心（P2-5），让端到端链路跑通，再回头补充条件分支和并行能力。这样可以尽早暴露集成问题，避免 Graph 编排和报告引擎都做完后才发现接口不匹配。

### 6.3 前后端分离迁移步骤

前后端分离是 Phase 4 的重头戏，迁移过程需保证线上功能不受影响。建议分四步渐进迁移，每一步验证通过后再进入下一步。

| 步骤 | 操作 | 验证点 | 风险 |
|------|------|--------|------|
| 第 1 步 | 抽取前端代码为独立 Vue 3 项目 | 前端可独立构建和运行 | 接口契约不一致 |
| 第 2 步 | 后端接口去 Thymeleaf 依赖，纯 API 化 | 所有接口返回 JSON，无 SSR 页面 | 遗漏页面依赖 |
| 第 3 步 | 前端构建产物部署到 Nginx / CDN | 前端通过 Nginx 反代访问后端 API | 跨域、路由问题 |
| 第 4 步 | 联调验证全部功能 | 对话、报告、盯盘、任务全链路正常 | 集成回归问题 |

迁移期间的关键原则是**保持后端接口不变**。前端从 Thymeleaf 模板迁移到 Vue 3 组件时，后端 REST API 和 SSE 接口的路径、参数、返回格式应保持一致，避免前后端同时改动导致难以定位问题。如果接口确实需要调整，应单独做一个接口版本升级，与前端迁移解耦。

### 6.4 微服务拆分评估标准

微服务拆分在原报告中标注为"可选"，这意味着不应盲目拆分。建议在以下评估标准全部满足时再启动拆分，否则保持单体架构。

| 评估维度 | 拆分触发标准 | 当前状态（Phase 3 完成后） | 建议 |
|----------|-------------|---------------------------|------|
| 性能瓶颈 | 单体出现明确瓶颈点（如 Graph 执行阻塞对话响应） | 单体 + 虚拟线程可支撑初期 | 暂不拆分 |
| 团队规模 | 团队 > 5 人，需并行开发不同模块 | 2-3 人小团队 | 暂不拆分 |
| 部署独立性 | 数据采集与对话服务需独立发布节奏 | ERP 已独立，C 端内部耦合低 | 暂不拆分 |
| 故障隔离 | 单模块故障需不影响其他模块 | 单体故障影响全局 | 可考虑拆分 |
| 运维成本 | 能承受多服务部署和监控成本 | 运维资源有限 | 暂不拆分 |

综合评估，Phase 4 阶段建议**只做前后端分离（P4-8），不做微服务拆分（P4-9）**。微服务拆分留到用户量达到万级、团队扩编后再评估。过早拆分会增加部署复杂度和调试成本，与小团队的资源不匹配。

### 7.2 技术债务管理策略

技术债务在快速开发中不可避免，关键是要有意识地管理而非放任积累。建议采用"显式记录、定期偿还"的策略。

**显式记录**：每当因工期压力做出妥协（如临时硬编码、跳过测试、简化校验），在代码中用 `// TODO(debt):` 注释标记，并在项目看板上创建技术债务条目，记录债务位置、产生原因和预估偿还成本。这样技术债务是可见的，不会在代码中隐性积累。

**定期偿还**：每个 Phase 结束后预留 3-5 天的**债务偿还窗口**，集中清理本阶段积累的债务。偿还优先级按"影响数据正确性 > 影响系统稳定性 > 影响可维护性"排序。如果某个债务在两个 Phase 后仍未偿还，应升级为正式任务纳入下一个 Phase 的计划。

**债务红线**：有两类债务不允许积累。第一，**涉及数据正确性的债务**（如因子计算临时简化、数据校验跳过），必须在当前 Phase 内清偿，不允许跨 Phase。第二，**涉及 AI 幻觉防护的债务**（如合规过滤未接入、数据溯源缺失），必须在上线前清偿。这两类债务一旦遗留到线上，可能导致用户基于错误数据决策，是平台的信任红线。
