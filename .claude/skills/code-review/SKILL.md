# 代码评审器

本技能用于指导智能体针对本地开发代码、远程拉取请求开展专业且全面的代码评审工作。

评审**两条腿走路，缺一不可**：① 核心维度的定性分析；② 对照检测清单逐项检查。只有定性分析会让评审流于"感觉没问题"——逐项检测让评审结论可追溯、可打勾。

## 工作流程

### 1. 确定评审对象
*   **远程PR**：若用户提供PR编号或URL（例如"评审 PR #123"），则以该远程拉取请求为评审目标。
*   **本地变更**：若未指定具体PR，或用户要求"评审我的变更"，则以当前本地文件系统状态（暂存区与未暂存变更）为评审目标。

### 2. 评审准备

#### 远程PR场景：
1.  **检出代码**：使用 GitHub CLI 工具检出对应PR分支。
    ```bash
    gh pr checkout <PR编号>
    ```
2.  **前置校验**：按变更语言执行项目真实校验，提前排查编译/测试可发现的故障（本项目无 `npm run preflight`，勿使用）。
    ```bash
    node stock-watcher/run.js compile-dev   # Java 变更：增量编译（最快）
    node stock-engine/run.js test           # Python 变更：跑 engine 测试
    ```
3.  **明确上下文**：阅读PR描述与已有评论，理解变更目标与历史评审记录。

#### 本地变更场景：
1.  **识别变更范围**：
    *   查看状态：`git status`
    *   读取差异：`git diff`（工作区变更）和/或 `git diff --staged`（暂存区变更）。
2.  **前置校验（可选）**：变更规模较大时，可建议作者先跑对应校验：Java 用 `node stock-watcher/run.js compile-dev`，Python 用 `node stock-engine/run.js test`。

### 3. 深度分析

#### 3.1 核心维度定性分析
围绕以下核心维度对代码变更展开分析：

*   **正确性**：代码是否能实现预期目标，不存在缺陷或逻辑错误？
*   **可维护性**：代码是否整洁、结构清晰，便于后续理解与迭代修改？需综合考量代码清晰度、模块化程度，以及是否遵循既定设计模式等因素。
*   **可读性**：代码是否在必要位置补充了注释，格式是否统一规范，是否符合项目编码风格要求？
*   **执行效率**：本次变更是否引入了明显的性能瓶颈或资源浪费问题？
*   **安全性**：是否存在潜在安全漏洞，或采用了不安全的编码实践？
*   **边界场景与错误处理**：代码是否妥善覆盖了边界场景，对潜在异常是否有合理的处理逻辑？
*   **可测试性**：新增或修改的代码是否具备充足的测试覆盖（即便前置校验已通过）？可提出补充测试用例的建议，以提升测试覆盖度与代码健壮性。

#### 3.2 检测清单逐项对照（关键步骤，不可跳过）

**必须**对照两份检测清单逐项检查，给出每项的结论（✅通过 / ❌不通过 / ⚠️风险 / ➖不适用）：

-   **通用非功能性检测清单** → [`references/general-checklist.md`](./references/general-checklist.md)
    性能 / 缓存 / 事务 / 异常 / 并发 / 幂等 / 数据库 / 安全 / 日志 / API / 配置 / 可维护性 / 前端 共 13 大类（数据爬取/Tushare 专项见项目专项清单 E 组）。
-   **项目专项检测清单** → [`references/project-checklist.md`](./references/project-checklist.md)
    StockPulse 硬约束与高频易错点：engine 分层、API 参数封装、Map 禁用、魔法值、循环单条 SQL、Tushare 对接铁律（分页/超量降维/限流/大事务/批量）、akquant 滑点/T+1、run.js 启动等。

**智能裁剪规则（重要）：**

1.  先根据变更范围，确定需要检查的章节——两份清单顶部都有「适用范围」表，按表选择必查章节。
2.  **未检查的章节必须在报告里注明「未检查 + 原因」**，禁止静默跳过。静默跳过会让报告看起来"全通过"，这是对评审结论的污染。
3.  项目专项清单的每项都指向权威文档（CLAUDE.md / `.trae/rules/...`），检测到疑似问题时**去查权威文档确认细节，不要凭记忆判定**。
4.  涉及数据库 / SQL 时，**必须先查 `stock-watcher/src/main/resources/schema-mysql.sql`** 确认表结构与索引，勿凭记忆。

> **判定纪律：** 检测清单的「判定标准」是硬规则。命中"❌ 不通过"就如实报告，不要因为"代码能跑""改动很小""作者很资深"而放宽。

### 4. 输出评审反馈

**必须严格按以下结构输出（这是契约，不要增删主要章节、不要把结论埋在散文里）：**

```markdown
# 🔍 代码评审报告

## 评审总结
- 评审对象：[远程PR #xxx / 本地变更]
- 变更概述：[涉及文件 / 变更类型 / 涉及模块]
- 评审结论：[✅ 评审通过 / ⚠️ 有条件通过 / ❌ 要求变更]

## 检查覆盖范围
- 已检查章节：[列出]
- 未检查章节及原因：[列出，禁止省略]

## ❌ 必须修复项（严重级别不通过）
| # | 检测项编号 | 问题描述 | 涉及代码位置 | 修复建议 |
|---|-----------|---------|-------------|---------|

## ⚠️ 建议优化项（风险 / 建议级别）
| # | 检测项编号 | 问题描述 | 涉及代码位置 | 优化建议 | 优先级 |
|---|-----------|---------|-------------|---------|--------|

## 💡 细微问题（格式 / 风格，可选）
- [次要风格问题]

## ✅ 亮点（做得好的设计）
- [非功能性方面做得好的地方]

## 📊 总体评价
[一段话：本次变更的非功能性质量如何，是否可合并，主要风险点]
```

#### 表达语气
*   保持建设性、专业与友善的态度。
*   解释提出修改建议的原因与依据。
*   对于评审通过的内容，明确认可本次贡献的具体价值。

### 5. 收尾操作（仅远程PR场景）
*   评审完成后，询问用户是否需要切回项目默认分支（如 `main` 或 `master`）。
