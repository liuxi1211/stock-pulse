# 板块行情功能修复与优化

## 一、问题核查结论（根因已锁定）

通过代码审查 + 数据库实查（mcp_mysql）确认：**前端展示不出任何数据的根因在后端数据层，前后端契约本身是正确的**。

### 根因 1（致命）：`src` 取值不一致导致数据查不到

- 代码全局硬编码 `src = "SWS2021"`（17 处 Java + 2 处 SQL schema 注释）。
- 但 Tushare `index_classify` / `index_member_all` 接口**实际返回并落库的是 `src = "SW2021"`**（申万 2021 版本标准 src）。
- 数据库实查证据：
  - `sw_industry`：`src='SW2021'` 有 level=1 共 31 个、level=2 共 134 个、level=3 共 346 个；**`src='SWS2021'` 为 0 条**。
  - `sw_industry_member`：`src='SW2021' AND is_new=1` 有 17820 条；**`src='SWS2021'` 为 0 条**。
- 后果链：
  1. `SwIndustryServiceImpl.getIndustryRanking()` 第 1 步 `listByLevel(1)` → `selectByLevel(1, "SWS2021")` 返回**空列表**。
  2. 第 197 行 `if (industries.isEmpty()) return Collections.emptyList();` 直接返回空。
  3. 前端 `loadRankingData()` 收到空数组 → `renderHeatmap()` 不渲染格子、`renderRankingTable()` 显示"暂无数据"、不触发 `selectIndustry` → K线图和成分股都不加载。
  4. **整个页面全空**。这与"前端什么数据都展示不出来"的现象完全吻合。

### 根因 2（致命）：`index_daily` 表完全没有 801xxx.SI 行业指数数据

- 数据库实查：`SELECT ts_code FROM index_daily WHERE ts_code LIKE '801%'` → **0 行**。
- 原因：行业指数代码来源于 `IndexDailyFetchService.listSwL1IndexCodes()`，该方法同样调用 `selectByLevel(1, "SWS2021")`，因 src 不匹配返回空 → 定时任务从不抓取行业指数 → K线图必然空白。
- 根因 1 修复后，定时任务会自动开始抓取当日行业指数，但**历史 K 线数据缺失**，需手动触发一次历史回填。

### 非根因（已排除）

- 前后端字段命名一致：VO 用 Lombok `@Data`（驼峰序列化），前端读 `industryCode`/`pctChg`/`topGainerPctChg` 等均匹配。
- `StockApp` 公共方法（`get`/`escapeHtml`/`formatNumber`/`formatVolume`）均存在于 `common.js`。
- Mapper SQL（注解 + XML）实现完整，无缺失方法。
- Controller 参数校验完备。
- `IndexDailyController` 的 DESC→ASC 翻转逻辑正确。

## 二、已发现的其他 bug / 优化点

### Bug A（中等）：`SwIndustryServiceImpl.listByLevel(int)` 仍写死 "SWS2021"

`getIndustryRanking` 依赖 `listByLevel(1)` → 内部调用 `listByLevel(1, "SWS2021")`。即使其他地方改了 src，这里仍是硬编码，必须一并改。

### Bug B（中等）：`IndexDailyFetchService.listSwL1IndexCodes()` 同样写死 "SWS2021"

导致行业指数永不抓取。与根因 1 同源。

### Bug C（低）：`schema-mysql.sql` 注释和 `DEFAULT` 值写的是 'SWS2021'

`sw_industry.src` 和 `sw_industry_member.src` 的列默认值与注释都是 'SWS2021'，与实际 Tushare 返回值不符。虽不影响现有数据（插入时显式传 src），但会误导后续维护。

### 性能优化点 P1（推荐）：`getIndustryRanking` 的 N+1 风险

当前 6 步聚合中，`buildStockNameMap` 用 MyBatis-Plus `selectList(in(tsCode))` 一次查全量股票名（OK），但全量成分股 `selectAllCurrentL1Members` 一次返回 17820 条到内存再 Java 分组，数据量大时内存压力大。**本次不重写为 SQL（改动过大、风险高）**，仅在计划中记录，作为后续优化候选。

### 性能优化点 P2（可选）：行业排行接口无缓存

每次刷新都重算 6 步聚合 + 查 5 张表。可加本地缓存（如 Caffeine，TTL 到当日收盘后）。**本次不做**，避免扩大改动面。

## 三、修复方案（决策完成）

### 决策 1：src 统一为 `SW2021`

- 理由：Tushare 接口实际返回值就是 `SW2021`，库内现有 31 + 17820 条数据也是 `SW2021`，无需数据迁移。
- 改代码侧，不改数据库。

### 决策 2：修复范围 = 仅修 src + 触发数据同步

- 不重写聚合 SQL（风险高），不加缓存（改动大）。
- 修复 src 后，手动触发一次：① 行业分类 + 成分股重新拉取（幂等，验证 src 落库正确）；② 行业指数历史回填。

### 决策 3：测试范围 = Service 聚合逻辑 + Controller 校验

- 纯 Mockito 单测，不启动 Spring、不连 DB（与现有 `ScreenerServiceImplTest` 约定一致）。
- 不做 `@MybatisTest` + H2（成本过高，且 Mapper 逻辑简单）。
