# 数据预计算架构设计

> **目标**：
> 1. 把"每日数据更新后就不变"的聚合查询从「请求时实时算」改为「数据更新后预热 + 查询时懒兜底」，消除 5k 参数 SQL 等痛点
> 2. 建立**可扩展的预计算框架**，后续新数据源/新聚合接口按统一模式接入
> 3. **整合定时任务管理**到现有「数据管控中心」，让所有 cron 任务元信息（cron / 上次执行 / 下次执行 / 关联表）通过统一 API 可观测，新增任务只需加注解自动注册

---

## 一、当前现状分析

### 1.1 现有定时任务体系（15 个 task 类，26 处 `@Scheduled`）

| 时间 | 任务 | 更新的源表 | 缓存清理 |
|---|---|---|---|
| 16:00 | `DailyUpdateTask` | trade_cal / stock_basic / **daily_quote** / adj_factor / dividend | `@CacheEvict(sectorRanking, sectorMoneyflow, sectorValuation)` + 清 `kline` |
| 16:10 | `BasicDataTask` | **daily_basic** | `@CacheEvict(sectorValuation)` |
| 16:10 | `MoneyflowDataTask` | **stock_moneyflow** + 6 张资金类表 | `@CacheEvict(sectorMoneyflow)` |
| 16:25 | `IndexBasicTask` | index_basic | 无 |
| 16:30 | `IndexDailyFetchService` | **index_daily** | `@CacheEvict(sectorRanking)` |
| 16:30 | `FactorSnapshotTask` | factor_snapshot（已预计算） | 无 |

**核心问题**：
1. **任务间无事件机制**，完全靠 cron 时序错峰，前序任务延迟会导致后续读到不完整数据
2. **`@CacheEvict` 只清不填**，盘后清空缓存后，下一个用户首次访问仍然会触发 5k SQL
3. **缓存 TTL 30 min**，每隔 30 分钟会重新聚合一次（数据其实一天不变）
4. **没有任务完成事件**，无法可靠地"完成后触发预计算"

### 1.2 定时任务管理现状的问题

| 维度 | 现状 | 痛点 |
|---|---|---|
| cron 表达式 | 硬编码在 26 处 `@Scheduled` 注解中 | 改 cron 要遍历 15 个 task 类文件 |
| 任务元信息 | `InitStep.updateFrequency` 是**人工编写的展示字符串**（如"每个交易日 16:00"），与 `@Scheduled` 注解无运行时绑定 | 改 cron 后易忘记同步 InitStep，前端展示与实际调度脱钩 |
| 上次执行时间 | 仅"拉取类"任务在 `data_pull_log` 有记录；检测类在 `data_governance_metric.check_time` | 无法统一查询所有任务的上次执行 |
| 下次执行时间 | **完全没有** | 无法预知下次何时跑 |
| 任务执行历史 | `data_pull_log` 只覆盖 DataInitService 手动触发的拉取；`@Scheduled` 任务执行不留痕（除日志文件） | 定时任务失败后只能翻日志文件排查 |
| 任务启用/禁用 | 没有，只能注释代码重启 | 排错时不方便临时停某任务 |
| 与数据管控中心的关系 | `TableStatusVO.updateFrequency` 展示的是 `InitStep` 静态字符串，不是真实 cron | 用户看到的"更新频率"可能和实际不一致 |

### 1.3 现有实时聚合接口（首批接入预计算的范围）

| Service 方法 | 文件:行 | 当前实现痛点 | 依赖源表 |
|---|---|---|---|
| `SwIndustryServiceImpl.getIndustryRanking` | `SwIndustryServiceImpl.java:211` | **5k 参数 IN 查询** + 28 次循环查 index_daily + 全量查 stock_basic | daily_quote, sw_industry_member, index_daily, stock_basic |
| `SwIndustryServiceImpl.getIndustryMoneyflow` | `SwIndustryServiceImpl.java:460` | JOIN + GROUP BY 单 SQL | stock_moneyflow, sw_industry_member |
| `SwIndustryServiceImpl.getIndustryValuation` | `SwIndustryServiceImpl.java:502` | JOIN + GROUP BY 单 SQL | daily_basic, sw_industry_member |
| `MarketServiceImpl.getMarketIndices` | `MarketServiceImpl.java:111` | 已有缓存，但 key 用 `getLatestTradeDate()` 间接失效 | index_daily |
| `MarketServiceImpl.getMarketRanking` | `MarketServiceImpl.java:161` | **无缓存**，4 次单表 LIMIT 10 查询 | daily_quote |
| `MarketServiceImpl.getMarketTemperature` | `MarketServiceImpl.java:183` | JOIN + CASE WHEN SUM 聚合 | daily_quote, stock_basic |

**不接入预计算的接口**：
- `getIndustryMembers` / `getStockList` —— 分页 + 动态搜索，缓存粒度太细
- `ScreenerServiceImpl` —— 已有 `ScreenerResultCache`（24h TTL，SHA256 key），参数是动态 JSON 无法预先知道

### 1.4 现有缓存配置（`CacheConfig.java`）

```
sectorRanking / sectorMoneyflow / sectorValuation  → 30 min TTL
marketTemperature / indices                       → 无 TTL（用 tradeDate 做 key 自然失效）
```

### 1.5 现有数据管控中心模块边界

| 已有能力 | 缺失能力 |
|---|---|
| 表质量状态（NORMAL/DELAYED/ERROR/UPDATING） | 任务 cron 表达式 |
| 拉取历史（`data_pull_log`，仅手动触发） | 任务下次执行时间 |
| 检测历史（`data_governance_metric`） | `@Scheduled` 任务执行历史 |
| 运行中任务进度（`TaskProgressCache` 30 min） | 任务启用/禁用 |
| 前端页面 `data-governance.html` + 16 个 API | 任务与表的关联关系（运行时绑定） |

**整合策略**：扩展现有数据管控中心模块，把"定时任务元信息 + 执行历史"纳入其管理范围，不新建独立模块。

## 二、总体架构设计

### 2.1 五层架构图

```
┌──────────────────────────────────────────────────────────────────────┐
│  Layer 1: 数据更新任务层（整合 @ManagedTask 注解）                       │
│  DailyUpdateTask / BasicDataTask / MoneyflowDataTask /                │
│  IndexDailyFetchService / FactorSnapshotTask / ...                    │
│  每个 @Scheduled 方法标注 @ManagedTask(name, tableCode, group, desc)    │
│  完成后 publishEvent(DataUpdatedEvent) 替代 @CacheEvict                 │
└────────────┬─────────────────────────────────────┬───────────────────┘
             │                                     │
             ▼                                     ▼
┌────────────────────────────────┐   ┌──────────────────────────────────┐
│  Layer 2: 任务管理整合层           │   │  Layer 3: 事件分发层               │
│  @ManagedTask 注解 +              │   │  DataUpdatedEvent +              │
│  ScheduledTaskRegistryService +   │   │  PrecomputeEventDispatcher       │
│  TaskExecutionLogAspect (AOP)     │   │  根据 tableCode 路由到 Job        │
│  → 数据管控中心 /scheduled-tasks  │   │  @Async 异步执行                  │
└────────────────────────────────┘   └──────────────┬───────────────────┘
                                                    │
                                                    ▼
                                    ┌──────────────────────────────────┐
                                    │  Layer 4: 预计算任务层             │
                                    │  PrecomputeJob 接口 + 6 个实现    │
                                    │  调 computeXXX → cacheManager.put │
                                    └──────────────┬───────────────────┘
                                                   │
                                                   ▼
                                    ┌──────────────────────────────────┐
                                    │  Layer 5: Caffeine 缓存层          │
                                    │  TTL 24h；不再 @CacheEvict         │
                                    │  预热 + 懒兜底双保险                │
                                    └──────────────────────────────────┘
```

### 2.2 三大设计原则

#### 原则 1：事件驱动，而非 cron 时序
- 数据更新任务完成后 `publishEvent(DataUpdatedEvent(tableCode, tradeDate))`
- 预计算订阅事件，根据 `tableCode` 路由到对应 Job
- **解决**：cron 时序错峰的脆弱性（前序任务延迟导致后续读到脏数据）

#### 原则 2：依赖声明，自动路由
- 每个 `PrecomputeJob` 声明 `dependsOnTables()` 返回依赖的源表集合
- `PrecomputeEventDispatcher` 维护 `Map<tableCode, List<PrecomputeJob>>` 路由表
- **新增预计算**：实现 `PrecomputeJob` 接口 + `@Component` 注册，自动接入

#### 原则 3：预热 + 懒兜底，双保险
- **预热**：事件触发时主动算好结果塞进 Caffeine（用户首屏零延迟）
- **懒兜底**：查询时若缓存未命中（重启/未触发/过期），Spring `@Cacheable` 注解天然执行方法体并写缓存
- **解决**：用户选「仅预热 Caffeine」但不丢数据可用性

#### 原则 4：任务管理整合到数据管控中心
- 现有 26 处 `@Scheduled` 方法加 `@ManagedTask` 注解，声明任务名/关联表/分组/描述
- 运行时通过 Spring `ScheduledTaskHolder` 解析所有任务的真实 cron
- AOP 切面自动记录每次执行到 `task_execution_log` 表
- 数据管控中心新增 `/api/data-governance/scheduled-tasks` 接口和前端"定时任务"分区
- `InitStep.updateFrequency` 改为运行时从注册中心取真实 cron（启动时校验一致性，不一致打 WARN）

## 三、定时任务整合层详细设计（Layer 1 + Layer 2）

### 3.1 新增文件

#### 3.1.1 `@ManagedTask` 注解

**`annotation/ManagedTask.java`**
```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface ManagedTask {
    /** 任务名称（展示用，如"日线行情更新"） */
    String name();

    /** 关联的表代码，对应 InitStep.code；无关联表填空字符串（如 MetricCleanupJob） */
    String tableCode() default "";

    /** 任务分组：DATA_FETCH / GOVERNANCE / MAINTENANCE / PRECOMPUTE / VERIFY */
    String group();

    /** 任务描述 */
    String description() default "";
}
```

#### 3.1.2 任务执行历史 DO + Mapper

**`model/do/TaskExecutionLogDO.java`** + **`mapper/TaskExecutionLogMapper.java`** + XML

```sql
CREATE TABLE IF NOT EXISTS task_execution_log (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    task_name     VARCHAR(64) NOT NULL COMMENT '任务名称（@ManagedTask.name）',
    task_class    VARCHAR(128) NOT NULL COMMENT '任务类全限定名',
    method_name   VARCHAR(64) NOT NULL COMMENT '方法名',
    table_code    VARCHAR(32) DEFAULT NULL COMMENT '关联表代码',
    task_group    VARCHAR(32) NOT NULL COMMENT '任务分组',
    trigger_type  VARCHAR(16) NOT NULL COMMENT 'SCHEDULED / EVENT / MANUAL',
    start_time    VARCHAR(32) NOT NULL COMMENT '开始时间 yyyy-MM-dd HH:mm:ss',
    end_time      VARCHAR(32) DEFAULT NULL COMMENT '结束时间',
    duration_ms   BIGINT DEFAULT NULL COMMENT '耗时毫秒',
    status        VARCHAR(16) NOT NULL COMMENT 'SUCCESS / FAILED',
    error_message TEXT DEFAULT NULL,
    INDEX idx_task_log_name_time (task_name, start_time),
    INDEX idx_task_log_table (table_code, start_time)
);
```

保留期：3 个月，由 `MetricCleanupJob` 顺带清理（与 `data_pull_log` 一致）。

#### 3.1.3 任务元信息注册中心

**`service/ScheduledTaskRegistryService.java`** + **`service/impl/ScheduledTaskRegistryServiceImpl.java`**

核心职责：
1. **运行时解析所有 `@Scheduled` 任务**：注入 `ScheduledTaskHolder`（Spring 内置 Bean），调 `getScheduledTasks()` 拿到所有已注册的 `Task` 实例，反射读取方法上的 `@Scheduled` 和 `@ManagedTask` 注解
2. **构建任务元信息列表**：每个任务包含 taskClass / methodName / cron / tableCode / name / description / group
3. **计算下次执行时间**：用 Spring 的 `CronExpression.parse(cron).next(now)` 计算
4. **启动时一致性校验**：对每个带 `tableCode` 的任务，校验其 cron 与 `InitStep.fromCode(tableCode).expectedUpdateTime` 是否匹配，不匹配打 WARN（不阻断启动）
5. **提供查询 API**：`listScheduledTasks()` / `getScheduledTask(taskName)` / `getNextExecutionTime(taskName)`

#### 3.1.4 任务执行 AOP 切面

**`aspect/TaskExecutionLogAspect.java`**

- 切点：所有标注 `@ManagedTask` 的方法
- `@Around` 环绕通知：
  1. 记录 startTime
  2. 执行原方法
  3. 记录 endTime / durationMs / status=SUCCESS
  4. 异常时记录 status=FAILED + errorMessage
  5. 异步写入 `task_execution_log` 表（不阻塞主流程）
- trigger_type 推断：若调用栈中有 `ScheduledMethodRunnable` 则为 SCHEDULED；若有 `ApplicationEvent` 则为 EVENT；否则 MANUAL

#### 3.1.5 任务元信息 VO

**`dto/governance/ScheduledTaskVO.java`**
```java
@Data
@Builder
public class ScheduledTaskVO {
    private String taskName;          // @ManagedTask.name
    private String taskClass;         // 类全限定名
    private String methodName;        // 方法名
    private String cron;              // @Scheduled.cron
    private String tableCode;         // 关联表
    private String tableName;         // 关联表中文名（从 InitStep.label 取）
    private String taskGroup;         // 分组
    private String description;
    private String lastExecutionTime; // 最近一次执行开始时间（查 task_execution_log）
    private String lastStatus;        // 最近一次执行状态
    private Long lastDurationMs;
    private String nextExecutionTime; // 下次执行时间（CronExpression 计算）
    private Boolean enabled;          // 是否启用（默认 true，预留开关字段）
}
```

## 四、预计算层详细设计（Layer 3 + Layer 4 + Layer 5）

### 4.1 新增文件

#### 4.1.1 事件层（2 个文件）

**`event/DataUpdatedEvent.java`**（继承 `ApplicationEvent`）
```java
@Getter
public class DataUpdatedEvent extends ApplicationEvent {
    private final String tableCode;     // 源表代码（如 "daily_quote"）
    private final String tradeDate;     // 交易日 yyyyMMdd
    private final String source;        // SCHEDULED / MANUAL / INIT
}
```

**`event/PrecomputeEventDispatcher.java`**（`@Component`）
- `@PostConstruct`：扫描所有 `PrecomputeJob` Bean，构建 `Map<tableCode, List<PrecomputeJob>>` 路由表
- `@EventListener` + `@Async("precomputeExecutor")`：接收 `DataUpdatedEvent`，根据 tableCode 找到所有依赖的 Job，逐个调 `precompute(tradeDate)`，单 Job try-catch 隔离失败

#### 4.1.2 预计算框架（3 个文件）

**`service/precompute/PrecomputeJob.java`**（接口）
```java
public interface PrecomputeJob {
    String name();                           // Job 名称
    Set<String> dependsOnTables();           // 依赖的源表 tableCode 集合
    void precompute(String tradeDate);       // 执行预计算，结果塞入 Caffeine
}
```

**`service/precompute/AbstractPrecomputeJob.java`**（抽象基类）
- 模板方法：日志（开始/结束/耗时）、异常捕获、单 Job 锁（避免并发重复算同一 tradeDate）
- 子类只需实现 `doPrecompute(tradeDate)`

**`service/impl/PrecomputeServiceImpl.java`**（手动触发入口）
- `precomputeNow(String jobName, String tradeDate)`：懒兜底用，按 jobName 同步执行单个 Job
- `precomputeAll(String tradeDate)`：手动触发全部 Job（运维/排错用）
- `precomputeByTable(String tableCode, String tradeDate)`：手动触发依赖某表的所有 Job

#### 4.1.3 6 个具体 Job 实现

均位于 `service/precompute/` 目录，注入对应 Service + CacheManager：

| Job 类 | 依赖源表 | 调用的 Service 方法 | 写入的缓存 |
|---|---|---|---|
| `SectorRankingPrecomputeJob` | `daily_quote`, `sw_industry_member`, `index_daily`, `stock_basic` | `swIndustryService.computeIndustryRanking(tradeDate)` | `sectorRanking:{tradeDate}` |
| `SectorMoneyflowPrecomputeJob` | `stock_moneyflow`, `sw_industry_member` | `swIndustryService.computeIndustryMoneyflow(tradeDate)` | `sectorMoneyflow:{tradeDate}` |
| `SectorValuationPrecomputeJob` | `daily_basic`, `sw_industry_member` | `swIndustryService.computeIndustryValuation(tradeDate)` | `sectorValuation:{tradeDate}` |
| `MarketIndicesPrecomputeJob` | `index_daily` | `marketService.computeMarketIndices()` | `indices:{latestTradeDate}` |
| `MarketRankingPrecomputeJob` | `daily_quote` | `marketService.computeMarketRanking()` | `marketRanking:{latestTradeDate}` |
| `MarketTemperaturePrecomputeJob` | `daily_quote`, `stock_basic` | `marketService.computeMarketTemperature(tradeDate)` | `marketTemperature:{tradeDate}` |

> **关键**：Job 内部调用 Service 的 `computeXXX` 方法（无 `@Cacheable` 注解，绕过 AOP），拿到结果后用 `CacheManager.put` 显式写入缓存。

#### 4.1.4 异步线程池配置（1 个文件）

**`config/PrecomputeAsyncConfig.java`**
```java
@Configuration
@EnableAsync
public class PrecomputeAsyncConfig {
    @Bean("precomputeExecutor")
    public Executor precomputeExecutor() {
        ThreadPoolTaskExecutor exec = new ThreadPoolTaskExecutor();
        exec.setCorePoolSize(2);
        exec.setMaxPoolSize(4);
        exec.setQueueCapacity(50);
        exec.setThreadNamePrefix("precompute-");
        exec.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        exec.initialize();
        return exec;
    }
}
```

**问题**：Job 调用 `swIndustryService.getIndustryRanking(tradeDate)` 时，Spring AOP 会先查缓存，命中则直接返回（不执行方法体），导致 Job 拿到旧值。

**方案**：每个 Service 拆分 `getXXX`（带 `@Cacheable`）和 `computeXXX`（无注解，包可见）：

| Service | 公开查询方法（带 `@Cacheable`） | 内部计算方法（无注解） |
|---|---|---|
| `SwIndustryServiceImpl` | `getIndustryRanking` | `computeIndustryRanking` |
| `SwIndustryServiceImpl` | `getIndustryMoneyflow` | `computeIndustryMoneyflow` |
| `SwIndustryServiceImpl` | `getIndustryValuation` | `computeIndustryValuation` |
| `MarketServiceImpl` | `getMarketIndices` | `computeMarketIndices` |
| `MarketServiceImpl` | `getMarketRanking` | `computeMarketRanking` |
| `MarketServiceImpl` | `getMarketTemperature` | `computeMarketTemperature` |

`getXXX` 改为：
```java
@Cacheable(value = "sectorRanking", key = "T(com.arthur.stock.util.CacheKeyResolver).resolveSectorKey(#tradeDate)",
           unless = "#result == null || #result.isEmpty()")
public List<IndustryRankingVO> getIndustryRanking(String tradeDate) {
    return computeIndustryRanking(tradeDate);
}
```

Job 调用：
```java
public void precompute(String tradeDate) {
    List<IndustryRankingVO> result = swIndustryService.computeIndustryRanking(tradeDate);
    String key = CacheKeyResolver.resolveSectorKey(tradeDate);
    cacheManager.getCache("sectorRanking").put(key, result);
}
```

**`MarketServiceImpl.getMarketRanking`**（行 161）额外加 `@Cacheable`：
```java
@Cacheable(value = "marketRanking", key = "#root.target.getLatestTradeDate()")
```

### 4.3 关键技术点

#### 4.3.1 Job 并发控制
`AbstractPrecomputeJob` 内部维护 `ConcurrentHashMap<String, Boolean>` 记录正在执行的 `(jobName, tradeDate)`，避免事件重复触发。

#### 4.3.2 错误处理与可观测性
- 每个 Job 独立 try-catch，失败只打 ERROR 日志，不影响其他 Job
- 失败时不清缓存（保留旧值，避免缓存穿透）—— 配合懒兜底，下次查询会重试
- 通过 `@ManagedTask` 注解，预计算任务也可被 AOP 切面记录到 `task_execution_log`（group=PRECOMPUTE）

#### 4.3.3 与现有 `factor_snapshot` 的关系
- `FactorSnapshotTask` 是**持久化预计算表**模式（适合需要回溯历史的因子数据）
- 本架构是**内存预热模式**（适合不需要回溯、当日有效的聚合接口）
- 两者并存，互不影响。`FactorSnapshotTask` 也加 `@ManagedTask` 注解纳入统一管理

## 八、假设与决策

### 8.1 假设
1. Caffeine 缓存容量足够容纳 6 个接口 × 多日数据（每接口约 28 行业数据，1 日约 10KB，6 接口 × 30 日 ≈ 1.8MB）
2. 数据更新任务串行执行（单线程 `@Scheduled`），不会并发发布同一 tableCode 的事件
3. 预计算 Job 执行时间 < 30 秒（参照 `FactorSnapshotTask` 全市场预计算约 10 秒）
4. Spring `ScheduledTaskHolder` 能拿到所有 `@Scheduled` 注解注册的任务（Spring 4.0+ 内置能力）

### 8.2 关键决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 任务管理整合位置 | 扩展现有数据管控中心 | 用户明确要求，避免新建独立模块 |
| 任务元信息来源 | 运行时反射 `ScheduledTaskHolder` + `@ManagedTask` 注解 | 无需新建 DB 表存任务元信息；cron 改了立即生效 |
| 任务执行历史存储 | 新建 `task_execution_log` 表 | 现有 `data_pull_log` 只覆盖手动拉取，需统一记录所有 `@Scheduled` 任务 |
| `InitStep.updateFrequency` | 保留作为兜底展示，启动时校验一致性 | 向后兼容；改 cron 时打 WARN 提醒同步 |
| 预计算存储方式 | Caffeine 内存预热 | 用户明确选择，且数据一天不变、不需要回溯历史 |
| 懒兜底 | 是 | 用户明确要求"查询时没有当日数据要重新计算" |
| 事件机制 | Spring `ApplicationEvent` | 项目已有 `@EventListener` 用例（`BacktestServiceImpl`），无新依赖 |
| 异步执行 | `@Async` + 独立线程池 | 避免阻塞定时任务主流程；隔离预计算失败 |
| Job 注册 | Spring Bean 自动发现 | 无需配置文件，新增 Job 加 `@Component` 即可 |
| 缓存 TTL | 24h | 数据一天不变，30 min 失效过于激进 |
| `@CacheEvict` | 移除 | 由预计算主动 put 覆盖旧值，不需要 evict |

### 8.3 风险与缓解

| 风险 | 缓解 |
|---|---|
| AOP 切面影响所有 `@Scheduled` 方法性能 | 切面只做时间记录 + 异步写日志，同步部分 < 1ms |
| `ScheduledTaskHolder` 反射失败 | 启动时 try-catch，失败降级为空列表 + WARN 日志 |
| 预计算 Job 失败导致缓存为空 | 懒兜底机制保证查询时仍能拿到数据 |
| 事件分发器异常导致所有 Job 不触发 | Dispatcher 加 try-catch；懒兜底兜底 |
| Caffeine 重启后缓存清空 | 懒兜底自动重算 |
| `@Async` 线程池满 | `CallerRunsPolicy` 降级为同步执行 |
| Job 重复执行（同一 tradeDate 多次事件） | `AbstractPrecomputeJob` 内部 ConcurrentHashMap 去重 |
| `task_execution_log` 表膨胀 | 3 个月保留期，由 `MetricCleanupJob` 顺带清理 |
