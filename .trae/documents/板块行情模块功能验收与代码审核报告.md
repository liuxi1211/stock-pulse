## 一、老股民视角：产品设计与前端交互审核

### 1.1 功能设计合理性总评

**总体评价：功能骨架完整，但离"老股民真正爱用"还有明显差距。**

板块行情是 A 股交易者（尤其短线和轮动玩家）最高频使用的功能之一。当前实现做到了"能看到 28 个一级行业的涨跌概览 + K线 + 成分股"，这满足**最低可用性**，但对照东方财富/同花顺/通达信的板块功能，存在多处老股民会觉得"别扭"或"缺关键信息"的地方。

#### ✅ 做得好的地方

1. **热度图 + 排行表 + K线 + 成分股 四联动**：符合主流行情软件的板块页布局范式，单次 `/ranking` 接口驱动多视图，体验���畅。
2. **5 档色阶热力图**：>3% / 0~3% / 平 / -3~0% / <-3%，视觉直观，符合红涨绿跌的 A 股习惯。
3. **领涨/领跌股直接展示在排行表**：省去再点进去看龙头的需求，信息密度合理。
4. **K线默认 250 日 + MA5/10/20/60 可切换 + 十字光标联动 Legend**：技术分析基础能力齐备。

### 1.2 功能完整性缺口（含数据可得性核查）

#### 🔴 缺口 1（高频）：缺少"板块资金流向"——**数据已落库，需新增板块聚合层**
- **老股民视角**：判断板块轮动，"资金是否在进"比"今天涨多少"更重要。光看涨跌幅容易追高被套。
- **数据核查结论**：✅ **数据已落库，无需新对接 Tushare**
  - 表：`stock_moneyflow`（[schema-mysql.sql:604-627](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/schema-mysql.sql#L604-627)），含 `buy/sell_{sm,md,lg,elg}_amount`（小/中/大/特大单）+ `net_mf_amount`（净流入额）。
  - Tushare 已对接：`moneyflow` 接口（[TushareApiEnum.java:120-125](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/constant/TushareApiEnum.java#L120-L125)）。
  - 定时同步：每日 16:10（[MoneyflowDataTask.java](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/task/MoneyflowDataTask.java)）。
- **现状缺口**：现有 `MoneyflowService` 仅提供**个股维度**（`queryTop` 主力净流入 TOP N、`queryDetail` 单股明细，见 [MoneyflowService.java](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/MoneyflowService.java)），**未做板块维度聚合**。
- **实现路径**：`stock_moneyflow` JOIN `sw_industry_member`(is_new=1) 按 `index_code` 聚合 `SUM(net_mf_amount)` 或 `SUM(buy_lg+buy_elg-sell_lg-sell_elg)`（主力=大单+特大单）。**不新建表、不新对接接口**。
- **重复风险**：❌ 与 moneyflow 模块不重复（那是个股维度），属于互补新增。

#### 🔴 缺口 2（高频）：缺少"涨跌家数比/涨跌停家数"—��**数据已落库，市场级能力可下推**
- **老股民视角**：板块"普涨"和"一只权重股带涨"是不同信号。涨跌家数比是判断板块真实强度的核心指标。
- **数据核查结论**：✅ **数据已落库，市场级统计逻辑已存在可直接复用下推**
  - 涨停价表：`stock_stk_limit`（含 `up_limit`/`down_limit`，[schema-mysql.sql:353-360](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/schema-mysql.sql#L353-360)），Tushare `stk_limit` 已对接、每日同步。
  - **已有市场级实现**：[MarketServiceImpl.java:183-207](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/impl/MarketServiceImpl.java#L183-207) 的 `getMarketTemperature`，用 `daily_quote.pct_chg` + `stock_basic.market` 推算涨跌停家数（主板≥9.9%、创业板/科创板≥19.9%、北交所≥29.9%、ST≥4.9%）。
- **现状缺口**：`getIndustryRanking` 的 `IndustryRankingVO` 已有 `constituentCount`/`activeCount`，但**缺 `upCount/downCount/limitUpCount/limitDownCount`**。市场级 group by 全市场，板块级需加 `sw_industry_member.index_code` 维度。
- **实现路径**：在现有 6 步内存聚合里**零成本扩展**——遍历 `memberQuotes`（已 sorted）时按 pct_chg 正负、是否触涨停阈值统计。**无需新查询、无需新表**。
- **重复风险**：⚠️ 与 `MarketServiceImpl.getMarketTemperature` 逻辑同源（都是 pct_chg 推算），建议**抽取公共方法**避免两处阈值硬编码漂移。注意回测模块用的是精确版（JOIN stk_limit 比较 up_limit，[BacktestServiceImpl.java:734-744](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/impl/BacktestServiceImpl.java#L734-744)），板块统计用推算版即可（精度够、性能好）。

#### 🟡 缺口 3（中频）：缺少"板块轮动趋势/历史表现"——**数据已落库，可直接计算**
- **老股民视角**：板块轮动玩的是"持续多日资金流入+跑赢大盘"，只看一天毫无意义。需要近 5 日/20 日/年内涨跌幅。
- **数据核查结论**：✅ **数据已落库，现有 Service 直接可用**
  - 表：`index_daily` 已含行业指数（801010.SI~801980.SI），每日 16:30 由 [IndexDailyFetchService.java:113-132](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/IndexDailyFetchService.java#L113-132) 动态从 `sw_industry` level=1 读取并同步。
  - **现有 Service**：`IndexDailyService.getByCodeOrderByTradeDate(tsCode, limit)` 可取近 N 日行情，前端用 `close[-1]/close[-1-N]-1` 即可算 N 日涨跌幅。
- **实现路径**：在 `getIndustryRanking` 里为每个行业额外取近 5/20 日 close 算区间涨跌幅，或前端拿到 K线数据后自行计算。**无需新表、无需新对接**。
- **重复风险**：❌ 不重复。注意现有 ranking 的 `pctChg` 是行业指数**当日**涨跌幅，不是成分股聚合，口径要区分清楚。

#### 🟡 缺口 4（中频）：缺少"板块 PE/PB 估值分位"——**数据已落库，需新增加权聚合**
- **老股民视角**：板块涨多了要看"贵不贵"，估值分位（当前 PE 在历史 N 年分位数）是判断高/低位的关键。
- **数据核查结论**：✅ **数据已落库，需新增板块加权**
  - 表：`daily_basic`（[schema-mysql.sql:170-191](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/schema-mysql.sql#L170-191)），含 `pe`/`pe_ttm`/`pb`/`total_mv`/`circ_mv`（总/流通市值，万元）。
  - Tushare 已对接：`daily_basic`，每日 16:10 同步。
  - **现有 Service**：`DailyBasicService.listByCodesAndDate(tsCodes, tradeDate)` 支持批量查（可做板块聚合）。
- **实现路径**：`daily_basic` JOIN `sw_industry_member` 按 `index_code` 聚合，板块 PE 需按市值加权（`SUM(pe * total_mv)/SUM(total_mv)`）或算术平均。**无需新表、无需新对接**。
- **重复风险**：⚠️ `MarketServiceImpl.getStockList` 已 JOIN daily_basic 返回个股估值（13 列），但那是**个股维度**；板块加权是新增，不冲突。注意复用 `DailyBasicService` 的批量查询，不要重写。

#### 🟢 缺口 5（低频）：缺少"概念板块"维度——**❌ 唯一需从零搭建的功能**
- **老股民视角**：A 股题材炒作时代，概念板块（AI、低空经济等）比行业板块更活跃，但申万行业是基础盘，优先级合理。
- **数据核查结论**：❌ **当前完全不可实现，需从零搭建全链路**
  - 无表：`schema-mysql.sql` 全文无 concept 相关表，仅有申万行业表。
  - 未对接：`TushareApiEnum`（27 个接口）无 `concept`/`concept_detail`，全代码搜索"概念"无业务命中。
  - 无数据。
- **实现路径（若要做）**：① 新建 `concept`+`concept_detail` 表 ② `TushareApiEnum` 新增枚举 ③ 新建 `ConceptService`+`ConceptTask` ④ 新建 Controller。**工作量大，建议作为 v2 规划**。
- **重复风险**：无。

#### 🟢 缺口 6（低频）：缺少"个股反向查板块"——**能力已存在，仅缺前端入口**
- **数据核查结论**：✅ **后端能力已具备**
  - `SwIndustryMemberMapper.selectCurrentL1ByTsCode(tsCode)` 已能按股查当前一级行业（[SwIndustryMemberMapper.java:37-42](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/mapper/SwIndustryMemberMapper.java#L37-42)）。
- **实现路径**：仅在个股详情页加"所属板块"标签，点击跳回板块页。**无需新接口**（可复用已有 mapper，或前端调 `/api/industry/list` 反查）。
- **重复风险**：❌ 不重复。

#### 💡 复用与查重总结（避免重复开发）
- **核心复用点**：`SwIndustryService.getIndustryRanking` 已实现当日行业排行，新增功能应**在其基础上扩展**，不要重写。
- **前端入口已存在**：`PageController.sector()` 已渲染 `/page/sector`，后端 API 走 `/api/industry/*`（SwIndustryController），**无需新建 SectorController**。
- **可复用的现成数据源**：`stock_moneyflow`（资金流）、`daily_basic`（估值）、`index_daily`（行业指数历史）、`stock_stk_limit`（涨跌停）、`sw_industry_member`（成分股关系）**全部已落库且有 Service**。
- **避免重复**：涨跌停统计逻辑应抽取 `MarketServiceImpl` 的阈值常量共用，不要在板块模块再硬编码一遍。

### 1.3 前端 UI 交互问题（按严重度排序）

#### 🔴 交互问题 1：`btnRefresh` 刷新按钮触发的只是 `loadRankingData`，不刷新成分股和 K线
- **位置**：[sector.js:49](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L49) `btnRefresh.addEventListener('click', loadRankingData)`
- **问题**：用户点"刷新"期望整个页面数据更新，但实际只重新拉了排行数据。若用户当前停留在某行业的成分股第 3 页，点刷新后成分股和 K线**纹丝不动**，与用户预期不符。
- **建议**：刷新时应同时触发 `selectIndustry(currentIndustry)` 重新加载 K线 + 成分股。

#### 🟡 交互问题 2：排行表行点击使用 `onclick` 内联 + 全局 `SectorPage` 对象，与事件绑定风格不一致
- **位置**：[sector.js:281](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L281)
- **问题**：表格其他交互（排序、分页）都用 `addEventListener`，唯独行点击用 `onclick="SectorPage.selectByCode(...)"` 内联。风格不统一，且 `SectorPage` 挂 window 形成隐式全局。
- **影响**：轻微，不影响功能，但维护性差。

#### 🟡 交互问题 3：成分股搜索框右侧的搜索按钮是"死按钮"
- **位置**：[sector.html:102](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/templates/pages/sector.html#L102)
- **问题**：`<button class="btn btn-outline-secondary"><i class="bi bi-search"></i></button>` 没有 `id`、没有绑定事件。用户点击它毫无反应，只能靠 `input` 的 debounce 触发搜索。
- **建议**：要么给按钮绑定 click 触发搜索，要么移除按钮避免误导。

#### 🟡 交互问题 4：成分股分页"下一页"无边界保护
- **位置**：[sector.js:111-116](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L111-116)
- **问题**：`nextBtn` 点击直接 `memberPage++` 后请求，**没有判断是否已到最后一页**。当用户在最后一页继续点"下一页"，会请求一个超出总页数的 page，后端返回空列表，前端显示"暂无成分股"，体验割裂。
- **建议**：根据 `pageData.total / pageData.size` 计算 `totalPages`，到末页时禁用 next 按钮。

#### 🟡 交互问题 5：K线 `全部` 范围用 `limit=9999` 硬编码，非真正"全部"
- **位置**：[sector.js:83](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L83) `currentRange = range === 'all' ? 9999 : parseInt(range, 10)`
- **问题**：若某行业指数历史超过 9999 个交易日（约 40 年，目前不现实但语义不准），会被截断。更重要的是，`/api/index-daily` 的 `limit` 默认 250、无上限校验（见后端 §2.2），传 9999 会一次性拉取全量，**浪费带宽**。
- **建议**：`all` 应传一个合理的上限（如 3650 = 10 年），或后端支持 `limit=0` 表示全量。

#### 🟢 交互问题 6：表格无"涨跌幅/成交额"以外的列可排序，且排序状态无视觉指示
- **位置**：[sector.js:52-63](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L52-63)
- **问题**：只有 `pctChg` 和 `amount` 两列可排序，表头箭头图标始终是 `bi-arrow-down-up`（双向），**点击后不变成单向箭头**，用户不知道当前是升序还是降序。
- **建议**：根据 `sortState` 动态切换为 `bi-arrow-down` / `bi-arrow-up`。

#### 🟢 交互问题 7：热度图 Tooltip 在屏幕右下角会溢出
- **位置**：[sector.js:228-232](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L228-232) `tooltipEl.style.left = (e.clientX + 14)`
- **问题**：Tooltip 定位用 `clientX + 14`，鼠标移到屏幕右侧时 Tooltip 会溢出视口产生横向滚动条。
- **建议**：判断 `clientX + tooltipWidth > window.innerWidth` 时改为 `clientX - tooltipWidth - 14`。

#### 🟢 交互问题 8：成分股成交额用 `formatVolume`（成交量格式化），单位混淆
- **位置**：[sector.js:376](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L376) `var amtStr = m.amount != null ? StockApp.formatVolume(m.amount) : '--'`
- **问题**：成交额（元）和成交量（手）用了同一个 `formatVolume` 格式化函数，而排行榜里的成交额用的是 `formatNumber(x, 1) + '亿'`（[sector.js:182](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L182)）。**两处成交额展示格式不一致**，老股民会困惑。
- **建议**：统一成交额格式化逻辑。

### 2.1 🔴 性能问题

#### P0-性能 1：`getIndustryRanking` 每次刷新全量加载 17820 条成分股到内存
- **位置**：[SwIndustryServiceImpl.java:206](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/impl/SwIndustryServiceImpl.java#L206)
  ```java
  List<SwIndustryMemberDO> allMembers = swIndustryMemberMapper.selectAllCurrentL1Members(SwIndustryConstants.SW_SRC);
  ```
- **问题**：每次调用 `/api/industry/ranking` 都把当前一级成分股**全量**（约 17820 条）拉到 JVM 内存，再 Java `groupingBy` 分组、stream 排序取首尾。
- **放大效应**：
  - 紧接着 [L216-221](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/impl/SwIndustryServiceImpl.java#L216-221) 用这 17820 个 `tsCode` 去查 `daily_quote`（IN 17820 个元素的查询）和 `stock_basic`。
  - **`daily_quote` IN 17820 元素**：MySQL 对超长 IN 列表优化差，且 `daily_quote` 是千万级大表，即使有 `(ts_code, trade_date)` 索引，单次 IN 上万也会产生显著开销与解析成本。
- **严重度**：高。并发用户一多，内存 + DB 双重压力。
- **建议**：
  1. **短期**：给 ranking 接口加 Caffeine 本地缓存，TTL 到当日收盘后（数据一天只变一次，没必要每次重算）。这是修复文档 P2 已识别但未做的项。
  2. **中期**：把"领涨/领跌股"改为 SQL 聚合（按 index_code 分组取 `MAX/MIN(pct_chg)` 对应股票），避免全量回表到内存。需权衡改 SQL 的风险。
  3. **`stock_basic` 名称查询**：5000 行小表，建议直接全量缓存（`Map<tsCode, name>`），不要每次 IN 查。

#### P1-性能 2：`/api/index-daily` 的 `limit` 无上限，可被恶意拉全表
- **位置**：[IndexDailyController.java:56](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/controller/IndexDailyController.java#L56)
  ```java
  @RequestParam(defaultValue = "250") int limit  // 无上限校验
  ```
- **问题**：前端"全部"按钮传 `limit=9999`，但接口本身**没有上限校验**。恶意/误操作传 `limit=999999` 会一次性拉取 `index_daily` 全量，拖垮 DB。
- **对比**：同文件 `/api/industry/members` 的 `size` 严格限制 1~100，而这个接口的 `limit` 完全没限制，**校验风格不一致**。
- **建议**：`limit` 限制在 1~3650（10 年日线）之间，超界返回 400。

#### P2-性能 3：成分股分页查询 `ORDER BY q.pct_chg DESC` 在大表上可能慢
- **位置**：[DailyQuoteMapper.xml:313](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/mapper/DailyQuoteMapper.xml#L313)
- **问题**：`selectMembersWithQuote` 是三表 JOIN（`sw_industry_member` INNER `stock_basic` LEFT `daily_quote`），最后 `ORDER BY q.pct_chg DESC LIMIT size OFFSET offset`。
  - `daily_quote` 的 `pct_chg` 列通常无独立索引（主索引是 `ts_code, trade_date`），`ORDER BY pct_chg` 易触发 **filesort**。

- **缓解**：单行业成分股通常几百只，JOIN 后结果集不大，实际可能可接受。但需用 `EXPLAIN` 验证。`countMembersWithQuote` 同理。
- **建议**：验证执行计划；若慢，考虑给 `daily_quote(trade_date, pct_chg)` 加索引，或改用覆盖索引 + 延迟关联。

#### P3-性能 4：ranking 接口全程无缓存
- **位置**：[SwIndustryServiceImpl.java:192-232](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/impl/SwIndustryServiceImpl.java#L192-232)

- **建议**：见 P0-性能 1 的短期方案。

### 2.2 🟠 逻辑 Bug 与数据正确性

#### Bug 1（中）：`/api/index-daily` 的 `tsCode` 参数完全未校验
- **位置**：[IndexDailyController.java:48-50](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/controller/IndexDailyController.java#L48-50)
- **问题**：`tsCode` 是 `@RequestParam String tsCode`（required=true 但无格式校验）。传入任意字符串（如 `'; DROP TABLE--`）虽不会造成 SQL 注入（MyBatis 参数化），但会直接打到 DB 做无意义查询，**缺少前置防御**。
- **对比**：`SwIndustryController` 对 `industryCode` 有正则 `\d{6}(\.SI)?`，这个接口却完全没有。
- **建议**：加 `tsCode` 格式校验（如 `[A-Z0-9]{6,9}(\.(SH|SZ|SI))?`）。

#### Bug 2（中）：成分股查询 `LEFT JOIN daily_quote` 缺失行情时，`pctChg` 为 null 的排序不稳定
- **位置**：[DailyQuoteMapper.xml:307,313](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/mapper/DailyQuoteMapper.xml#L307)
  ```sql
  LEFT JOIN daily_quote q ON m.ts_code = q.ts_code AND q.trade_date = #{tradeDate}
  ...
  ORDER BY q.pct_chg DESC
  ```
- **问题**：
  1. 用 `LEFT JOIN`，当某成分股当日**停牌/无行情**时，`q.pct_chg` 为 NULL。MySQL 中 `ORDER BY ... DESC` 时 NULL 默认排在**最前**（取决于 `NULLS` 语义），导致停牌股排在涨幅榜顶部，**违反直觉**。
  2. 多个 NULL 之间顺序不确定，分页时可能出现**数据重复或丢失**（跨页错位）。
- **建议**：`ORDER BY (q.pct_chg IS NULL), q.pct_chg DESC`，让 NULL 沉底；或前端排序时统一把 null 当 0 处理。

#### Bug 3（中）：`getIndustryMembers` 的 `tradeDate` 永远传 null，Controller 无法指定历史日期
- **位置**：[SwIndustryController.java:80](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/controller/SwIndustryController.java#L80)
  ```java
  return ApiResponse.success(swIndustryService.getIndustryMembers(industryCode, null, page, size, keyword));
  ```
- **问题**：Service 签名支持 `tradeDate`，但 Controller **硬编码传 null**，意味着前端永远只能看"最新交易日"的成分股行情，**无法回看历史某天的板块成分表现**。
- **影响**：与 ranking 接口支持 `tradeDate` 形成不对称；想做"昨天板块谁领涨"的历史复盘做不到。
- **建议**：Controller 增加 `@RequestParam(required=false) String tradeDate` 透传，并做 `\d{8}` 校验。

#### Bug 4（中）：前端排序把 null 当 0，与"无数据"语义混淆
- **位置**：[sector.js:250-252](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/resources/static/js/sector.js#L250-252)

#### Bug 5（低）：`buildStockNameMap` 用 MyBatis-Plus `selectList(in(tsCode))`，超长 IN 有硬限
- **位置**：[SwIndustryServiceImpl.java:265-267](file:///d:/lcProject/stock-pulse/stock-watcher/src/main/java/com/arthur/stock/service/impl/SwIndustryServiceImpl.java#L265-267)

## 四、总体结论

### 4.1 产品视角结论
板块行情模块完成了 **PRD FR-1 ~ FR-7 的基础闭环**，作为"看申万一级行业今日涨跌"的工具**够用**。但距离老股民日常高频使用的产品（对标东方财富/同花顺）还有明显差距，核心短板是**只看到"今天的涨跌"，看不到"资金的进出、板块的真实强度（涨跌家数）、轮动的趋势、估值的高低"**。

### 4.2 功能缺失项的落地可行性（关键结论）
经逐项核查数据库表、Tushare 对接情况、定时同步任务、其他模块已有能力，得出：
- **除"概念板块"外，其余 5 项功能缺口所需数据均已落库**（`stock_moneyflow`/`daily_basic`/`index_daily`/`stock_stk_limit`/`sw_industry_member` 全部已有且有 Service）。
- **无需新建数据表、无需新对接 Tushare 接口**（概念板块除外），主要工作是在 `SwIndustryController`/`SwIndustryService` 上**新增聚合查询**。
- **不会与现有模块重复开发**：moneyflow/daily_basic/market 模块都是**个股或市场维度**，板块维度是互补新增；唯一需注意"涨跌停阈值"应抽取 `MarketServiceImpl` 的常量共用，避免硬编码漂移。
- 实现优先级建议（按性价比）：**缺口 2（涨跌家数，零成本）> 缺口 3（N日趋势，直接算）> 缺口 1（资金流聚合）> 缺口 4（估值加权）> 缺口 6（反查入口）> 缺口 5（概念板块，v2）**。

### 4.3 技术视角结论
后端架构清晰、Controller 校验规范、表结构与索引设计合理，**整体工程质量在合格线以上**。但存在两个必须重视的问题：
1. **ranking 接口的性能隐患**（全量内存聚合 + 大表 IN 查询 + 无缓存）是技术债的重灾区，随着用户量增长会率先暴露。
2. **成分股分页的 NULL 排序 bug** 是真实的正确性问题，会导致分页数据错位，应优先修复。

其余多为健壮性、防御性编码和体验优化，不影响主流程，可排期渐进修复。

### 4.4 验收建议
- **准予验收通过**（功能闭环完整、无阻断性 bug）。
- **附带整改建议**：P0 优先修复"ranking 缓存 + 成分股 NULL 排序"；P1 功能迭代从"涨跌家数 + N日趋势"切入（性价比最高，数据现成）。
