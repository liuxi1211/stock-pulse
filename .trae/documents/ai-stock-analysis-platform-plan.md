# AI 优先的股票分析平台 - 项目规划书（v2）

## 一、项目概述

### 1.1 项目定义

本平台是一个面向 C 端个人投资者的**互联网 AI 投资助手**，以自然语言对话为核心交互方式，采用 SaaS 模式云端部署。用户通过富交互 Chat 页面提问股票相关问题，平台调用数据查询、因子计算、研究分析、定时任务等能力，以**股票卡片、实时图表、结构化报告**等富媒体形式返回结果，而非纯文本回复。

与 stock-pulse 的根本区别：stock-pulse 是「规则化量化」本地部署系统；新平台是「对话化研究」的 C 端互联网产品。stock-pulse 仅作为参考项目，新平台从零构建全新代码库，借鉴其 Tushare 六层数据架构设计思路和 AI skill 研究方法体系，但不复用其代码。

### 1.2 目标用户

个人 A 股投资者，尤其是：
- 有一定投资经验但不具备专业研究能力，看不懂券商研报的散户
- 想要「问一句、答一串」式即时分析，同时希望看到数据图表提升信任度的用户
- 需要自动盯盘、定时跟踪自选股和板块动态，但没时间手动操作的上班族

### 1.3 核心差异化

| 维度 | 本平台 | 竞品短板 |
|------|--------|----------|
| 数据深度 | 25+ Tushare 接口 + 六层治理，数据可溯源 | FinChat 依赖第三方 API，口径不透明 |
| 分析方法 | 18 种研究方法映射为 Spring AI Graph 节点，可组合 | 财搭子 32 个 Agent 扁平堆叠，缺乏编排深度 |
| **交互体验** | 富交互 Chat：股票卡片 + 实时图表 + 数据可视化 + 常用问题引导 | 竞品多为纯文本对话或固定模板 |
| **个性化** | 自动盯盘 + 异动推送 + 报告中心 + 持仓管理 | 竞品仅支持预设推送，无自定义任务 |
| **报告管理** | 专业报告中心（分类/搜索/收藏/对比），非散落在对话历史 | 竞品报告散在聊天记录中，难以回溯 |
| 部署形态 | C 端 SaaS 互联网产品，用户无需部署 | 券商 AI 绑定账户生态 |

### 1.4 关键设计原则

1. **数据与 AI 分离**：数值计算全部走确定性代码，AI 只做解读和表达，避免幻觉
2. **富交互优先**：对话不只是文字，而是股票卡片、图表、报告的富媒体流
3. **渐进式架构**：初期前后端一体，做大后拆分微服务
4. **用户引导**：提供常用问题模板，降低用户使用门槛
5. **报告资产化**：分析报告是对话产物，更是可管理、可回溯的用户资产

## 二、可行性分析（小白投资者视角）

### 2.1 需求真实性

普通散户的信息获取路径：财经 App 推送 -> 股吧雪球讨论 -> 券商研报（看不懂）-> 凭感觉买卖。核心痛点是**信息过载但有效分析不足，且缺乏数据可视化支撑信任**。

用户问「茅台现在贵不贵」，系统不应只回复文字，而应返回一张**股票卡片**（当前价、涨跌幅、PE 分位）+ 一张**PE 历史折线图** + AI 文字解读「当前 PE 处于近 5 年 78% 分位，偏贵」。这种从自然语言到「数据 + 图表 + 结论」的富媒体跨越，是建立用户信任的关键。

三个约束必须正视：
1. **AI 分析的边界**：数值计算交给确定性代码，AI 只做解读和表达
2. **合规红线**：不提供买卖建议，所有分析标注「不构成投资建议」
3. **成本控制**：模型调用按量计费，数据积分成本需控制

### 2.2 技术可行性

| 维度 | 评估 | 依据 |
|------|------|------|
| Tushare 数据 | 可行 | 参考 stock-pulse 已验证的六层架构和 5 条铁律，重新实现 |
| AI 对话框架 | 可行 | Spring AI Alibaba 提供 ChatClient/Graph/RAG/Function Calling 全栈 |
| 富交互前端 | 可行 | SSE 流式 + ECharts 图表 + 组件化卡片，技术成熟 |
| C 端 SaaS 部署 | 可行 | Spring Boot 单体可支撑初期，后续按需拆分 |
| 用户个性化 | 可行 | Quartz 调度 + WebSocket 推送 + 事件驱动架构 |

## 三、竞争分析

### 3.1 竞品矩阵

| 竞品 | 核心能力 | 交互形态 | 个性化 | 报告管理 | 短板 |
|------|----------|----------|--------|----------|------|
| **FinChat** | 10万+全球股票对话查询 | 纯文本对话+图表 | 低 | 无 | 无自定义任务，无 ERP |
| **财搭子** | 32个垂直Agent，跨券商跟踪 | 对话+模拟回放 | 中，预设Agent | 散在对话中 | Agent扁平堆叠，无本地数据治理 |
| **AI 涨乐** | 券商原生AI | 对话 | 低 | 账户内 | 强绑定华泰，非客户不可用 |
| **daily_stock_analysis** | 自动日报（14.5k星） | 无对话，固定报告 | 低 | 无 | 无交互，分析维度固定 |
| **同花顺问财** | 自然语言选股筛选 | 自然语言筛选 | 中 | 无 | 仅筛选，无深度分析 |

### 3.2 市场空白与切入点

**空白一：富交互对话体验。** 竞品的对话多为纯文本问答，缺少股票卡片、实时图表、数据可视化。本平台在对话流中嵌入富媒体组件（股票卡片、K线图、PE分位图、资金流向图），让用户在对话中「看到」数据，提升信任度和科技感。

**空白二：用户自建定时任务 + 智能盯盘。** 竞品的定时推送都是平台预设的。本平台提供对话式任务创建 + 自动盯盘引擎：用户说「盯住茅台，跌破1700就通知我」，系统自动创建监控规则，触发时推送分析报告。

**空白三：专业报告中心。** 竞品的分析报告散落在对话历史中，用户难以回溯和管理。本平台将分析报告资产化，提供独立的报告中心：按股票/行业/类型分类、搜索、收藏、对比、导出。

### 4.2 双项目职责划分

| 维度 | C 端用户应用 | B 端 ERP 系统 |
|------|-------------|---------------|
| **定位** | 面向个人投资者的 AI 对话产品 | 面向运维/管理员的数据管理后台 |
| **端口** | :8080 | :8081 |
| **前端** | 富交互 Chat 页面 + SPA 式动态页面 | Thymeleaf SSR 管理页面 |
| **数据库权限** | 只读查询 + 用户业务表读写 | 全量读写（数据采集/治理） |
| **AI 能力** | Spring AI Alibaba 全栈 | 无 |
| **用户认证** | C 端用户注册/登录（手机号/微信） | 管理员账号 |
| **部署** | 独立部署，面向公网 | 内网部署，不暴露公网 |
| **数据流** | 从 MySQL 读取 Tushare 数据 -> AI 分析 -> 返回用户 | 从 Tushare API 拉取 -> 写入 MySQL -> 质量检测 |

### 4.3 渐进式架构策略

**初期（Phase 0-2）：前后端一体**
- C 端应用前端（Chat 页面等）与后端（Java）在同一个 Spring Boot 项目中
- 前端资源放在 `src/main/resources/static` 下，通过 Spring Boot 静态资源服务
- 后端提供 REST API + SSE 流式接口
- 优点：开发快、部署简单、调试方便

**中后期（Phase 3+）：前后端分离**
- 当 C 端用户量增长、前端复杂度提升时，拆分为独立前端项目（Vue/React）
- 后端纯 API 服务，前后端独立部署
- 可进一步按业务域拆分微服务（对话服务、数据服务、任务服务等）

### 5.2 对话容器体系（参考 AI Chat 产品设计最佳实践）

对话流中的每条 AI 回复不是简单的文字气泡，而是**富媒体容器**。参考行业 AI Chat 容器设计体系，分为以下类型：

| 容器类型 | 用途 | 触发场景 | 示例 |
|----------|------|----------|------|
| **股票行情卡片** | 展示实时行情 + 关键指标 | 用户查询某只股票 | 茅台当前价/涨跌幅/PE/PB/成交量 + K线缩略图 |
| **数据图表卡片** | 可视化数据展示 | AI 分析需要图表辅助 | PE历史折线图、资金流向柱状图、行业对比雷达图 |
| **结构化文本容器** | Markdown 渲染分析结论 | 深度分析、研报摘要 | 分层排版的分析报告，关键数据加粗 |
| **交互表单容器** | 引导用户补充信息 | 需要用户确认或选择 | 「请选择分析维度：技术面/基本面/估值」快捷按钮 |
| **报告预览容器** | 完整报告的对话内预览 | 生成深度研究报告 | 报告摘要 + 「查看完整报告」「收藏」「创建任务」操作按钮 |
| **任务确认容器** | 确认定时任务/盯盘规则 | 用户创建任务 | cron 表达式 + 执行内容 + 推送渠道 + 「确认创建」按钮 |

**容器设计核心原则**：
1. **高信噪比**：用户 0.5 秒内抓到核心信息，弱化分割线，靠字号/字重/留白分层
2. **行动导向**：容器本身是交互触发器，点击股票卡片可跳转详情页
3. **流式体验**：文字打字机输出 + 图表骨架屏占位，消除等待焦虑
4. **对话内完成**：所有交互在对话流内完成，避免跳转新页面打断沉浸感

### 7.4 报告与对话的关系

报告在对话中生成，但生成后独立存在于报告中心。两者关系：

1. **对话中生成报告**：用户在对话中请求深度分析 -> AI 生成报告 -> 对话流中展示报告预览容器（摘要 + 操作按钮）-> 完整报告存入报告中心
2. **报告中心查看**：用户随时在报告中心查看、搜索、收藏、对比历史报告
3. **对话引用历史报告**：用户问「上次分析的茅台现在怎么样了」-> AI 从报告中心检索历史报告 -> 对比当前数据生成跟踪分析
4. **报告内可追溯**：每份报告标注生成时的数据快照，用户可查看「AI 给出这个结论时用了什么数据」

### 7.5 报告对比功能

支持两份同类报告的横向对比：
- 选择两份不同时间的茅台深度分析报告，对比关键指标变化
- 对比 AI 观点变化（上次结论 vs 本次结论）
- 可视化差异（指标变化趋势图）

## 十二、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| AI 幻觉（编造数据） | 用户基于错误数据决策 | 数值计算走确定性代码；报告节点数据校验；每点溯源标注 |
| 模型调用成本失控 | 费用超预期 | 轻量查询用 qwen-turbo，深度分析用 qwen-plus；每日上限；缓存查询 |
| Tushare 接口限流 | 数据更新失败 | RateLimiter 阻塞限流；5 条铁律；data_pull_log 记录失败 |
| Graph 工作流超时 | 深度报告卡住 | 节点级超时；Human-in-the-loop 跳过可选节点；长任务异步+推送 |
| 对话上下文丢失 | 多轮对话断裂 | ChatMemory 持久化 MySQL；long-term memory 摘要 |
| C 端并发压力 | 响应变慢 | JDK 21 虚拟线程；Redis 缓存热点数据；后期拆分微服务 |
| 数据权限冲突 | ERP 写入与 C 端读取冲突 | 读写分离：ERP 独占写入，C 端只读查询；MySQL 读写锁 |

## 十三、假设与决策

### 13.1 关键假设

1. 通义千问 DashScope API 持续提供稳定服务和免费额度
2. 用户持有 Tushare Pro 2000 积分可覆盖接口需求
3. 部署环境为云服务器，可部署 Java + Python + MySQL + Redis
4. ifind MCP 在 Phase 4 才需要，前三个 Phase 不依赖
5. 平台定位为信息整理和研究辅助，不提供买卖建议

### 13.2 关键决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 项目结构 | 两个独立项目（C 端 + B 端 ERP） | 职责分离，C 端面向公网用户，ERP 内网管理数据 |
| 前后端 | 初期一体，后期分离 | 快速开发优先，Phase 4 拆分 |
| 新建 vs 复用 | 全新代码库，参考 stock-pulse 设计 | 交互范式完全不同，全新项目更清晰 |
| 前端框架 | 初期原生 JS，后期 Vue 3 | 初期轻量快速，后期可平滑迁移 |
| 向量数据库 | Redis Stack | SaaS 部署降低运维 |
| 模型 | 通义千问 | 原生适配，中文能力强 |
| 报告管理 | 独立报告中心，非散在对话中 | 报告资产化，可管理可回溯 |
| 个性化推送 | WebSocket 实时 + 邮件 + 微信 | 分层推送，满足不同场景 |
