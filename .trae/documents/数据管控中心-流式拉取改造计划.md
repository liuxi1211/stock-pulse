# 数据管控中心：流式拉取改造计划（拉一批处理一批）

## 摘要

核查 stock-watcher 模块 25 张业务表的增量/全量更新逻辑后发现：spec 022（增量/全量逻辑正确性、数据丢失、SQLite 兼容、事务安全）**已完成**，不在本次范围。本次聚焦用户提出的新问题——**"先从 Tushare 把全部数据拉到内存再统一处理"**的反模式，改造成"拉一页、转一页、存一页"的流式处理，以降低内存峰值、在分页间引入天然停顿以缓解 Tushare 限流。

经逐一核查全部 Service 实现，确认**仅 4 个文件**存在分页累积反模式，需改造；其余 21 个文件无此问题。

---

## 一、现状分析

### 1.1 反模式定位

反模式特征：分页拉取循环中用 `all.addAll(page)` 把所有页累积到一个大 List，循环结束后才统一 `toEntity` + `saveBatch`。问题：
- **内存**：全量重建时单次调用可能跨多页（单股票 30 年日线、全市场全日期涨跌停等），DTO 与 Entity 两份完整列表同时驻留内存；
- **限流**：所有 Tushare 分页请求密集发出（中间无 DB I/O 停顿），更易触发 Tushare 429；DB I/O 集中在末尾，未起到"拉取间隙"的天然节流作用。

### 1.2 已确认需改造的 4 个文件

| `StockStkLimitServiceImpl.java` | `fetchAndSaveAll` L54-74（`all.addAll` @L64） | 全市场全日期多页 | `@Transactional` 包整个循环（L53） | `int` | `persistByBizKey` 按 (ts_code,trade_date) 分批 delete+insert |
| `StockSuspendDServiceImpl.java` | `fetchAndSaveAll` L57-77（`all.addAll` @L67） | 全市场全日期多页 | `@Transactional` 包整个循环（L56） | `int` | `persistByBizKey` 同上 |

### 1.4 关键依赖确认

- **TransactionTemplate 先例**：`ExpressServiceImpl`(L44/L62)、`ForecastServiceImpl`(L46/L64)、`StrategyServiceImpl`(L78/L92) 均注入并使用 `TransactionTemplate`。Spring Boot 自动配置，可直接 `private final TransactionTemplate transactionTemplate;` 构造器注入。
- **流式参考实现**：`SwIndustryServiceImpl.fetchAndSaveAllMembers`（L119-145）已是目标范式——循环内 `persistMembers(page)` 逐页落库。
- **DailyQuote 返回值依赖**：`TushareApiController.java:39` 使用 `fetchAndSaveDailyQuotes` 返回的 `List<DailyQuoteDTO>` 返回给前端；`DailyUpdateTask`/`DataVerifyTask` 调用 `fetchAndSaveByTradeDate` 时**忽略返回值**。因此 DTO 返回契约需保留。

## 二、改造方案

### 2.1 总体策略

1. **注入 `TransactionTemplate`**（构造器注入，遵循现有先例）；
2. **移除方法级 `@Transactional`**（原为包裹整个分页循环的长事务，长事务持锁久、失败回滚量大）；
3. **循环内流式处理**：每拉一页 → 立即 `toEntity` + 用 `transactionTemplate.execute(...)` 落库该页 → 拉下一页；
4. **保留页内分批**：`Lists.partition(list, BATCH_SIZE)` 的 delete+insert 不变；
5. **幂等安全**：所有 persist 均为"先删后插"，部分页成功后失败重跑不会产生重复（已删的再删为空，新数据幂等覆盖）。
6. **事务粒度=每页一个独立事务**：单页失败不影响已提交页；重跑幂等覆盖。

### 2.2 文件级改动要点

#### 2.2.1 DailyQuoteServiceImpl.java

**改动**：`doFetchAndSaveDailyQuotes` 和 `fetchAndSaveByTradeDate` 改流式。

- 新增私有方法 `fetchAndSavePagesStreaming(DailyQueryDTO baseParam)`：循环内每页 `tushareClient.daily(param)` → `toEntity` 该页 → `transactionTemplate.execute(saveQuotes)` → 累积该页 DTO 到返回列表。
- `doFetchAndSaveDailyQuotes`（L90-127）与 `fetchAndSaveByTradeDate`（L134-155）改为调用流式方法；**移除**其 `@Transactional`（事务下沉到页内）。
- **保留 `fetchAllPages`（L224-250）不改**：`queryByCodeAndDateRange`（L53-60）与 `queryByTradeDate`（L66-71）是纯查询方法，不落库，必须返回完整列表。
- DTO 返回值：流式方法仍累积每页 DTO 到返回列表（供 `TushareApiController` 使用）。Entity 不再全量累积——峰值内存从"全量DTO+全量Entity"降为"全量DTO+单页Entity"。
- **为什么**：单股票 30 年日线可能跨多页；单日全市场 5000+ 股票也常跨页。流式落库让每页 DB I/O 成为分页间的天然节流。
- **怎么改**：抽 `fetchAndSavePagesStreaming`；`saveQuotes` 改为接收单页 Entity 列表（内部仍 `Lists.partition` 分批）。

#### 2.2.2 StockStkLimitServiceImpl.java

**改动**：`fetchAndSaveAll`（L54-74）改流式。

- 循环内每页：`tushareClient.stkLimit(...)` → `persistByBizKey(page)` 包进 `transactionTemplate.execute(...)` → 累加 count。
- **移除**方法级 `@Transactional`（L53），事务下沉到页内 `persistByBizKey`。
- `persistByBizKey`（L120-134）**无需改**：已按 (ts_code, trade_date) 分批 delete+insert，天然支持逐页调用。
- `fetchAndSaveIncremental`/`fetchAndSaveByRange`：单次 API 调用无分页，保留现有 `@Transactional`。
- **为什么**：全市场全日期涨跌停跨多页，累积后一次性 persist 内存峰值高。

#### 2.2.3 StockSuspendDServiceImpl.java

**改动**：`fetchAndSaveAll`（L57-77）改流式。与 stk_limit 完全同构。

- 循环内每页 `persistByBizKey(page)` 包进 `transactionTemplate.execute(...)`。
- **移除**方法级 `@Transactional`（L56）。
- `persistByBizKey` 无需改（按 ts_code+trade_date 分批 delete+insert）。

#### 2.2.4 StockNamechangeServiceImpl.java

**改动**：`fetchAndSaveAll`（L55-75）改流式，**且落库方法从 `persistByTsCode` 改为 `persistByBizKey`**。

- **⚠️ 关键正确性**：`persistByTsCode`（L103-124）按 ts_code **全删**该股票所有记录再插入。若流式逐页调用，第 2 页会删掉第 1 页已插入的记录 → 数据丢失。因此流式版本必须用 `persistByBizKey`（按 ts_code+start_date 单条 delete+insert，幂等，跨页安全）。
- 循环内每页：`persistByBizKey(page)` 包进 `transactionTemplate.execute(...)`。
- **移除**方法级 `@Transactional`（L54）。
- `persistByBizKey`（L129+）已存在（增量路径用），无需新增。
- **验证 `persistByBizKey` 是否已实现 delete+insert**：实施时确认该方法存在且语义正确；若仅 insert 无 delete，需补 delete 逻辑。

### 2.3 不在本次范围

- 不重做 spec 022（增量/全量逻辑、SQLite 兼容、事务已全部完成）；
- 不改数据库 schema、不改 Mapper XML；
- 不改纯查询方法（DailyQuote 的 `query*`）；
- 不改 controller / 定时任务调用契约（返回值类型保持不变）。

## 三、假设与决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 事务粒度 | 每页一个独立事务（TransactionTemplate） | 长事务持锁久、回滚代价大；页内事务失败不影响已提交页，重跑幂等 |
| 事务实现 | TransactionTemplate（编程式） | 代码库已有 3 处先例；同类 self-invocation 下 `@Transactional` 代理失效，编程式更可靠 |
| DailyQuote 返回值 | 保留 `List<DailyQuoteDTO>` 累积 | `TushareApiController:39` 依赖返回值；改契约影响面大、超出用户诉求 |
| DailyQuote 内存收益 | 仅省 Entity 全量累积 | DTO 仍累积供返回；但 Entity（含多 BigDecimal 字段）不再全量驻留，峰值约降一半 |
| StockNamechange 落库 | persistByTsCode → persistByBizKey | persistByTsCode 按 ts_code 全删，流式逐页会丢数据；persistByBizKey 按业务键幂等 |
| 纯查询方法 | 保留 fetchAllPages 不改 | 不落库，必须返回完整列表 |
| BATCH_SIZE | 保持 500 不变 | 现有配置，不引入变更 |

## 四、验证步骤

1. **编译验证**：`mvn -q compile`（stock-watcher 模块），确认 4 文件 import（TransactionTemplate）无缺失、无报错。
2. **日志确认按页落库**：触发单表全量重建（如 `POST /api/data-governance/tables/stk_limit/full-rebuild`），日志应出现多次"page ... saved"而非单条"Saved N records"。
3. **单表增量触发**：`POST /api/data-governance/tables/daily/incremental-update`，确认 DailyQuote 正常返回 DTO 列表（API 契约不变）。
4. **事务独立性**：人为制造第 2 页失败（如临时改错字段），确认第 1 页已提交、重跑后幂等覆盖、无重复数据。
5. **内存对比**：全量重建 stk_limit / suspend_d / namechange 前后对比 JVM 堆峰值（Entity 不再全量累积）。
6. **数据一致性回归**：改造后 4 张表总记录数与改造前一致（`SELECT COUNT(*)`）。
7. **StockNamechange 专项**：全量重建后确认历史记录完整（未被 persistByBizKey 误删），抽查某 ts_code 的全部更名记录均在。
8. **定时任务回归**：`DailyUpdateTask`（调用 `fetchAndSaveByTradeDate`）正常执行，无异常。
