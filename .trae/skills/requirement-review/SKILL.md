# 需求评审（Requirement Review）

## 概览

对一份需求文档，先做**结构化预处理**，再用**三个独立上下文的子代理**分别从【产品/UX】【研发/架构】【测试/质量】三个视角并行评审，最后**汇总去重 + 冲突检测 + 优先级排序**，产出一份可直接驱动决策的综合报告。

**核心原则：**

- **三个子代理必须独立上下文**，互不"污染"——每个角色只从自己的专业视角出发，不会因为看到另一个角色的观点而妥协。
- **先结构化再评审**——三个角色基于相同的事实基础评审，减少理解偏差。
- **汇总时做去重 + 冲突检测**——多角色共识的问题置信度更高；冲突点暴露的是需求本身的矛盾。

## 何时使用

**触发关键词：** 需求评审、评审需求、review requirement、审需求、需求找茬

**适用：**

- 用户提供需求文档（markdown 文件路径 / 粘贴文本 / 口头描述），要求评审
- 开发前对 PRD 做质量把关
- 想快速知道"哪些必须改、哪些可以不管"

**不适用：**

- 需求文档过于简略（少于 200 字）——先提示用户补充基本信息再评审
- 只是单纯写需求（用 brainstorming/prd 类 skill）
- 评审的是已写好的代码（用 code-review 类 skill）



**关键决策点：** 三个子代理**必须并行且独立**——在同一条消息里分派 3 个 Agent（每个独立上下文），不要串行、不要把前一个角色的结论传给后一个。

## 执行步骤

### 第一步：需求结构化预处理

解析需求，提取以下要素（缺失则标记"未定义"）：

```
- 功能名称
- 目标用户
- 核心用户故事（As a... I want... So that...）
- 功能点清单
- 数据实体（涉及哪些数据表/对象）
- 外部依赖（第三方 API、数据源等）
- 非功能性要求（性能、安全、并发等）
- 验收标准
```
 
这份结构化结果是后续三个子代理的**共享输入**。

如果需求少于 200 字：**先停下来**，提示用户补充基本信息后再评审，不要硬评。

### 第二步：分派 3 个独立子代理（并行）

**必须使用 dispatching-parallel-agents 的模式：在一条消息里发 3 个 Agent 调用，并发执行，互不传阅结论。**

把第一步的结构化需求作为输入传给每个子代理。每个子代理的完整角色设定、评审维度、输出格式见：

- **产品/UX 评审官** → `references/product-reviewer.md`
- **研发/架构评审官** → `references/tech-reviewer.md`
- **测试/QA 评审官** → `references/qa-reviewer.md`

每个参考文件可直接作为对应子代理的 system prompt / 任务指令。

### 第三步：汇总评审结果

三份报告到手后，由主代理汇总，遵循以下规则：

1. **去重合并**：三个角色可能发现同一问题（如"空状态未定义"），合并为一条并标注"多角色共识"。
2. **冲突处理**：若不同角色对同一问题给出矛盾建议（如产品要"展示所有数据"、研发要"必须分页"），标注冲突并给平衡建议。
3. **优先级排序**（所有问题按此排序）：

   - **P0（阻塞）**：不解决无法开发
   - **P1（严重）**：不解决会导致返工
   - **P2（建议）**：不解决影响质量但不阻塞
   - **P3（可选）**：锦上添花
## 最终输出格式

汇总报告**必须**严格按此结构输出（这是契约，不要增删章节、不要把结论埋在散文里）：

```markdown
# 📋 需求评审综合报告

## 需求名称：[XXX]
## 评审结论：[通过 / 有条件通过 / 不通过]

## 一、评审结论摘要
| 角色 | 评价 | 核心关注点 |
|------|------|-----------|
| 👤 用户视角 | [一句话] | [最关注的1-2个问题] |
| 🔧 研发视角 | [一句话] | [最关注的1-2个问题] |
| 🧪 测试视角 | [一句话] | [最关注的1-2个问题] |

## 二、多角色共识问题（高置信度，必须处理）
[至少两个角色都提到的问题]
| # | 问题 | 提出角色 | 优先级 | 建议处理方式 |
|---|------|---------|--------|-------------|

## 三、各角色独立发现的关键问题
### P0 阻塞项
| # | 问题 | 来源角色 | 详细说明 | 建议 |
### P1 严重问题
| # | 问题 | 来源角色 | 详细说明 | 建议 |
### P2 建议优化
| # | 问题 | 来源角色 | 建议 |
### P3 可选优化
| # | 问题 | 来源角色 | 建议 |

## 四、角色间冲突点（需要决策）
| # | 冲突描述 | 角色 A 观点 | 角色 B 观点 | 平衡建议 |

## 五、需求补充建议
### 建议补充的验收标准
| 功能点 | 验收标准 | 来源 |
### 建议补充的边界/异常定义
| 场景 | 预期行为 | 来源 |

## 六、下一步行动项
| # | 行动项 | 负责人 | 截止时间建议 |

## 附录：各角色完整评审报告
[产品视角报告] / [研发视角报告] / [测试视角报告]
```
 
## 快速参考

| 步骤     | 动作                         | 关键约束            |
|----------|------------------------------|---------------------|
| 1 预处理 | 提取 8 要素，缺失标记"未定义" | <200 字先停         |
| 2 分派   | 3 个 Agent，一条消息并发      | 独立上下文，互不传阅 |
| 3 汇总   | 去重 + 冲突检测 + P0-P3 排序 | 按契约结构输出      |

## 常见错误

| 错误                                | 后果                    | 正确做法                |
|-------------------------------------|-------------------------|-------------------------|
| 串行跑子代理、把前一个结论传给后一个 | 角色互相污染，失去独立性 | 一条消息并发 3 个 Agent |
| 主代理自己代替三个角色评审          | 丢失多视角，置信度下降   | 必须分派真实子代理      |
| 汇总时不去重                        | 同一问题重复列三遍      | 合并并标"多角色共识"    |
| 跳过冲突检测                        | 需求自身矛盾被掩盖      | 矛盾建议单独列入第四节  |
| 建议空泛（"优化用户体验"）            | 无法执行                | 必须具体可执行          |
| 需求过短仍硬评                      | 评审基于臆测            | <200 字先让用户补充     |

## 注意事项

- 需求涉及特定领域（金融、医疗等）时，在子代理 prompt 中追加领域知识提示。
- 评审中的"建议"必须**具体可执行**，禁止空泛表述。
- 需求过大时，建议用户拆分后分批评审，避免单次评审过载。
